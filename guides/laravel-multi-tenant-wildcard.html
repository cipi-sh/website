Multi-tenant Laravel SaaS with wildcard subdomains

Build a SaaS where every customer gets their own subdomain, explained from zero: how wildcard DNS, routing and certificates fit together, setting them up with Cloudflare and Cipi, resolving the tenant in Laravel, custom domains for customers, and when to give a tenant its own app instead.

By Andrea PollastriUpdated November 23, 20263 min read

Share

A multi-tenant app serves many customers from one codebase. A common shape gives each customer an address like acme.yourapp.com. Three things have to line up: DNS sends every subdomain to your server, Nginx sends them to your app, and a certificate covers all of them.

Before you start#

  • A Laravel app on Cipi with its primary domain, e.g. yourapp.com (first deploy).
  • The domain's DNS on Cloudflare (free). Moving DNS doesn't move your traffic: you can keep records "DNS only" (grey cloud).

1. DNS records#

In Cloudflare, add:

TypeNameContentProxy
A@your server IPyour choice
A*your server IPsame as above

2. A Cloudflare API token#

Cloudflare → My Profile → API Tokens → Create token → template "Edit zone DNS", limited to this zone. That's the only permission needed (Zone → DNS → Edit).

bash
sudo cipi ssl dns set --token=YOUR_CLOUDFLARE_TOKEN

3. Route every subdomain to the app#

bash
sudo cipi alias add saas '*.yourapp.com'      # the quotes matter
sudo cipi alias list saas

4. Issue the wildcard certificate#

bash
sudo cipi ssl install saas --dns=cloudflare
sudo cipi ssl status
curl -sI https://acme.yourapp.com | head -1
HTTP/2 200

Takes about a minute. Renewals reuse the same token automatically. If the records are proxied (orange cloud), set Cloudflare SSL/TLS to Full (strict).

5. Find the tenant in Laravel#

A middleware reads the subdomain and loads the tenant:

php
// app/Http/Middleware/ResolveTenant.php
public function handle(Request $request, Closure $next)
{
    $host = $request->getHost();                       // acme.yourapp.com
    $sub  = Str::before($host, '.yourapp.com');

    $tenant = Tenant::where('slug', $sub)
        ->orWhere('custom_domain', $host)
        ->firstOrFail();

    app()->instance(Tenant::class, $tenant);
    URL::defaults(['tenant' => $tenant->slug]);

    return $next($request);
}

Or with route domains:

php
Route::domain('{tenant}.yourapp.com')->middleware('tenant')->group(function () {
    Route::get('/', DashboardController::class);
});
ConcernTip
Data isolationA global scope on tenant_id, or a package such as stancl/tenancy or spatie/laravel-multitenancy
SessionsLeave SESSION_DOMAIN empty so each tenant has its own cookie; .yourapp.com only to share a login across tenants
Queued jobsPass the tenant id to the job; don't rely on the request
Cache keysPrefix with the tenant: "tenant:{$id}:stats"
Reserved namesBlock www, api, admin, mail as tenant slugs

6. Customer custom domains#

A customer wants portal.acme.com. The routing part is easy: add it as an alias and save it as the tenant's custom_domain.

bash
sudo cipi alias add saas portal.acme.com

The certificate needs a plan. An app has one certificate; with a wildcard issued over Cloudflare DNS, a name outside your Cloudflare zone can't join it over DNS, and a plain HTTP reissue would drop the wildcard.

ApproachHowGood for
Cloudflare for SaaS (recommended)Customers CNAME to a hostname you proxy; Cloudflare issues each customer's certificate at the edge; your origin keeps its wildcard and Full (strict)Many customers, self-service
Separate app for custom domainsA second Cipi app from the same repository, pointed at the same database, with the customer names as aliases and an HTTP-01 certificate (cipi ssl install)A handful of customers, no Cloudflare
No wildcardList every tenant subdomain and custom domain as aliases, HTTP-01, up to 100 names per certificateFew, known tenants

Automate whichever you pick from your app with the Cipi API when a customer saves the domain (POST /api/apps/{name}/aliases, then POST /api/apps/{name}/ssl).

7. When to give a tenant its own app#

Step 1 of 4Shared app

All tenants in one database, separated by a tenant_id column. Cheapest and simplest; start here.

Step 2 of 4Database per tenant

One database per tenant, same code. Stronger separation and per-tenant restores, more to manage.

Step 3 of 4App per tenant

One Cipi app per tenant: its own user, PHP, database and backups. Created through the API at signup.

Step 4 of 4Server per tenant

A dedicated server for a tenant who pays for it (enterprise contracts, data residency).

For the last two, create apps through the API from your signup flow (POST /api/apps), one per tenant, each with its own domain, database and backups.

Questions

Do I need Cloudflare?

For an automatic wildcard certificate, Cipi automates Cloudflare's DNS (free plan is fine). With another DNS provider you can list subdomains one by one or bring your own wildcard certificate.

How many tenants can one app serve?

As many as the app and server can handle: the wildcard covers every one-level subdomain with a single alias and a single certificate.

Can customers use their own domain?

Yes. Routing is one alias; the certificate needs a plan because an app has one certificate. Cloudflare for SaaS is the smoothest; the guide lists the alternatives.

Does `a.b.example.com` work?

Not with a single wildcard: *.example.com covers one level only. Keep tenants one label deep.

One database or one per tenant?

Start with one database and a tenant_id column (simplest, cheapest). Use a database per tenant, or a whole Cipi app per tenant, when customers need strict isolation, their own backups or their own server.

Will `api.example.com` be caught by the wildcard?

Not if api.example.com belongs to another app: exact names always win over the wildcard.

What if a step fails?

Read the troubleshooting table above first. Then check the matching docs page, open a GitHub issue, or ask in the community. Most commands print the fix when they refuse something.
