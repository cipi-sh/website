Upgrade PHP for a Laravel app without downtime

How PHP versions work on a server, explained from zero: running several versions side by side, checking your code and Composer dependencies, moving one app at a time with zero downtime, rolling back, nightly security patches, end-of-life versions and Octane's own PHP.

By Andrea PollastriUpdated November 23, 20262 min read

Share

PHP has a new minor version every year (8.4, 8.5, 8.6…), each supported with security fixes for a few years. Moving apps forward keeps them fast and patched. On a Cipi server you can do it one app at a time, test it, and move back in seconds if needed.

Key ideas, in plain words#

TermMeaning
Minor version8.5, 8.6: new features, small breaking changes
Patch version8.5.3 → 8.5.4: bug and security fixes only
PHP-FPM poolThe PHP processes that serve one app's web requests
Server defaultThe version for php on the command line and new apps
End of life (EOL)No more security fixes from PHP: move off it
  • shopPHP 8.6 pool
  • blogPHP 8.4 pool
  • legacyPHP 8.3 pool
  • Nginxroutes each domain to its app's pool

Before you start#

  • Know your app's current version: sudo cipi app show shop.
  • Read the PHP migration notes for the target version (php.net has one per minor).
  • Have a backup or a pre-deploy snapshot.

1. Check your code locally#

bash
php -v                                    # run the target version on your laptop
composer why-not php 8.6                  # which dependencies block it
composer update                           # within your constraints
php artisan test

Update composer.json's "php" constraint (e.g. "^8.3") only if you want to drop old versions. Commit the updated composer.lock.

2. Install the version on the server#

bash
sudo cipi php list
sudo cipi php install 8.6
PHP versions
$ sudo cipi php list
$ sudo cipi php install 8.3
$ sudo cipi app edit blog --php=8.5

The install adds the version next to the others. Nothing changes for running apps.

3. Try it on a copy first#

With a staging app (or a clone):

bash
sudo cipi app clone shop --domain=shop-86.example.com --name=shop-86
sudo cipi app edit shop-86 --php=8.6
sudo cipi deploy shop-86

Click through, run the queue, check sudo cipi app logs shop-86 --type=laravel for deprecations.

4. Move the app#

bash
sudo cipi app edit shop --php=8.6
Step 1 of 5New pool

A PHP-FPM pool for the app is created on the new version.

Step 2 of 5Vhost

The app's Nginx vhost is pointed at the new pool.

Step 3 of 5Nginx reload

Nginx reloads gracefully: requests in flight finish, new ones use the new PHP.

Step 4 of 5Workers, cron

Workers and cron lines switch to the new PHP binary and restart.

Step 5 of 5Old pool

The app's pool on the old version is removed. The old version itself stays installed for other apps.

Then deploy once, so Composer installs dependencies under the new version:

bash
sudo cipi deploy shop

If the lock file rejects the new version, the deploy fails and the live release keeps running: update the dependency, commit, deploy again.

5. Roll back if needed#

bash
sudo cipi app edit shop --php=8.5
sudo cipi deploy shop --rollback          # if a deploy changed the vendor folder

6. Change the server default and clean up#

bash
sudo cipi php switch 8.6                  # CLI `php`, panel, new apps
sudo cipi php remove 8.3                  # refused while any app uses it

Patches happen on their own#

WhatWhenHow
PHP security releasesEvery night at 03:30Only affected pools restart
Check nowAny timesudo cipi php upgrade
Octane appsWith FrankenPHPsudo cipi frankenphp upgrade

sudo cipi php list shows the state of each version: patched, VULNERABLE (a fix exists, not installed yet), distro, END OF LIFE, prerelease. How CVEs are handled.

php.ini settings survive#

Settings set with sudo cipi ini move with the app. Check them after the switch:

bash
sudo cipi ini list --app=shop

Troubleshooting#

ProblemFix
Your lock file does not contain a compatible set of packagesA dependency doesn't support the version yet: composer why-not php 8.6, update or wait
Assigning is refused: missing extensionsThe extension isn't published for that version yet; --force only if the app doesn't use it
Deprecation warnings flood the logSet LOG_DEPRECATIONS_CHANNEL=null while you fix them
php -v shows the old versionThat's the server default: sudo cipi php switch (apps use their own anyway)
Worker still on the old versionsudo cipi worker restart shop

Questions

Can apps on one server use different PHP versions?

Yes. Each app has its own PHP-FPM pool with its own version. Deploys, Composer, cron and workers always use the app's version, never the server default.

Is the switch really without downtime?

Yes. Cipi starts the new pool, points the app's vhost at it and reloads Nginx; requests in flight finish on the old pool.

What if the new version breaks the app?

Move it back with the same command (--php= the old version). Both versions stay installed until you remove one.

Which versions can I install?

8.3 to 8.6. Older versions on old servers are listed, patched by the distro if possible and can be removed, but aren't offered to apps.

Do I need to patch PHP myself?

No. Cipi applies PHP security releases every night at 03:30 and restarts only the affected pools. sudo cipi php upgrade does it now.

What about Octane apps?

They run the PHP inside their FrankenPHP binary. sudo cipi frankenphp upgrade updates it; sudo cipi php upgrade lists them too.

A new PHP minor is out but an extension isn't.

Cipi installs what's available, records what's missing and adds it as soon as it's published. Assigning the version to an app that needs the missing extension is refused, with the list.
