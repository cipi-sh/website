cipi.yml: keep your server settings in the repository

Version PHP, workers, scheduler, domains, databases, health checks, backups and deploy options next to your Laravel code, review them in pull requests, and apply them safely.

By Andrea PollastriUpdated November 23, 20262 min read

Share

Most panels keep an app's server settings in a database you can't review. Cipi lets you put them in cipi.yml, a file at the root of your repository. It travels with each release: you review it in a pull request, see exactly what it would change, and apply it in one step.

  1. Commit cipi.ymlreviewed like code
  2. Deploythe file ships with the release
  3. Planevery change listed first
  4. Applyall or nothing

1. Start from what the app already has#

bash
sudo cipi yml generate shop --save
cat /home/shop/cipi.yml

Commit that file at the root of the repository. After the next deploy, cipi yml plan shop should say there's nothing to do: the file describes the server as it is.

2. Describe the app#

A typical Laravel app:

yaml
version: 1

app:
  php: "8.6"
  aliases: ["www.shop.example.com"]
  www: to-root
  ini: { upload_max_filesize: 50M }

workers:
  horizon: true
  reverb: true

schedule: true
search: true

health:
  url: "https://shop.example.com/up"
  rollback_on_unhealthy: true

deploy:
  branch: main
  predeploy_snapshot: true
  node_build: "npm ci && npm run build"
  post:
    - artisan cache:clear

env: { required: [STRIPE_KEY, STRIPE_SECRET, MAIL_HOST] }

backup:
  profiles:
    - { name: shop-nightly, scope: all, cron: "0 2 * * *", keep_days: 14, destinations: [s3], encrypt: true }
BlockReplaces
appcipi php, cipi alias, cipi www, cipi ini, cipi app limits
workers, schedulecipi worker, cipi app reverb, the scheduler cron
searchcipi search enable
healthcipi health set
deploycipi deploy-config
backup.profilescipi backup profile

The full list, with routes, proxies, crons and Node apps, is in the cipi.yml reference.

3. Validate before you push#

Install the Cipi Agent in the app and validate with the same rules as the server, locally or in CI:

bash
composer require cipi/agent
php artisan cipi:yml validate

Add # yaml-language-server: $schema=./cipi.schema.json at the top of the file (after php artisan cipi:yml schema --write) for autocompletion in VS Code or PhpStorm.

4. Plan and apply#

After deploying the release that contains the file:

cipi.yml
$ cipi yml plan shop
$ cipi yml apply shop
$ cipi yml auto shop on

plan lists every change and every blocker. apply performs them as one transaction: if anything fails, nothing is left half done.

5. Apply on every deploy#

bash
sudo cipi yml auto shop on

From now on each successful deploy (CLI, webhook or panel) applies the file. Anyone who can push can now change this app's server settings, which is the point: protect the branch and review the file like code.

Why it's safe#

GuardEffect
Plan before applyYou see every change; blockers stop everything
Namespaced resourcesDatabases must be shop or shop_*, backup profiles shop or shop-*: a file can't touch another app
No secretsRequired variables are names; credentials are written to shared/, never to the repo
Allowlisted commandsdeploy.post and crons accept known runners only (artisan, php, composer, npm…)
Server picks the fileThe app's environment decides between cipi.yml and cipi-staging.yml; a commit can't redirect production

Questions

Can a commit break production?

The server plans every change first and applies all or nothing. An invalid file, an out-of-range value or a missing required variable blocks the plan and nothing changes.

Do secrets go in cipi.yml?

No. env.required lists variable names only; values stay in the server's .env. Basic-auth users are names or bcrypt hashes, never passwords.

Do I have to use it?

No. Every setting also works from the CLI or the panel. cipi yml generate writes a file from what an app already has, so adopting it later is one command.
