When a deploy runs out of time — slow builds, long migrations, npm on a small VPS

Find the step that makes a Laravel or Node deploy fail on time, decide whether it needs more time or a fix, and set per-app limits from the CLI, cipi.yml, the web panel or the API — with the previous release serving throughout.

By Andrea PollastriUpdated November 28, 20263 min read

Share

Every command of a deploy runs against a clock: a step that hangs — a migration waiting on a lock, an npm install stuck on a registry, a build that asks a question — can't hold the deploy and its lock for ever. When the clock runs out, the deploy fails like any other: the previous release keeps serving, and Cipi says which step it was.

Key ideas, in plain words#

TermMeaning
StepOne command of the deploy: clone, composer install, a migration, optimize, a task of yours
BuildThe front-end build (npm run build), the step that is long by nature
step_timeoutHow long any step may take: 300 seconds by default, up to 1800
build_timeoutHow long the build may take: 1800 seconds by default, up to 3600

1. Find the step#

sudo cipi deploy names it, right under the failure:

bash
sudo cipi deploy shop
…
[ERROR] Deploy failed (exit 1)
[WARN] The step artisan:migrate was stopped after 300 seconds, the most Deployer gives a command.

The log has a time on every line: the gap before the error is the step that took it.

bash
sudo cipi deploy shop --log=200
sudo cipi deploy shop --history          # how long the last deploys took

The panel shows the same in the app's Deploy tab and in each deploy's log. A deploy failed on time is also in the failure notification.

2. More time, or a fix?#

The slow stepUsuallyDo
A migration rewriting a large tableLegitimately longMore step_timeout, and consider a migration that doesn't lock
composer install on a slow disk or first deployLegitimately longMore step_timeout
npm ci / npm run build that passes some days and not othersClose to the limit; the server is the variableSee below before raising anything
A build that never endsIt waits for an answerCI=true in front of the script in package.json
A step that stops with KilledOut of memory, not out of timeMore RAM or swap; more time won't help

3. Give the app more time#

bash
sudo cipi app deploy-config shop                         # the current limits
sudo cipi app deploy-config shop --step-timeout=900      # 15 minutes for every step
sudo cipi app deploy-config shop --build-timeout=2700    # 45 minutes for the build

Or in the repository, so it travels with the code:

yaml
# cipi.yml
version: 1
deploy:
  step_timeout: 900
  build_timeout: 2700

From the web panel: the app → Deploy → Deploy pipeline, two fields with the minutes beside them. Over the API: PUT /api/apps/shop/deploy-config with step_timeout, build_timeout; cipi-cli deploy config set shop --step-timeout 900. The change counts from the next deploy. A value outside the range is refused, and nothing changes.

4. A build that passes some days and not others#

CauseCheckFix
The server swaps during the buildMemory and swap in the metrics; deploys are marked on the chartsMore RAM; or build in CI
A backup or another deploy at the same timeThe time of the failuresMove the nightly work, or deploy at another time
A slow registryThe install step is the long oneA lockfile in the repository; it still fits the 30 minutes
An interactive scriptThe log stops at a questionCI=true

5. Or don't build on the server#

A build that can't finish in an hour on the server is better done elsewhere: run npm run build in CI and commit the built assets to the branch Cipi deploys (or a release branch), and leave the front-end build off the app. The server then only pulls and links. See CI/CD workflows.

Troubleshooting#

ProblemFix
The panel stopped following a deployIt follows one for 2 hours; the deploy itself goes on. sudo cipi deploy shop --status
--build-timeout refused60 to 3600 seconds; --step-timeout 60 to 1800
The limit in cipi.yml is ignoredThe file is applied with its plan: sudo cipi yml plan shop shows whether it's pending, sudo cipi yml apply shop applies it (or turn on auto-apply). A value outside the range blocks the plan
The deploy is locked after the failureIt isn't: a timed-out deploy releases its lock. An interrupted one (reboot) does with sudo cipi deploy shop --unlock

Questions

Is the site down while a deploy fails?

No. The previous release keeps serving; the new one never goes live, and the lock is released.

What are the default limits?

5 minutes for each step (clone, Composer, a migration, optimize), 30 minutes for the front-end build — for a Node app, 30 for the install and 30 for the build.

What are the maximums?

1 hour for the build, 30 minutes for every other step. A deploy started from the panel, the API, cipi-cli or the SDK is followed for 2 hours in all.

Where do I set them?

sudo cipi app deploy-config, deploy.build_timeout and deploy.step_timeout in cipi.yml, the panel's Deploy pipeline, the API or the SDK.

Does a custom app have limits?

It deploys with a git pull, with no steps to time.
