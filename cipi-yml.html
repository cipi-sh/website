Configuration as code

cipi.yml: your server settings, in your repository

One file next to your code describes how the server runs the app. Change it in a pull request; Cipi shows the plan and applies it, all or nothing.

The whole app, in one file#

yaml
version: 1

app:
  php: "8.6"
  aliases: ["www.shop.example.com"]
  www: to-root
  ini: { upload_max_filesize: 50M }

workers:
  horizon: true
  reverb: true

schedule: true
search: true

health:
  url: "https://shop.example.com/up"
  rollback_on_unhealthy: true

deploy:
  predeploy_snapshot: true
  node_build: "npm ci && npm run build"
  post:
    - artisan scout:sync-index-settings

env: { required: [STRIPE_KEY, MAIL_HOST] }

backup:
  profiles:
    - { name: shop-nightly, scope: all, cron: "0 2 * * *", keep_days: 14, destinations: [s3], encrypt: true }
BlockWhat it controls
appPHP version, aliases, www/apex, php.ini values, resource limits, basic auth
workers, scheduleQueues, Horizon, Reverb, the scheduler
searchMeilisearch for Laravel Scout
healthURL probed every 5 minutes and after each deploy, with automatic rollback
deployBranch, releases kept, DB snapshot, asset build, post-deploy steps
databases, backupExtra databases and backup profiles for this app
redirects, proxies, crons, nodeRoutes, scheduled commands, Node apps

See the plan before anything changes#

cipi.yml
$ cipi yml plan shop
$ cipi yml apply shop
$ cipi yml auto shop on

plan lists each change and each blocker. apply performs them in one transaction. auto on applies the file after every successful deploy, from the CLI, the webhook or the panel.

Safe to accept from Git#

Anyone who can push controls the file, so it's designed to fail closed.

GuardEffect
Configure onlyIt can never create, rename or delete an app
NamespacedDatabases are shop or shop_*, backup profiles shop or shop-*: no reaching into other apps
No secretsRequired variables are names; generated credentials stay on the server
No shellOnly allowlisted runners (artisan, composer, npm, php…), no pipes or ;
Small YAMLAnchors, tags, merges and block scalars are refused
Strict routesProxies can't target Cipi's own ports, link-local or cloud-metadata addresses
Server picks the fileStaging reads cipi-staging.yml because the server says so, never because a commit asks

Validate before you push#

bash
composer require cipi/agent
php artisan cipi:yml validate          # same validator as the server
php artisan cipi:yml generate --write  # a first file inferred from your code
php artisan cipi:yml schema --write    # autocompletion in your editor

Add php artisan cipi:yml validate --json to CI and a broken file never reaches a server. AI assistants connected through the agent's MCP can validate drafts too.

Start in two minutes#

bash
sudo cipi yml generate shop --save      # the app as it is today
cat /home/shop/cipi.yml                 # commit it at the repository root
sudo cipi deploy shop && sudo cipi yml plan shop

Step by step: keep your server settings in the repository.

Questions

Is it like Docker Compose or Terraform?

Smaller and safer. It configures one app on a Cipi server (runtime, workers, domains, backups), can't create or delete apps, and refuses anything outside the app's own namespace.

What happens with an invalid file?

Nothing is applied. The plan reports the error; with auto-apply on you get a yml_fail notification and the deploy itself still succeeds.

Can I start using it on an existing app?

Yes. cipi yml generate <app> --save writes the current setup as a file; commit it and the next plan shows nothing to change.

Do secrets end up in Git?

No. env.required lists names only; credentials Cipi creates go to shared/, and basic-auth users are names or hashes.
