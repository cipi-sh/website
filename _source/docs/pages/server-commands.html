cipi — Server & Self-Update

Top-level commands for server status and Cipi self-management.

bash
cipi status              # CPU, RAM, disk, services, PHP versions, apps
cipi disk                # disk usage of the server and of every app (v5.5.0+)
cipi version             # show installed Cipi version
cipi self-update         # update Cipi to the latest version
cipi self-update --check # check for updates without installing

Password & credential reset

Cipi provides commands to regenerate server-level passwords. New passwords are stored in /etc/cipi/server.json (encrypted via Vault) and displayed on screen. Save them immediately. Since 5.8.2 cipi credentials prints the current ones again, in the installer's layout (root, MariaDB, PostgreSQL, Valkey, the Meilisearch master key, the backup encryption key, with connection URLs), and cipi credentials export writes them as a plain CSV (title,url,username,password,notes) that any password manager imports — to stdout, so nothing is left on the server: ssh cipi@<ip> sudo cipi credentials export > cipi.csv from your own machine (--output=FILE writes a mode-600 file instead). Every show or export is logged and raises the credentials_show notification trigger.

bash
cipi reset root-password              # regenerate the root Linux user SSH password
cipi reset db-password [--engine=…]   # regenerate root password (default or chosen engine)
cipi reset valkey-password           # regenerate the Valkey password and restart the service
cipi credentials                      # the install summary again: root, MariaDB, PostgreSQL, Valkey, Meilisearch, backup key
cipi credentials export [--output=…]  # CSV (title,url,username,password,notes) for any password manager
cipi reset valkey-password (alias cipi reset redis-password) restarts the Valkey service. Connected clients will be temporarily disconnected. If your apps use Valkey for cache or sessions, expect a brief interruption.

Self-Update

Cipi can update itself from GitHub without affecting any app, database, or configuration.

bash
cipi self-update --check   # check for a new version
cipi self-update           # update to latest

Update process

  1. Downloads the latest version from GitHub
  2. Backs up the current installation to /opt/cipi.bak.YYYYMMDDHHMMSS/
  3. Replaces CLI and lib scripts
  4. Runs any pending migration scripts in order (e.g. new Nginx directives, new packages)
  5. Updates the version file

Migration scripts live in lib/migrations/ and are named by version (e.g. 4.1.0.sh, 5.0.18.sh). When updating from v4.0.0 to v4.2.0, Cipi automatically runs 4.1.0.sh and 4.2.0.sh in order. Your apps, databases, and configurations are never touched.

Recent migrations improve reliability without changing app data: 5.0.6 — default IP whitelist file and regenerated API sudoers; 5.0.9 — cipi php switch in sudoers for PUT /api/php/default; 5.0.13 — reclaim API/GUI ownership after update; 5.0.14–5.0.17 — timed GitHub/Packagist panel package updates (no more hung cipi self-update on API/GUI Composer VCS clones); 5.0.18 — repair Panel GUI after symlink/open_basedir HTTP 500 (cipi gui fix-permissions). Run cipi self-update to reach 5.1.0.

Migration 5.1.0

The 5.1.0 migration is the largest of the 5.x line. On an existing server it:

  • installs the automatic-deploy wrapper and repoints each app's webhook cron at it;
  • backfills the CLI 99-cipi.ini and rewrites FPM pools so they inherit the server-wide file — see cipi ini;
  • converts the hardcoded nightly backup job into a default backup profile, carrying over its existing --weeks retention;
  • takes over the backup schedule with the managed crontab block;
  • claims the :443 default server when nothing else does.

Every step degrades to a warning and carries on. That matters: on an early 5.1.0 build a grep that matched nothing could fail the migration under set -o pipefail, and a failed migration makes cipi self-update refuse the release and retry it, failing again, every night.

Migrations 5.4.0 and 5.4.1

5.4.0 turns on the deploy audit ledger for existing apps: it installs cipi-deploy-audit, adds one sudoers rule per app (validated with visudo and restored if rejected), appends the audit hooks to each deploy.php without touching the rest of the file, switches the deploy-trigger cron from rm to mv, and writes the audit start marker.

It also moves servers off Node 20, which reached end of life in April 2026:

  • Fresh installs: setup.sh installs Node 22 from NodeSource.
  • Servers still on Node 20 (the NodeSource package, or cipi node default 20) are switched with cipi node default 22, which downloads and verifies the official build and links it into /usr/local/bin ahead of /usr/bin. The NodeSource package is not touched, so cipi node default system restores 20. Laravel asset builds, cipi app run npm and deploy.post use 22 from their next run.
  • Servers on another major, or with no Node at all, are left as they are.
  • A failed download leaves the server on 20, prints how to retry and lets the update carry on. A node_default notification is sent.

5.4.1 regenerates /etc/sudoers.d/cipi-api so the panel API can drive redirects, proxies and Node apps. Neither migration deploys, reloads or restarts anything.

Migration 5.5.0

The 5.5.0 migration moves Laravel apps from dated log files to one laravel.log — see log retention. It runs for every Laravel app; custom and Node apps are not touched:

  1. Rewrites /etc/logrotate.d/cipi-app-logs with the new storage/logs/*[!0-9].log pattern.
  2. In shared/.env, LOG_CHANNEL=daily becomes single, and so does a daily inside LOG_STACK. Any other channel (stack, stderr, slack, …) is left as it is. The rewrite runs as the app user and goes through a copy that replaces the .env in one rename, with the same owner and mode: the file is never truncated in place, so a write that fails (a full disk) leaves it exactly as it was. An .env the app user cannot rewrite is reported with a warning.
  3. Where the .env changed, so that no process keeps the old channel in memory:
    • artisan config:cache as the app user, if the current release has a cached config. Other .env edits that were waiting for a deploy become active with it.
    • SIGTERM to the app's running Supervisor programs (queue workers, Horizon, Octane, Reverb). They finish the job in hand and Supervisor starts them again; stopped programs stay stopped. Octane and Reverb drop their connections for the few seconds of the restart, as on a deploy.
    • One systemctl reload of PHP-FPM per PHP version in use by those apps.
  4. Folds the dated files into laravel.log, oldest first: laravel-<date>.log, .log.N, .log.N.gz and the empty stubs. It runs as the app user. A file is removed only after its content is in laravel.log; an existing laravel.log is appended to, never replaced; a file a process still has open, or an archive that cannot be read, is left where it is and named in the output.
Unlike the 5.4 migrations, this one restarts processes: running workers, Horizon, Octane and Reverb get a graceful SIGTERM, and PHP-FPM is reloaded. The nightly cipi self-update (03:50) will apply it unattended — if you would rather watch Octane and Reverb reconnect, run cipi self-update yourself first. The migration also needs free disk space for one uncompressed copy of an app's dated logs while it folds them; if that fails, the app's files are left as they were. A second run finds nothing to do.

Everything else in 5.5.0 needs no migration step: cipi disk, cipi firewall attempts, cipi ssh apps, the named Cloudflare accounts and the soft disk limits change nothing until they are used, and the tab-completion fixes arrive with the completion files self-update rewrites on every run.

Migration 5.5.1

From 5.5.1 Cipi writes the HTTPS server block of every vhost itself and certbot only issues and renews (wildcard domains). The migration brings existing servers in line:

  1. Writes the certbot deploy hook /etc/letsencrypt/renewal-hooks/deploy/cipi-reload-nginx (nginx -t -q && systemctl reload nginx), so nginx serves a renewed certificate whether certbot.timer or Cipi's weekly cron renewed it.
  2. Removes --nginx from the certbot renew line of root's crontab: on the command line it overrode how each certificate was issued, and would have renewed a DNS-01 wildcard over HTTP-01.
  3. Writes /etc/nginx/snippets/cipi-ssl.conf (TLS 1.2/1.3, Mozilla intermediate ciphers), included by every HTTPS block Cipi writes.
  4. Apps whose certificate renews over DNS-01 but are not recorded as DNS-01 — the install stopped at the old certbot install step — get ssl_dns_provider and ssl_dns_account; a certificate issued with --wildcard gets ssl_wildcard. The next cipi ssl install keeps DNS-01 and the wildcard.
  5. Rewrites, with the HTTPS block written by Cipi, the vhost of every app that has a certificate and a wildcard name, a Cloudflare Origin CA certificate, or no HTTPS in its vhost at all. One app at a time, with nginx -t after each: the previous file is kept in /var/lib/cipi/vhost-backup-5.5.1 and put back if nginx refuses the new one.

Other apps keep their certbot-written vhost until it is next regenerated (any alias, www, basic auth, redirect or proxy change), which switches it. No certificate is requested or renewed, and nothing is deployed. cipi ssl status then shows, per app, what it is served with and which of its names the certificate does not cover.

Migration 5.5.2

From 5.5.2 the panel API can run cipi disk. The migration regenerates /etc/sudoers.d/cipi-api so www-data may run cipi disk and cipi disk * (--json, db --json). Nothing else on the server changes, and nothing is deployed. cipi disk itself has existed since 5.5.0; until this sudoers line, GET /api/disk and GET /api/disk/dbs (API 1.33.0+, ability disk-view) answer 503. Setting a soft limit was already on the API in 1.32.0.

The same release also ships the cipi.yml fixes in the CLI itself: deploy.node_build, predeploy_snapshot, cipi yml generate --save, removal of backup profiles the file no longer lists, and a cipi.yml line on the deploy-success mail. Those arrive with the updated scripts and need no further migration step. See cipi.yml.

When the update itself fails

Up to 5.0.x, cipi self-update reported only “Download failed” — git's stderr was discarded, so the one message that explains what happened (no DNS, no outbound HTTPS, a missing branch, a full disk, an expired CA bundle) never reached anyone. Since v5.1.0 the real error is printed, the likely cause is named, and the command to reproduce it by hand is shown. The clone also runs under a 180-second timeout instead of being able to hang indefinitely, and a missing git is reported as such. An unattended nightly update now also sends the self_update notification, so it no longer lands without a word. Since v5.2.1 that mail is decided from a snapshot taken before /etc/cipi/version is rewritten, and is sent only when that snapshot differs from the downloaded version. A nightly refresh that stays on the same release is silent. 5.2.1 itself has no migration: self-update copies the libs and refreshes shell completion.

For example, the 4.5.5 migration retro-fits existing apps with the new ll='ls -al' shell alias: it appends the alias to each app's ~/.bashrc once (only when missing, preserving ownership), so apps created before 4.5.5 get it on the next cipi self-update.

Automatic maintenance crons

Cipi schedules several root-level jobs during installation. App-level crontabs (scheduler, deploy trigger) are separate — see User crontab.

Schedule Job
Daily 02:00 cipi backup run — S3 backups for all apps
Daily 03:00 cipi backup prune --weeks=4
Daily 03:30 cipi php upgrade — security patches for all installed PHP versions (wrapped by cipi-cron-notify; weekly on Sundays before 5.6.3)
Daily 03:50 cipi self-update (wrapped by cipi-cron-notify)
Sun 04:10 cipi ssl renew
Daily 04:15 Panel API maintenance (cipi-api-maintain — prune jobs/metrics)
Daily 04:30 cipi api update — soft-update panel Laravel + cipi/api

cipi completion

Since v5.2.0, tab-completion for bash and zsh is installed for you. setup.sh and every cipi self-update write it, and setup.sh also installs the bash-completion package. Nobody edits a dotfile — a new login shell simply has it.

bash
cipi app <TAB>               # create  list  show  edit  clone  limits  …
sudo cipi dep<TAB>           # → deploy
sudo cipi deploy sh<TAB>     # → shop  shop2 (your apps)
sudo cipi firewall <TAB>     # → allow  list  attempts
cipi help <TAB>              # help topics

# only needed for another user or a custom rc file
cipi completion bash
cipi completion zsh --print  # write the script to stdout, change nothing

The files written: /etc/bash_completion.d/cipi, /usr/share/zsh/vendor-completions/_cipi (when that directory exists), an /etc/profile.d/cipi-completion.sh loader for every interactive login shell, and — since v5.5.0 — a loader in the ~/.bashrc of root and the cipi user, the two who can run cipi (added once, existing content untouched, interactive shells only).

It completes the top-level verbs, each verb's sub-commands and flags, cipi help <topic>, and app names: from /etc/cipi/apps-public.json when the shell's user can read it (root or the cipi-api group), otherwise from the members of the cipi-apps group, which every user can list.

Where it did not work before 5.5.0

Completion has been installed since 5.2.0, but in three everyday situations <Tab> did nothing. v5.5.0 fixes all three:

  • sudo cipi … — how the cipi user runs every command. It relied on the sudo completion of the bash-completion package; without the package <Tab> offered file names. The script now brings its own for that case (_cipi_sudo_complete): it skips sudo's options, completes cipi as the command even though the binary is root-only, and hands the rest of the line to the cipi completion. With bash-completion loaded nothing changes.
  • Non-login shells — sudo -s, su, tmux, screen. The loader lived only in /etc/profile.d, which those shells do not read; the new ~/.bashrc loader covers them.
  • App names for the cipi user — they came only from /etc/cipi/apps-public.json, which the cipi user cannot read, so sudo cipi deploy <Tab> offered nothing. They now fall back to the cipi-apps group.

New servers get this from setup.sh; existing servers from their next cipi self-update, which rewrites the completion files on every run — no migration step, no package to install. A shell that is already open needs to be reopened. All of the above holds for bash; zsh loads the same completion from its vendor directory and /etc/profile.d.

The completion is hand-written, not framework-generated: tests/verify-5.2.0.sh fails if the verb list drifts from the dispatch table in cipi itself.
