Certbot issues and renews Let's Encrypt certificates; since v5.5.1 Cipi writes the HTTPS server block of the vhost itself (certbot never edits an app vhost), so every vhost change — alias, www, basic auth, redirects, Octane, Reverb, suspend — keeps HTTPS, wildcard certificates included. Certificates renew through certbot.timer and a weekly cron, each the way it was issued, and nginx reloads after every renewal. cipi ssl status lists the certificates with their expiry and, per app, what it is served with and which of its names the certificate does not cover.

bash
cipi ssl install myapp   # provision / renew — includes all aliases (SAN)
cipi ssl force myapp     # re-apply HTTP→HTTPS redirect (no new issuance)
cipi ssl renew            # force renewal of all certificates
cipi ssl status           # certificates + per app: served with, names not covered

# DNS-01 via Cloudflare (v5.0+) — wildcard certs
cipi ssl dns set --token=YOUR_CF_TOKEN               # Zone → DNS → Edit
cipi ssl install myapp --dns=cloudflare              # includes a '*.myapp.com' alias
cipi ssl install myapp --dns=cloudflare --wildcard   # adds myapp.com + *.myapp.com anyway
cipi ssl install myapp --dns=cloudflare --no-wildcard
cipi ssl install myapp --http                        # back from DNS-01 to HTTP-01 (v5.5.1+)

# Several Cloudflare accounts (v5.5.0+)
cipi ssl dns set --name=client-a --token=CLIENT_A_TOKEN
cipi ssl install shop --dns=cloudflare --wildcard --account=client-a
cipi ssl dns list [--json]      # accounts and the certificates that renew with each
cipi ssl dns remove client-a    # refused while a certificate still renews with it

Since v4.8.0, cipi ssl force <app> re-applies the HTTP → HTTPS redirect for an app that already has a Let's Encrypt certificate — without issuing a new one. cipi ssl install also sets force_https in apps.json automatically.

Since v5.0, optional DNS-01 challenges via Cloudflare replace the default HTTP-01 flow when you need wildcard certificates or cannot expose port 80. Configure once with cipi ssl dns set, then pass --dns=cloudflare (and optionally --wildcard) to cipi ssl install. Since v5.5.1:

  • An app whose certificate was issued over DNS-01 is reissued over DNS-01 by a plain cipi ssl install <app> (and by the panel API), with the same account and wildcard. Before, it fell back to HTTP-01, which replaced the certificate's names and dropped the wildcard. --http goes back to HTTP-01 on purpose.
  • The certificate names are primary + aliases (plus <apex> + *.<apex> with --wildcard), without the names a wildcard already covers: Let's Encrypt refuses *.example.com and www.example.com in the same order. --wildcard is remembered; --no-wildcard drops it, and --wildcard without --dns is an error.
  • A wildcard certificate does not route anything: when *.<apex> is not one of the app's names, the install says cipi alias add <app> '*.<apex>'.

Behind the Cloudflare proxy, use SSL/TLS mode Full (strict) — Flexible loops on Cipi's HTTPS redirect. Error codes, Origin CA and the setup without Cloudflare: Wildcard domains & SSL.

Domains in different Cloudflare accounts (v5.5.0+)

A DNS-01 certificate needs an API token of the Cloudflare account that holds its zone. Up to 5.4 the server kept one token, in one file: a server hosting the domains of clients with their own Cloudflare accounts could serve only one of them, and setting a second token overwrote the first — the certificates issued with it then stopped renewing. Since v5.5.0 every account has a name:

  • cipi ssl dns set --name=NAME --token=TOKEN adds an account, any number of them. Without --name it is the default account, in the same file as before (/etc/cipi/cloudflare.ini), so a server with one token changes nothing. Named accounts live next to it, one root-only file each in /etc/cipi/cloudflare/. Running it again on an existing name replaces the token — that is how a token is rotated.
  • cipi ssl install <app> --dns=cloudflare --account=NAME issues with that account. Without --account an app keeps the account its certificate was last issued with, else default. An account that is not configured is refused before certbot runs, with the list of the ones that are.
  • Renewals need nothing. certbot records the credentials file in each certificate's renewal config, so every certificate renews with the token of its own account.
  • cipi ssl dns list shows every account with the certificates that renew with it (--json too); tokens are never printed. cipi ssl status names the account next to each DNS-01 certificate.
  • cipi ssl dns remove <NAME> refuses while a certificate still renews with that account: without its token the certificate would fail to renew, silently, until it expired.

Account names are lowercase letters, digits, - and _. The credentials file is now written under a umask that keeps the token unreadable by other users even while it is being written — before 5.5.0 it was world-readable for an instant inside /etc/cipi. When issuance fails, the error says which account was used and that it must hold the zone.

Since v5.3.0, cipi ssl knows about Cloudflare Zero Trust. HTTP-01 refuses while cipi zt lock http is on — Let's Encrypt does not validate from Cloudflare's IPs — and on an app that uses a Cloudflare Origin CA certificate, which it would overwrite; use --dns=cloudflare instead. Apps routed through the tunnel get certbot's --no-redirect, and cipi ssl force refuses on them, because cloudflared talks plain HTTP to :80 and an origin redirect would break it.

After cipi alias add, run the command it prints — cipi ssl install for a new name, --dns=cloudflare for a wildcard — unless it says the name is already covered (a *.example.com certificate covers every new tenant subdomain). cipi ssl force turns the HTTP → HTTPS redirect back on without reissuing.
