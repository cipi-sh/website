Manage the authorized SSH keys for the cipi user — the admin SSH entry point. The cipi user (group cipi-ssh) uses public-key only; root login is disabled. App users (group cipi-apps) connect with password — see SSH as the app user. Since v5.5.0, cipi ssh apps can keep app users out of SSH and SFTP, one app or all of them.

Commands

bash
cipi ssh list                 # list all authorized keys with fingerprint, comment, and current-session marker
cipi ssh add [key]             # add a new SSH public key (validates format, prevents duplicates)
cipi ssh remove [n]            # remove a key by number
cipi ssh rename [n] [name]     # change the display name / comment of a key

# Structured output (v5.0.6+) — panel API
cipi ssh list --json

REST: GET|POST /api/ssh/keys, DELETE /api/ssh/keys/{n} (API 1.15.0+ / Cipi 5.0.6+).

Safety mechanisms

cipi ssh remove includes two safeguards to prevent lockout:

  • Current-session protection — you cannot remove the key used by your active SSH session.
  • Last-key protection — you cannot remove the last remaining authorized key.

Key comments

SSH keys are stored with their original comments intact, making it easy to identify who each key belongs to. Use cipi ssh rename to change the display name of any key:

bash
# list keys to find the number
cipi ssh list

# rename key #2
cipi ssh rename 2 "john-macbook"

Email notifications

When SMTP is configured, Cipi sends an email alert every time a key is added, removed, or renamed. The notification includes the server hostname, IP address, key fingerprint, key comment, timestamp, and remaining key count. Rename notifications also include the old and new key name.

cipi ssh apps — SSH/SFTP access of app users (v5.5.0+, the server's keys since v5.9.0)

Every app has its own Linux user. Since 5.9.0 the server's SSH keys — the ones of the cipi user, managed with the key commands above — open a shell as any app user: ssh shop@server, with the key you already use, whatever the app's own setting. sshd reads them at every login, so a key removed with cipi ssh remove stops working for the apps in the same moment. What an app accepts besides those keys — its password, over SSH and SFTP, and its own ~/.ssh/authorized_keys — is the switch below, for one app or for all of them:

bash
cipi ssh apps                     # every app user: enabled or disabled, and what new apps get
cipi ssh apps --json
cipi ssh apps disable shop        # from outside: the server's keys, nothing else
cipi ssh apps enable shop         # also its password (SSH, SFTP) and its own keys
cipi ssh apps sync                # rewrite Cipi's section of sshd_config (v5.9.0+)
cipi ssh apps disable --all       # every app user, and the apps created from now on
cipi ssh apps enable --all        # everyone back, whatever the single settings were
  • Disabled means: from another machine, the server's keys and nothing else — no password, no key of the app's own. (Before 5.9.0 it meant no login from outside at all.) Logins from the server itself stay as they were, because Deployer reaches the app user over ssh localhost: deploys, webhooks and rollbacks keep working. Sessions already open stay open until they close.
  • --all changes every app user, whatever the single settings were, and sets what apps created afterwards get (cipi app create, cipi sync import). After a disable --all, single users can still be enabled one by one.
  • How. The state is membership of the group cipi-nossh. One section of /etc/ssh/sshd_config, between # >>> cipi ssh apps and # <<< cipi ssh apps, holds three Match blocks: members of cipi-nossh from a non-local address get AuthenticationMethods publickey, AuthorizedKeysFile none and the server's keys through AuthorizedKeysCommand /usr/local/bin/cipi-ssh-keys (run as cipi); from localhost they log in as before; every other app user (cipi-apps) gets its password, its own keys and the server's. The section is written on a copy that sshd -t validates before it replaces the live file, followed by a reload, not a restart; a rejected copy changes nothing. The two blocks older versions wrote are folded into it; a block you added lines to is kept. After that, enabling or disabling a user is only a group change.
  • After a disable the command asks sshd itself (sshd -T -C) whether the rule applies to the user from outside and not from localhost, and warns if it does not.
  • The cipi user and root are refused by the command — the cipi user's access is managed with the key commands above.

Default: on a server installed with 5.9.0 or later new apps start disabled; a server that updates keeps the setting each app had, and gains the server's keys for all of them. Changes are logged and notified (trigger app_ssh_access). CLI only (root).
