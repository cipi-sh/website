Why not local?

Cipi is a production server provisioner. It is designed to turn a fresh Ubuntu VPS into a live, internet-facing Laravel host — not to run on your laptop, inside a local Docker container, or behind a home NAT.

This is explicit in the requirements and is not a bug or missing feature. Cipi needs a server that is:

  • Reachable from the public internet — with a routable public IPv4 address, not hidden behind NAT (home router, corporate firewall, or NAT-only cloud tiers)
  • Running on real hardware or full virtualization (KVM, VMware, Hyper-V, Xen HVM) — not on shared-kernel virtualization (OpenVZ, LXC) or desktop container runtimes that emulate a Linux VM on your machine. Since v5.5.0 the installer detects those and stops with the name of what it found
  • Accessible on ports 22, 80, and 443 — Let's Encrypt HTTP validation, Nginx vhosts, and SSH deploy workflows all assume inbound traffic can reach the host

Not compatible with local dockerization

Cipi is not compatible with local dockerized environments. Tools like Docker Desktop, OrbStack, Colima, and similar runtimes give you a Linux VM behind NAT on your Mac or Windows machine — no public IP, no inbound routing from the internet, and often a shared kernel under the hood. The Cipi installer may finish, but the result is not a production server:

  • SSL will not work — Certbot cannot complete Let's Encrypt validation when the host is not reachable on port 80 from the internet
  • Domains will not resolve — there is no public endpoint for DNS to point to
  • Deploy and webhook flows break — Git providers, CI runners, and external services cannot reach a NAT-ted local VM
Do not install Cipi inside Docker, OrbStack, WSL, or a local VM expecting a working production stack. Use a real VPS — even a €4/month instance is enough for development and staging.

Industry-standard constraint

No production server provisioner supports NAT-ted local environments. Commercial panels and open-source tools alike require a public, internet-accessible host — this is how SSL, domain routing, and remote deploy pipelines work. Cipi follows the same rule.

The difference is what Cipi does not ask for: no proprietary agent daemon, no dedicated outbound port to an external control panel, and no mandatory cloud account. Cipi runs entirely on your server — you SSH in and use the CLI. The public-internet requirement is about network topology, not about tying you to a SaaS vendor.

What to use locally instead

For local Laravel development, use Laravel Sail, Laravel Herd, or a plain composer install with php artisan serve. Provision a cheap VPS with Cipi when you need a real staging or production environment.

Why MariaDB?

MariaDB is the default database engine on every Cipi server (port 3306). Since v4.8.0 you can also install optional PostgreSQL (cipi db install pgsql, port 5432) and pick an engine per app or database — see cipi db and Why PostgreSQL?. MariaDB remains the right default for most Laravel apps: familiar MySQL-compatible SQL, strong out-of-the-box performance, and a license model that stays simple for self-hosted production.

Performance that matters in production

MariaDB is built for high-concurrency web workloads — exactly the pattern Laravel apps generate (many short queries, connection churn from PHP-FPM, mixed reads and writes).

  • Advanced query optimizer — better join planning and cost-based decisions than classic MySQL for typical application queries, which often means fewer full scans and lower latency under load.
  • Native thread pool — available in the community edition, so the server handles many concurrent connections more efficiently than a one-thread-per-connection model when PHP-FPM spikes.
  • InnoDB tuned for your VPS — Cipi sets innodb_buffer_pool_size from server RAM (256M on 1 GB hosts, up to 4 GB on 16 GB+ machines), so hot data stays in memory without starving Nginx or PHP.
  • Lean default for Laravel — most apps need a fast relational store, not exotic extensions. MariaDB delivers that with low operational overhead on a single Ubuntu box.

Fewer licensing headaches

Choosing MariaDB avoids the ambiguity that surrounds Oracle MySQL in commercial and redistribution scenarios — especially when you ship products, host client apps, or run infra for a company.

  • Pure GPL community server — MariaDB Server is GPL; there is no dual-license enterprise fork of the core engine that you must navigate just to stay compliant.
  • No Oracle MySQL CLA / dual-license maze — you are not depending on Oracle's MySQL product line, trademark policy, or commercial editions for features that “should” be free.
  • Predictable for SaaS and agencies — self-hosting MariaDB on your VPS keeps database licensing simple: you run open-source software on hardware you control, without MySQL Enterprise feature gates or surprise license reviews.
  • Aligned with Cipi's MIT philosophy — open stack, no vendor lock-in, no paid database SKU required for production performance features like the thread pool.

MySQL compatibility without the baggage

  • Drop-in for Laravel — use the mysql driver, the same DB_* env keys, and the same migration files. Eloquent, queues, and most packages just work.
  • Familiar tooling — TablePlus, DBeaver, Sequel Ace, and mariadb/mysql CLI clients connect the same way; Cipi still exposes a ready mariadb+ssh:// URL after install.
  • Native on Ubuntu — installs from MariaDB.org / Ubuntu packaging without inventing a custom database stack; Cipi wires users, backups, and vault credentials on top.
  • Battle-tested for the LAMP/LEMP world — decades of MySQL-compatible applications, docs, and hiring familiarity — with an engine that stays community-first.

Why PostgreSQL?

Since v4.8.0, PostgreSQL is a first-class optional engine on Cipi (port 5432). Install it with cipi db install pgsql, then create apps or databases with --engine=pgsql — see cipi db. Keep MariaDB as the default for classic Laravel MySQL workloads, or choose Postgres when you need richer SQL, stronger concurrency guarantees, or a stack that grows toward analytics and AI.

Functionality beyond “just tables”

  • Rich SQL and data types — JSON/JSONB, arrays, ranges, UUID, full-text search, and expressive constraints (CHECK, exclusion, deferred FKs) that map cleanly to complex domain models.
  • Powerful indexing — B-tree, GIN, GiST, BRIN, partial and expression indexes — so you can index JSON paths, search documents, or speed up time-series-style queries without a second datastore.
  • Extensions ecosystem — pgcrypto, uuid-ossp, pg_trgm, PostGIS, and many others turn Postgres into a platform, not only a SQL file.
  • First-class Laravel support — native pgsql driver, migrations, Eloquent, and a huge ecosystem of packages that assume Postgres features when you need them.

Scalability and concurrency

  • MVCC done right — readers do not block writers; long-running reports and busy write traffic coexist more gracefully than on lock-heavy setups.
  • Reliable under mixed load — strong consistency, transactional DDL in many cases, and a planner that holds up as schemas and query shapes get more sophisticated.
  • Room to grow on one VPS — then beyond — excellent vertical scale for a single-node Cipi server; when you outgrow the box, the same engine is what managed Postgres, replicas, and logical replication ecosystems are built around.
  • Operational clarity — mature monitoring views (pg_stat_*), explain plans, and tooling that senior teams already know how to tune.

Compatibility and portability

  • Industry standard — Postgres is the default answer for many SaaS backends, analytics pipelines, and cloud “managed database” offerings. Skills and runbooks transfer.
  • Standards-leaning SQL — closer to ANSI SQL than MySQL dialects, which reduces surprise when you share queries across tools, ORMs, and warehouses.
  • Works with the wider data stack — BI tools, ORMs, ETL, and CDC systems almost always speak Postgres; your Cipi-hosted DB is not a dead end.
  • Side-by-side with MariaDB on Cipi — both engines can run on the same server (3306 + 5432). Pick per app: WordPress-style or classic Laravel MySQL on MariaDB; product, multi-tenant, or JSON-heavy apps on Postgres.

Ready for AI and modern data workloads

  • Vectors and embeddings — with extensions such as pgvector, you can store embeddings next to relational data for semantic search, RAG, and recommendation features without bolting on a separate vector database on day one.
  • JSONB as a flexible document layer — keep structured columns for invariants and JSONB for evolving AI metadata, model outputs, or tool payloads — queryable and indexable.
  • Full-text + similarity building blocks — combine FTS, trigram similarity, and vectors for hybrid retrieval (keyword + semantic) inside one transactional system.
  • Analytics-friendly — window functions, CTEs, materialized views, and robust aggregation make Postgres a solid home for product metrics and feature stores before you need a warehouse.

When to choose PostgreSQL on Cipi

  • You need advanced constraints, JSONB, or Postgres-specific extensions
  • You care about concurrent writers, complex reporting, or stricter SQL semantics
  • You are building AI features (embeddings, hybrid search) or expect to
  • Your team or upstream packages already standardize on pgsql

MariaDB stays the zero-friction default. PostgreSQL is there when the product needs a more capable relational engine — still managed through the same cipi db workflow for create, list, backup, restore, and password rotation.

Why Valkey?

Cipi uses Valkey instead of Redis for several reasons:

  • Drop-in replacement — same RESP protocol on port 6379, same phpredis extension, same REDIS_* .env keys. Laravel doesn't notice the difference.
  • Truly open source — BSD-licensed fork stewarded by the Linux Foundation, created after Redis Inc. moved to the source-available SSPL / RSALv2 in 2024.
  • Native on Ubuntu — ships in Ubuntu 24.04's Universe repository (valkey-server + valkey-tools) without third-party PPAs.
  • No vendor lock-in — aligns with Cipi's MIT, self-hosted philosophy: free forever, backed by AWS, Google Cloud, Oracle, and a large community.
  • Auto-migrated — existing servers switch from Redis to Valkey automatically on cipi self-update, reusing the same password and dataset with zero app changes.

Why Laravel?

When v4 was designed, one of the clearest decisions was to drop generic PHP and WordPress support entirely and go all-in on a single framework. That framework was Laravel — and the reasoning goes well beyond personal preference.

Speed of development

Laravel gives developers an extraordinary head start. Authentication, queues, scheduled tasks, file storage, email, notifications, API resources, database migrations — all of it is built in, consistent, and documented. A team can go from an empty project to a production-ready application in a fraction of the time it would take with a lower-level stack. For Cipi, this means that every deployment assumption — directory layout, .env handling, queue workers, the scheduler — maps cleanly to a known structure. There is no guesswork.

A thriving open-source community

Laravel has one of the most active and welcoming communities in the PHP world. Packages are published, maintained, and discussed daily on GitHub, Laracasts, Discord, and X. When you hire a Laravel developer, you get someone who already knows the conventions, the tooling, and the ecosystem. When you publish a Laravel package, it reaches tens of thousands of developers overnight. That network effect is genuinely valuable — and it is one of the reasons Cipi's companion package, cipi-agent, works so well: drop it into a Laravel app and it just fits.

Security by default

Laravel takes security seriously out of the box. CSRF protection, SQL injection prevention through the query builder, XSS mitigation via Blade's auto-escaping, rate limiting, signed URLs, encrypted cookies — these are not add-ons you wire together, they are the defaults. The framework's release cycle includes prompt security patches, and the team publishes clear upgrade guides. For production applications that handle real users and real data, that reliability matters enormously.

Longevity and support

Every major Laravel version receives bug fixes for 18 months and security fixes for two years after release. LTS versions extend that further. Taylor Otwell and the core team have maintained a consistent, principled release cadence since 2011 — a track record that is rare and genuinely reassuring for long-term projects. When you deploy on Cipi, you are not betting on a framework that might be abandoned next year.

The Laravel ecosystem

Laravel does not stand alone. Around it has grown an ecosystem of first-party and community tools that are among the best in the industry:

  • Livewire — full-stack reactive components without leaving PHP
  • Filament — a stunning admin panel and form builder built on Livewire
  • Inertia.js — the bridge between Laravel and modern front-end frameworks (Vue, React, Svelte)
  • Laravel Horizon — a beautiful dashboard for monitoring Valkey/Redis queues; Cipi enables it with cipi worker horizon enable
  • Laravel Reverb — first-party WebSockets; Cipi wires Supervisor, Nginx /app proxy, and REVERB_* with cipi app reverb enable
  • Laravel Telescope — an elegant debug assistant for local and staging environments
  • Laravel Octane — supercharges application performance with FrankenPHP (and optionally Swoole / RoadRunner). Cipi runs Octane natively: cipi app create --octane or cipi app convert --to=octane
  • Pest — a delightful PHP testing framework with a Laravel-native plugin
  • Laracasts — the best screencasts in PHP, period

These tools do not just exist — they are actively developed, widely adopted, and genuinely fun to use. The Laravel world has a rare quality: it manages to be both opinionated enough to feel cohesive and flexible enough to stay out of your way when you need it to.

Ship or die

Taylor Otwell, the founder of Laravel, has a mantra that resonates far beyond the framework: "we must ship." It is a simple statement, but it encapsulates an entire philosophy — that code only has value when it reaches users, that perfectionism is the enemy of progress, and that the best developers are the ones who find ways to move forward even when the conditions are not ideal.

The broader tech world has its own, blunter version: ship or die. Build something real, put it in front of people, learn, and iterate — or watch it slowly become irrelevant in a drawer. Laravel's entire ecosystem is built around that spirit. The framework reduces friction, the community celebrates releases, and the tooling rewards velocity. Cipi exists for the same reason: to remove the server management friction that stands between a developer and a live, deployed application.

If you are reading these docs, you are probably a developer who wants to build things, not babysit infrastructure. That is exactly the kind of developer Cipi was made for.

Cipi is built for Laravel and with Laravel. The installer, the deploy pipeline, the agent package, the cron setup, the worker management — every decision was made with a Laravel app in mind. If you love the framework, you will feel right at home.

Why "ci-pi"?

Cipi is the Italian reading of the letters C and P — which stand for Control Panel. It is a quiet nod to the project's Italian roots and to the fact that, underneath all the CLI commands, Cipi is doing exactly what a control panel does: managing Nginx, PHP-FPM, MariaDB, Supervisor, Certbot, and UFW on your behalf — just without the browser tab.

The name also carries a deliberate lightness. Server management tools tend to take themselves very seriously. Cipi does not. It is a tool built by a developer for developers, with the goal of getting out of the way as quickly as possible.

The mascot

The Cipi mascot is a penguin — an intentional reference to Tux, the official Linux mascot created by Larry Ewing in 1996. Where Tux is polished and iconic, the Cipi penguin is drawn in a minimal, hand-sketched line style: same species, different attitude. Think of it as Tux's quieter sibling who prefers the terminal over the spotlight.

The illustration is rendered as a pure SVG using the project's accent color, so it adapts naturally to light and dark mode and scales to any size without losing quality.
