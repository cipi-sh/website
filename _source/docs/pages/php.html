cipi php

A new server is installed with PHP 8.6 since v5.9.1 (8.5 before, and for as long as the repository has no complete release of 8.6); a server that is already installed keeps the PHP it has. Additional versions can be added at any time; since v4.5.12 Cipi probes APT sources per Ubuntu codename. Since v5.6.3 the order is packages.sury.org first (24.04 and 26.04), then the ondrej/php PPA, then Ubuntu main as a last resort (co-installable 8.3–8.6 where the chosen repo supports it). Same maintainer and packages, but sury.org publishes first: on the 2026-10-21 security release it had the fixed builds for 24.04 while the PPA was still building them. Migration 5.6.3 moves existing servers off the PPA, removing it only once sury.org is in place.

Since v4.5.4 Cipi bundles Deployer 8 (since v5.10.0 pinned to 8.0.5 from its GitHub release and checked against its SHA-256 — see Deployer version), which requires PHP ≥ 8.3. cipi php install, cipi php switch, cipi app create and cipi app edit therefore accept only 8.3, 8.4, 8.5 and, since v5.9.1, 8.6. Legacy versions (7.4–8.2) remain detectable and removable, so you can still clean up a pre-4.5.4 server with cipi php remove <old-version>.

A server installed before v4.5.4 can still have PHP 7.4–8.2, with apps on them. Cipi manages what is there and adds nothing to it: cipi php list shows those versions (8.1 and older marked END OF LIFE), cipi service lists and restarts their FPM, and an app on one keeps it and keeps running. Since v5.9.1 cipi status lists their FPM too, and a server-wide cipi ini set reaches them. What no longer works on a legacy version: installing it, giving it to an app, making it the server's PHP, and — on a server with Deployer 8 — deploying an app that is still on it. Move the app first with cipi app edit <app> --php=8.5. The panel and the API follow the same rule: a legacy version is listed and marked, and never offered to an app (GUI after 4.2.1, API 1.39.2).

bash
cipi php list              # installed versions, status, patch version, security state, system default
cipi php install 8.4       # install an additional PHP version (8.3–8.6)
cipi php switch 8.4        # set system default (root/cipi, API pool)
cipi php remove 8.1        # remove a version, incl. legacy (blocks if default or apps use it)
cipi php upgrade           # apply security patches, then report the patch level (exit 1 while vulnerable)

PHP 8.6 (v5.9.1+)

A new server is installed with PHP 8.6. It is the server's PHP — the php command, the panel's pools — and what cipi app create uses when no --php is given. The installer does that when the repository has a release of 8.6 with every extension Cipi installs. While it only has a release candidate, or no redis, memcached or imagick package for 8.6 yet, the server gets 8.5 as before and the installer's last screen says why. That was still the case on the afternoon of 19 November 2026, the day PHP 8.6.0 was released: packages.sury.org had 8.6.0 itself and none of those three, so a server installed then got 8.5. The installer looks again at every install; nothing has to be updated for it to choose 8.6. On a server that got 8.5, cipi php install 8.6 and then cipi php switch 8.6 move it later.

A server that is already installed keeps the PHP it has. Updating to 5.9.1 does not install 8.6, does not move an app to it and does not change the server's PHP. There 8.6 is a version you add: cipi php install 8.6 installs it next to the ones already there, and cipi php switch, cipi app create --php=8.6, cipi app edit <app> --php=8.6 and php: "8.6" in cipi.yml accept it. Installing it does not make it the default: cipi app create without --php keeps using the server's PHP until cipi php switch 8.6. When you install it while the branch is new, three things are worth knowing:

  • You get what the repository has that day. PHP 8.6.0 was released on 19 November 2026 and packages.sury.org had it within hours; the Launchpad PPA, which servers set up before 5.6.3 may still use, carried a release candidate that afternoon. Where the repository only has a release candidate Cipi installs it and calls it what it is: cipi php list, cipi php upgrade and cipi pending show prerelease instead of comparing it with a security release. The nightly cipi php upgrade moves it to 8.6.0 when the repository has it.
  • Extensions that are not packaged yet come later, by themselves. PHP's own packages are published first; redis, memcached and imagick are separate projects and follow. Before 5.9.1 the install failed on the first missing package. Now it stops only if PHP itself (fpm, cli, common) is missing; otherwise it installs the version without the extensions apt does not have, names them, and keeps the list in /var/lib/cipi/php-ext-pending. The nightly cipi php upgrade installs each one as soon as it is published and restarts that version's FPM; cipi pending lists them until then. Mind what a missing one means: Laravel's default Redis client is the redis extension, so an app that uses Redis for cache, sessions or queues does not work on a PHP without it. For that reason cipi app create, cipi app edit --php, cipi app clone and php: in cipi.yml refuse a version that is still waiting for extensions and name what is missing. An app that uses none of them goes on with --force (cipi app edit <app> --php=8.6 --force); a Node app is not asked, its PHP only runs Deployer and the webhook receiver. From the panel the job fails with the same message: --force is given on the command line only.
  • An app's composer.lock may need a refresh first. Every Laravel app depends on nette/schema and nette/utils (through league/commonmark), and their releases before 20 October 2026 declare PHP up to 8.5: composer install refuses such a lock on 8.6 and the deploy fails, leaving the release that was live in place. Run composer update nette/schema nette/utils in the project (1.3.7+ and 4.1.6+), commit the lock, then switch the app.

The panel needs cipi/api 1.39.2 to install 8.6 or assign it to an app; on a server older than 5.9.1 it answers 422 with the version it needs.

Security patch upgrades

Since v4.7.13, PHP packages are excluded from unattended-upgrades and managed by Cipi instead. cipi php upgrade runs apt-get update and --only-upgrade on every installed php* and libphp* package, then restarts the affected PHP-FPM pools. When SMTP is configured and packages were upgraded, Cipi sends an email (php_upgrade trigger; disable with cipi notifications disable php_upgrade).

The check runs automatically every day at 03:30 via root crontab (wrapped by cipi-cron-notify). Log: /var/log/cipi/php-upgrade.log. With nothing to upgrade, a run costs one apt-get update and restarts nothing. Migration 4.7.13 added it as a weekly job (Sunday 03:30); since v5.6.3 it is daily, and existing servers move to the daily schedule on cipi self-update (migration 5.6.3). A schedule changed by hand is left as it is.

Patch level report (v5.6.3+)

After upgrading, cipi php upgrade prints one line per installed PHP version, compared with the oldest release that carries every security fix Cipi knows about. Since v5.9.1 that is 8.5.13, 8.4.28, 8.3.37 and 8.2.36 — the PHP security release of 2026-11-19 — and 8.6.0, released the same day with the same fixes. Up to v5.9.0 it was 8.5.12, 8.4.27, 8.3.36 and 8.2.35 (the release of 2026-10-21); a server on those is reported vulnerable from v5.9.1 on:

  • patched — at or past that release.
  • VULNERABLE — the fix exists but this server does not have it, typically because the repository has not published it yet. Run cipi php upgrade again later.
  • distro — a build from the Ubuntu archive, which backports fixes without changing the version number; check apt changelog php8.3-fpm.
  • END OF LIFE — PHP 8.1 and older get no fixes from the PHP project any more. Cipi installs 8.3 and later only, so this affects servers set up before 4.5.4; move their apps with cipi app edit <app> --php=8.5. PHP 8.2 security support ends on 2026-12-31, and the report says so.
  • prerelease (v5.9.1+) — a release candidate, beta or alpha: what the repository carries for a branch that is not released yet (see PHP 8.6). It is not compared with a security release.

The release of 2026-11-19. It fixes, among others, request smuggling in PHP-FPM (CVE-2026-129289), a use-after-free in the PHP-FPM master (CVE-2026-129291), two ways to code execution through session files (CVE-2026-126714, CVE-2026-115560), a use-after-free of the timezone cache (CVE-2026-129496) and, on 8.5 and later, one in fatal-error backtraces (CVE-2026-129474). Migration 5.9.1 runs cipi php upgrade, which installs the fixed packages and restarts PHP-FPM. Where a Cipi server stood before that: its vhosts never set fastcgi_keep_conn, which the request smuggling needs (check a vhost written by hand with nginx -T | grep fastcgi_keep_conn); upload progress and fatal_error_backtraces are off in every pool since v5.6.3 and in Octane apps since v5.7.1, which closes CVE-2026-115560, CVE-2026-129474 and the upload path of CVE-2026-126714; the PHP-FPM master issue needs catch_workers_output, set only in the panel's own pools, and code already running as their user. The timezone one has no setting that closes it: it needs the update. An Octane app runs the PHP built into its FrankenPHP binary, which apt does not touch: cipi php upgrade lists it as vulnerable until the app has a FrankenPHP build on a fixed PHP.

While a version is VULNERABLE the command exits 1, so the nightly cron mails a failure through cipi-cron-notify until the fix is in.

Octane apps are checked too. FrankenPHP runs on the PHP built into its binary, and apt never updates that binary. cipi php upgrade lists, per Octane app, the FrankenPHP build it is pinned to (v5.10.0+), the PHP inside it, and flags any build on a PHP older than the fixed release. To fix one:

bash
cipi frankenphp upgrade <app>     # or --all: newest build on the app's PHP minor, restarted and checked

Up to 5.9.x the advice here was php artisan octane:install --server=frankenphp and a restart — which does nothing when a binary is already there: octane:install keeps it.

cipi php list shows the same patch version and security state for each version; cipi php list --json adds patch, security (patched, vulnerable, distro, eol, prerelease since 5.9.1, or unknown) and security_floor to every entry.

FPM pool hardening (v5.6.3+)

Every PHP-FPM pool Cipi writes — app pools, Node webhook pools, and the panel API and GUI pools — turns off the two confirmed attack paths of CVE-2026-109619 (PHP security advisory of 2026-10-21, with CVE-2026-109618: unauthenticated remote code execution in every SAPI that serves web requests):

ini
php_admin_flag[session.upload_progress.enabled] = off
php_admin_flag[fatal_error_backtraces] = off   ; PHP 8.5 only — the setting does not exist earlier

They are set as php_admin_flag, so they apply before the request is parsed and .user.ini or ini_set() cannot turn them back on. The PHP project says only the patch release is a complete fix; the flags narrow the attack until it is installed. Migration 5.6.3 renders the app and Node webhook pools again, edits the cipi-api and cipi-gui pools in place, keeps the previous pools in /var/lib/cipi/fpm-pool-backup-5.6.3/ (a version whose new pools fail php-fpm -t gets the old ones back), runs cipi php upgrade and restarts every PHP-FPM service — a restart, not a reload, because a stale worker is what CVE-2026-109619 exploits.

Octane (FrankenPHP) hardening (v5.7.1+)

FrankenPHP runs the PHP built into its own binary and never reads an FPM pool. Every Octane app therefore loads the same two settings from /etc/php/cipi-octane.d/99-cipi-hardening.ini: its <app>-octane Supervisor program sets PHP_INI_SCAN_DIR=":/etc/php/cipi-octane.d". The leading : keeps PHP's compiled-in scan directory, so the php that starts Octane still loads its conf.d, and Octane passes the variable on to FrankenPHP.

ini
session.upload_progress.enabled = 0
fatal_error_backtraces = 0   ; ignored by PHP below 8.5

The settings load at startup, so ini_set() cannot turn upload progress back on. This also covers the PHP advisory of 2026-10-23 (CVE-2026-115560, no fixed release yet), whose only mitigation is session.upload_progress.enabled=0. Migration 5.7.1 writes the file, renders every Octane program again (previous files in /var/lib/cipi/supervisor-backup-5.7.1/, put back if Supervisor refuses the new ones) and restarts the running ones.

Optional, not a default: the advisory also suggests a lower body limit and an unlimited memory limit for servers that cannot update. Neither is applied by Cipi — a 32M body limit would break uploads that work today, and an unlimited memory limit trades this bug for runaway workers. Both are available through cipi ini set, server-wide or per app with --app=<app>:

bash
# lower body limit: upload_max_filesize first, then post_max_size
cipi ini set upload_max_filesize=30M [--app=<app>]
cipi ini set post_max_size=32M [--app=<app>]

# unlimited memory_limit — only with a systemd MemoryMax= cap on the phpX.Y-fpm service
cipi ini set memory_limit=-1 [--app=<app>]

Cap the service with a systemd MemoryMax= on phpX.Y-fpm (for example systemctl edit php8.5-fpm). Do not use RLIMIT_AS or RLIMIT_DATA for this: the advisory warns that they can trigger the allocation failure behind the bug.

PHP is not the only package Cipi keeps out of unattended-upgrades. Since v5.2.3, nginx, MariaDB, PostgreSQL and Valkey have their own operator-triggered equivalent — see manual stack upgrades. Unlike PHP, those are never scheduled.

System default vs app-specific PHP

The system default is the PHP version used by the root and cipi users, the Cipi API FPM pool, and the API queue worker. Use cipi php switch <ver> to change it. The command migrates the API pool (and the GUI FPM pool when installed), recreates panel sockets, and restarts the API worker. Since 5.0.9+, PUT /api/php/default wraps this via the panel API (php-manage ability). Since 5.0.10–5.0.12, switch tolerates partial update-alternatives success, remounts read-only roots when needed, and keeps API/GUI FPM pools on the target version to avoid nginx 502.

REST: GET /api/php, POST /api/php/install, DELETE /api/php/{version}, PUT /api/php/default (API 1.15.0+ / Cipi 5.0.6+). CLI JSON: cipi php list --json (since 5.0.6).

Each app has its own PHP version (set at app create or via cipi app edit --php=). Deployer, Composer, crontab deploy triggers, and cipi sync import always run with the app's configured PHP — never the system default.

To switch an existing app to a different version:

bash
cipi app edit myapp --php=8.5

This hot-swaps the PHP version with zero downtime: updates the FPM pool, Nginx socket, Supervisor workers, crontab, Deployer config, and .env in one atomic operation.

cipi ini

Available since v5.1.0. A guided way to change PHP settings without hunting for the right php.ini. Every server-wide change reaches both SAPIs — PHP-FPM and CLI — so what your web requests see is also what queue workers, artisan and cron see.

bash
cipi ini list                                # effective values and which layer set them
cipi ini list --app=shop                     # as seen by one app
cipi ini get memory_limit                    # one setting
cipi ini set upload_max_filesize=50M         # server-wide (FPM + CLI)
cipi ini set memory_limit=512M --app=shop    # for one app only
cipi ini unset memory_limit --app=shop       # fall back to the wider value
cipi ini reset [--app=shop]                  # back to Cipi defaults
cipi ini keys                                # what can be set, and what cannot

A 5.1.3 hotfix stopped cipi ini list from dying on the first setting after printing the table header (_INI_SOURCE: unbound variable). No migration: cipi self-update copies the new lib/ini.sh.

What it does for you

  • It raises the settings that would silently cap yours. Setting upload_max_filesize also raises post_max_size and memory_limit when they would otherwise limit it, and Nginx's client_max_body_size is flagged when it would.
  • It refuses what should not be set this way. Settable keys are an explicit whitelist — see cipi ini keys. open_basedir, auto_prepend_file, extension and friends are refused by name, with the reason, because Cipi manages them as part of app isolation. The two keys of the 2026-10-21 PHP advisory, session.upload_progress.enabled and fatal_error_backtraces, are listed there too (5.7.2+): off in every pool since 5.6.3, in each version's fpm/conf.d/99-cipi.ini since 5.7.2.
  • Per-app overrides win. --app=<app> writes into that app's FPM pool, which outranks the server-wide file — for that app only.

Why this needed fixing

Before 5.1.0 every FPM pool hardcoded upload_max_filesize, post_max_size and max_execution_time, and pool values outrank conf.d — so a server-wide php.ini change could not reach a single app. On top of that, Cipi wrote 99-cipi.ini for FPM only, leaving the CLI SAPI (queue workers, artisan, cron) on the PHP package defaults.

In 5.1.0 pools carry only what is genuinely per-app (open_basedir, the error log, explicit overrides) and inherit everything else; both SAPIs get their file; and migration 5.1.0 backfills the CLI 99-cipi.ini and rewrites existing pools on update.

Each change fires the ini_set notification trigger, so a PHP setting never changes on a shared server without a trace. An app can also carry its PHP version and per-app settings in its repository — see cipi.yml.
