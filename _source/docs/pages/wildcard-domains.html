Yes, Cipi does wildcards — one app answering on every <tenant>.myapp.com, with one certificate that covers all of them. It takes two separate things, and most problems come from having only one of them:

  • Routing — Nginx sends *.myapp.com to the app when the pattern is one of its names: cipi alias add myapp '*.myapp.com' (or a wildcard primary domain). Works since v5.1.0, whatever DNS or certificate you use.
  • Certificate — Let's Encrypt validates a wildcard name over DNS-01 only: it asks for a TXT record in the zone. Cipi creates that record through the Cloudflare API, the only DNS provider it automates: cipi ssl install myapp --dns=cloudflare. HTTP-01 (the default, through port 80) can never issue a wildcard.

Since v5.5.1 Cipi writes the HTTPS server block of the vhost itself; certbot only issues and renews the certificate. Before that, a wildcard certificate was issued and then failed to install (Which server blocks would you like to modify? — certbot's nginx installer cannot be driven non-interactively for a wildcard name), and the next vhost change dropped HTTPS without a word. If that happened to you, cipi self-update: the 5.5.1 migration installs the certificate that is already on disk.

With Cloudflare — step by step

  1. DNS records in the Cloudflare dashboard: A @ → <server-ip> and A * → <server-ip> (AAAA too if the server has IPv6). The * record also covers www, app, admin… unless a record with that exact name exists. Proxied or DNS only: both work, wildcard records can be proxied on every plan.
  2. API token — Cloudflare → My Profile → API Tokens → Create Token → template Edit zone DNS, Zone Resources: Include → Specific zone → myapp.com. The only permission needed is Zone → DNS → Edit.
  3. Give it to Cipi, once per server (several accounts: --name=).
  4. Route the subdomains to the app with a wildcard alias. Quote it, so the shell does not expand the *.
  5. Issue the certificate over DNS-01. Cipi asks for myapp.com + *.myapp.com + any other alias the wildcard does not cover, writes the HTTPS vhost and redirects every subdomain from HTTP to HTTPS. It takes about a minute (Cipi waits 30 seconds for the TXT record to propagate).
  6. Proxied records only: Cloudflare → SSL/TLS → Overview → Full (strict). Also check Rules → Configuration Rules / Page Rules: a rule that sets SSL to Flexible for a hostname wins over the global setting.
  7. Check — cipi ssl status lists every app with the certificate it is served with and the names that certificate does not cover.
bash
cipi ssl dns set --token=YOUR_CLOUDFLARE_TOKEN          # step 3
cipi alias add myapp '*.myapp.com'                        # step 4
cipi ssl install myapp --dns=cloudflare                 # step 5
cipi ssl status                                          # step 7
curl -sI https://tenant1.myapp.com | head -1             # HTTP/2 200 (or your app's answer)

Renewals need nothing: each certificate renews the way it was issued (certbot.timer twice a day, plus Cipi's weekly cron), with the Cloudflare token it was issued with, and nginx reloads after every renewal. A certificate issued over DNS-01 is always reissued over DNS-01 — cipi ssl install myapp without flags keeps it (--http goes back to HTTP-01 on purpose).

--wildcard adds myapp.com + *.myapp.com to the certificate even when the app does not serve *.myapp.com — useful to cover many explicit aliases with one name. It does not route anything: subdomains reach the app only through the wildcard alias. The flag is remembered for later reissues; --no-wildcard drops it.

Cloudflare proxy: the SSL/TLS mode decides everything

With the orange cloud, the visitor talks HTTPS to Cloudflare, and Cloudflare opens a second connection to your server. The SSL/TLS mode says how:

  • Flexible — never with Cipi. Cloudflare connects to http:// on port 80. As soon as the app has a certificate, Cipi answers port 80 with a redirect to HTTPS, which Cloudflare fetches again over HTTP: an endless loop (ERR_TOO_MANY_REDIRECTS). Without a certificate it "works", but Laravel sees plain HTTP and builds http:// URLs.
  • Full — Cloudflare connects over HTTPS and accepts any certificate. Works, but does not protect the second hop.
  • Full (strict) — HTTPS with a valid certificate for the hostname: the Let's Encrypt certificate from Cipi, or a Cloudflare Origin CA one. The right setting.

Order for a new site behind the proxy: issue the certificate first with --dns=cloudflare (DNS-01 does not care about the proxy, the firewall or port 80), then switch to Full (strict). HTTP-01 behind the proxy depends on Cloudflare settings (Always Use HTTPS, WAF rules, Under Attack mode, cipi zt lock http) — you do not need to turn the proxy off and on again if you use DNS-01. The edge certificate Cloudflare shows to visitors (Universal SSL, free) covers myapp.com and *.myapp.com: one level of subdomains. Deeper names (a.b.myapp.com) need Cloudflare's Advanced Certificate Manager at the edge, and their own wildcard at the origin.

Alternative behind the proxy: Cloudflare Origin CA

A certificate signed by Cloudflare, valid 15 years, trusted only by Cloudflare: fine for proxied records with Full (strict), a browser warning for a DNS-only record. It covers the app's names, wildcard alias included. It needs the cipi zt API token (Zone → SSL and Certificates → Edit), not the DNS-01 one. Since 5.5.1 it works on an app that never had HTTPS, and survives every vhost change.

bash
cipi zt token set --token=ZT_TOKEN --account=ACCOUNT_ID
cipi alias add myapp '*.myapp.com'
cipi zt origin-cert myapp       # reissue after adding names

Without Cloudflare

When the zone is hosted elsewhere, Cipi cannot create the TXT record, so it cannot issue a wildcard certificate. Routing still works (cipi alias add myapp '*.myapp.com' plus a * record at your provider), but HTTPS needs one of these:

  1. Move the DNS to Cloudflare (recommended) — free plan, records set to DNS only: traffic does not change, only who answers DNS. Then follow the Cloudflare steps and skip the SSL/TLS mode.
  2. List the subdomains — when tenants are few and known, add each one as an alias (no wildcard) and let HTTP-01 issue one certificate for all of them: cipi alias add myapp acme.myapp.com, then cipi ssl install myapp. Every name needs its own DNS record (or the * record), port 80 must be reachable, a certificate holds at most 100 names, and every reissue counts toward Let's Encrypt's limit of 50 certificates per domain per week — not a fit for self-service signup.
  3. Bring your own certificate — issue it with the certbot DNS plugin of your provider (Route 53, DigitalOcean, OVH, Gandi, …) under the certificate name Cipi expects: the app's primary domain (without *. for a wildcard primary). Cipi finds it in /etc/letsencrypt/live/<name>/ and serves it; certbot renews it with your plugin and Cipi's hook reloads nginx. Do not run cipi ssl install on that app afterwards: without --dns=cloudflare it reissues over HTTP-01, without the wildcard.
bash
# option 3, example with Route 53 (credentials as the plugin documents them)
apt install python3-certbot-dns-route53
certbot certonly --dns-route53 -d myapp.com -d '*.myapp.com' --cert-name myapp.com
cipi alias add myapp '*.myapp.com'      # rewrites the vhost with the certificate
cipi ssl force myapp                    # or this, if the alias was already there

Multi-tenant apps: good to know

  • Other apps still win on their exact names. With *.myapp.com on one app, api.myapp.com can still be a separate app: Nginx prefers an exact server_name to a wildcard.
  • Unknown hosts are closed by cipi nginx default-server (on by default) instead of reaching your tenant resolver.
  • Laravel: set SESSION_DOMAIN=.myapp.com only if a login must be shared across subdomains; resolve the tenant from the Host header. APP_URL is set to https://www.myapp.com for a wildcard primary.
  • Depth: Nginx's *.myapp.com also matches a.b.myapp.com, certificates do not — keep tenants one label deep.
  • One app per tenant is the alternative when tenants need isolation (own database, own backups, movable to another server): create each tenant as its own Cipi app with its exact domain through the Cipi API, and its DNS record through the Cloudflare API — every tenant then gets a plain HTTP-01 certificate.
