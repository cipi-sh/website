Since Cipi 5.8.2 and cipi/gui 4.0.2 the panel can sign people in through your identity provider over OpenID Connect: Microsoft Entra ID, Google Workspace, Okta, Keycloak, Authentik — anything that publishes a discovery document (/.well-known/openid-configuration). SAML is not supported. SSO is opt-in and configured from the server, because the panel's .env is Cipi's file to write; the same place is the break-glass when a provider is misconfigured.

1. Register the panel at your identity provider

Create an OIDC client (a “web application”) and give it the panel's callback as the redirect URI: https://<panel-domain>/auth/sso/callback. You will get back a client id and a client secret; note the issuer URL too.

  • Microsoft Entra ID — Entra admin center → App registrations → New registration: single-tenant, platform Web, redirect URI as above. Then Certificates & secrets → New client secret. The issuer is tenant-specific: https://login.microsoftonline.com/<tenant-id>/v2.0 (the Directory (tenant) ID from the Overview page, never common or organizations: the panel compares the issuer of every token with the one you configured). Users need a mail address on their account; the email claim is read from the userinfo endpoint.
  • Google Workspace — Google Cloud console → APIs & Services → Credentials → OAuth client ID, type Web application, authorised redirect URI as above. Issuer: https://accounts.google.com. Restrict who can sign in with --domains.
  • Okta, Keycloak, Authentik, Zitadel, Auth0 — a standard OIDC web client with the authorization-code flow (PKCE is used, a client secret is still required). The issuer is the realm or application URL whose /.well-known/openid-configuration answers.

2. Turn it on from the server

bash
cipi gui sso set --issuer=https://login.microsoftonline.com/<tenant-id>/v2.0 \
    --client-id=<application-id> --client-secret=<secret>      # Entra ID; the secret is asked when omitted
cipi gui sso set --issuer=https://accounts.google.com --client-id=… --client-secret=… --domains=example.com
cipi gui sso status                 # issuer, label, Redirect URI, who can get in, SSO-only or not
cipi gui sso only on                # password sign-in off for everyone — the SSO button only
cipi gui sso only off               # break-glass: passwords accepted again
cipi gui sso disable                # back to password sign-in; accounts and their links are kept

set writes the settings to the panel's .env, clears the config cache, runs the pending migration and prints the Redirect URI to check against the one registered at the provider. The login page gets a Sign in with … button, labelled after the issuer (“Microsoft Entra ID”, “Google”, “Okta”, else “SSO”; --label= to change it). Flags:

FlagWhat it does
--issuer=<url>The OIDC issuer; its discovery document is fetched and cached for an hour. Required, https:// only.
--client-id=<id>The client (application) id from the provider. Required.
--client-secret=<secret>The client secret. Asked on the terminal when omitted; kept when you re-run set to change another flag.
--label=<text>The button text instead of the one derived from the issuer.
--domains=<a.com,b.com>Email domains whose people get an account on their first sign-in: role user, no access until an admin grants servers or apps in Team. Without it only existing accounts can sign in.
--onlyPassword sign-in off for everyone, the same as cipi gui sso only on.
--scopes=<list>Instead of openid email profile; openid is always sent.

3. Who gets in, and how

  • Existing accounts — seeded by cipi gui, created from an invite link — are matched by their email (case-insensitive) and linked to the provider's identity (users.sso_subject) on the first sign-in; from then on the link wins, so a renamed mailbox still lands on the same account. An email already linked to a different identity is refused (“linked to another identity”).
  • New people get an account only when their email domain is in --domains; everyone else sees “No panel account for … Ask an admin for an invite link.” Nothing is created for a refused sign-in.
  • Roles and grants are the panel's, as before: an auto-created account is a user with nothing granted; admins hand out servers and apps in Team, where SSO-linked accounts carry an SSO badge.
  • MFA: the identity provider is the authority — the panel's own TOTP step is skipped after an SSO sign-in. Password sign-ins keep their TOTP as before.
  • Under the hood: authorization-code flow with PKCE (S256), state and nonce; the code is exchanged server-to-server with the client secret; the identity comes from the provider's userinfo endpoint, and the ID token's issuer, audience and nonce are checked against the handshake. An email_verified: false claim is refused; a provider that does not send the claim (Entra ID) is accepted.
  • Where it shows: Settings → Panel has a read-only Single sign-on card for admins (status, provider, SSO-only, auto-provisioned domains, the redirect URI to copy, and the CLI to change it); the panel's own .env keys are CIPI_GUI_SSO_ISSUER, _CLIENT_ID, _CLIENT_SECRET, _LABEL, _DOMAINS, _ONLY, _SCOPES.

4. Changing provider, locking yourself out, and other troubles

  • A new issuer or client id (another tenant, a new app registration) makes set forget every link: an identity's sub is per provider, and Entra ID's is per app registration. Everyone links again at the next sign-in by email; nothing else changes.
  • SSO-only and a broken provider: from the server, cipi gui sso only off brings password sign-in back, cipi gui sso disable turns SSO off altogether, cipi gui reset-user resets the admin account. Nothing in the panel can bypass SSO-only, by design.
  • “redirect_uri mismatch” from the provider: the URI registered there differs from the one cipi gui sso status prints (scheme, host, trailing path). After cipi gui move register the new one.
  • “issuer mismatch”: Entra ID configured with common or organizations instead of the tenant id, or an issuer with a trailing path the provider does not put in its tokens — use the exact issuer value from the discovery document.
  • “no email claim”: the account has no mail address, or the client was not granted the email scope (Entra: API permissions → Microsoft Graph → email, openid, profile). preferred_username is not accepted as an email.
  • Every cipi gui sso change is logged in cipi.log and raises the gui_sso notification trigger (Security).
