Available since v5.4.0. Until then a React or Vue SPA could only be a custom app serving a build committed to git: no build step, and client-side routes returned 404 on reload. SSR frameworks could not run at all. Node apps are an app type of their own, with the same lifecycle as Laravel apps — releases, rollback, webhook, SSL, basic auth, redirects and proxies, and the deploy audit ledger.

bash
# Vite + React/Vue/Svelte: build, then nginx serves dist/ with an /index.html fallback
cipi app create --user=web --domain=web.example.com \
    --repository=git@github.com:you/web.git --node=spa --framework=vite

# Pre-rendered site (Astro, Nuxt generate, Next export): real 404s
cipi app create --user=docs --domain=docs.example.com \
    --repository=git@github.com:you/docs.git --node=static --output=dist

# Node server with blue/green deploys
cipi app create --user=shop --domain=shop.example.com \
    --repository=git@github.com:you/shop.git --node=ssr --framework=next --node-version=24

Modes

Mode What nginx does
spa Serves current/<output>; unknown paths fall back to /index.html, so client-side routes survive a reload. assets/, _astro/, _nuxt/, _app/immutable/ and static/ are cached as immutable; *.html is no-cache.
static The same without the fallback: $uri.html, then a real 404 with /404.html.
ssr Proxies to a Node process on localhost through an upstream (/etc/nginx/conf.d/cipi-node-<app>.conf), with WebSocket upgrade and X-Forwarded-* headers.

Options and framework presets

--node=spa|static|ssrThe app type and mode.
--framework=next, nuxt, sveltekit, astro, remix (all ssr) or vite (spa, output dist). A preset fills in the mode, build and start command; explicit flags win.
--node-version=22|24Node major (even, LTS majors only). Defaults to the server default.
--build=Build command, default npm run build.
--start=SSR start command — e.g. node build (SvelteKit), node .output/server/index.mjs (Nuxt). Next.js starts with next start -H 127.0.0.1. Only a Node runner (node npm npx pnpm yarn bun) plus plain arguments is accepted.
--output=Build directory for spa / static; the deploy fails if <output>/index.html is missing.
--health-path=SSR only: the path a new release must answer below 500 before it takes traffic (default /).

The build

The Deployer recipe installs dependencies from the lockfile — npm ci, pnpm install --frozen-lockfile, yarn install --immutable (or --frozen-lockfile), bun install --frozen-lockfile; npm install with a warning when there is no lockfile — then builds with NODE_ENV=production and telemetry off. shared/.env is a shared file, so frameworks read it at build time and SSR servers at runtime. Edit it with cipi app env.

Blue/green deploys for SSR

An SSR app has two Supervisor programs, <app>-node-blue and <app>-node-green, each on its own localhost port in 3100–3999, in /etc/supervisor/conf.d/<app>-node.conf (so cipi-worker restart cannot bounce both). Before deploy:symlink, the recipe calls cipi-node-switch:

  1. the new release starts on the idle slot;
  2. it must answer below 500 on the health path within 60 seconds;
  3. the upstream moves (nginx -t, reload) and the old slot stops after a short drain.

A process that exits or never answers is stopped, the old slot keeps serving, and the deploy fails before current moves. cipi deploy <app> --rollback switches back the same way, and cipi node restart <app> is blue/green too — no downtime.

What the app user cannot change. cipi-node-switch runs as root through one sudoers rule per app. Only the release path comes from the caller, and it must be a release of that app; ports, start command, Node version and health path come from /var/lib/cipi/node/<app>.json, which only root writes. cipi-node-run reads .env as KEY=VALUE data and never sources it: PORT and HOST cannot be overridden, HOST, HOSTNAME and NITRO_HOST are forced to 127.0.0.1, and the start command runs as argv with no shell.

Webhooks without cipi/agent

A Node app has no Laravel to install Cipi Agent into, so /cipi/webhook goes to a receiver Cipi ships (/usr/local/share/cipi/webhook.php) through an on-demand PHP-FPM pool running as the app user: open_basedir limited to the home and the receiver, exec-family functions disabled, 2 MB body, POST only, never behind basic auth. It verifies GitHub and Bitbucket HMAC-SHA256 and GitLab / Azure DevOps tokens, deploys only pushes to the app's branch, and records the pusher, delivery id and commit in the audit ledger under claimed. With a Git provider token the webhook is registered for you, and cipi git refresh covers Node apps.

Managing a Node app

bash
cipi node status shop           # mode, commands, blue/green slots
cipi node restart shop          # zero-downtime restart (SSR)
cipi node logs shop --lines=100 # log of the serving slot
cipi app edit shop --start="node .output/server/index.mjs" --health-path=/health
cipi app edit web --node=static --output=dist
cipi app edit shop --node-version=24

cipi app edit accepts --build=, --start=, --output=, --health-path=, --node-version= and --node=spa|static|ssr. cipi app show and cipi app list show the mode and slots; cipi app delete stops and removes both slots, the upstream and the state. The same settings can live in the repository as the node: section of cipi.yml, applied by the deploy itself. Runtimes are managed with cipi node. From the panel: API 1.31+ and the GUI create, edit and restart Node apps.

Not yet: cipi sync skips Node apps with a message, and cipi app clone refuses them, as it does custom apps. No database is created with a Node app — add one with cipi db or the databases: section of cipi.yml.
