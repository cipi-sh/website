Cipi creates a dedicated database for each Laravel app automatically during app create. MariaDB (port 3306) is the native default; since v4.8.0 you can also install optional PostgreSQL (port 5432) and choose an engine per database or app. Custom apps do not get a database — use cipi db create --name=<app> if you need one (e.g. for WordPress or another CMS). After setup, a ready-to-use connection URL is displayed (MariaDB: mariadb+ssh://), combining SSH credentials, server IP, and database information for GUI clients like TablePlus, DBeaver, or Sequel Pro.

Engines (v4.8.0+)

bash
cipi db install pgsql              # install optional PostgreSQL
cipi db uninstall pgsql|mariadb    # remove a non-default engine (destroys data)
cipi db default mariadb|pgsql      # server-wide default when --engine is omitted
cipi db engines                    # installed engines, ports, and default

Database lifecycle

bash
cipi db create                              # interactive: engine menu, then the name
cipi db create --name=analytics             # engine menu on a terminal; default engine in a script
cipi db create --name=analytics --engine=pgsql
cipi db create --name=wpblog --app=blog     # v5.9.0+ created and shown as that app's
cipi db link wpblog blog                    # v5.9.0+ the same for a database that exists
cipi db unlink wpblog
cipi db list [--engine=mariadb|pgsql]       # databases with sizes and the app each belongs to; --json (v5.9.0+)
cipi db backup myapp [--engine=…]
cipi db restore myapp backup.sql.gz [--engine=…]
cipi db password myapp [--engine=…]         # regenerate password
cipi db delete analytics [--engine=…]

A database that belongs to an app (v5.9.0+)

A Laravel app gets its database with cipi app create. Everything else — the database of a WordPress on a custom app, a second database of a Laravel app — was created with cipi db create and belonged to nobody: nothing on the server or in the panel said which app it was for. --app=<app> on create, or cipi db link afterwards, says it.

  • The link is a label. The database keeps its own user and password, a database is linked to one app at most (linking it elsewhere moves it), and cipi app delete leaves a linked database where it is and names it — only the database created with a Laravel app goes with the app.
  • cipi db list on a terminal has an APP column: the linked app, the app a database was created with, or the app whose namespace it is in (<app>_…, what cipi.yml lets an app declare). cipi app show lists an app's linked databases, and so do the Apps and Databases pages of the panel.
  • Piped or run by a script, the table keeps the four columns it always had; cipi db list --json carries engine, name, user, size, app and link (linked, own, namespace).

Since v5.6.0, with both engines installed and no --engine, cipi db create on a terminal opens a menu — MariaDB or PostgreSQL, the server default (cipi db default) pre-selected, Enter to take it. A script, or a server with one engine, gets the default without a prompt.

Since v5.6.0, cipi db restore stops at the first failed statement on both engines and says what failed (PostgreSQL restore: ERROR: relation "users" already exists), exiting 1 — before, a PostgreSQL restore could leave the database empty and still print restored. A .gz that does not uncompress fails too. A dump taken on a newer PostgreSQL (e.g. pg_dump 17 into PostgreSQL 16 on Ubuntu 24.04) still restores: preamble SET lines for parameters this server does not have are dropped. The same applies to cipi app clone --with-db and cipi sync import.

Since v5.6.2, a failed PostgreSQL restore no longer empties the database: wipe and import run in one transaction and COMMIT is sent only after the whole dump has been read, so a truncated archive, a read error or a failing statement rolls the wipe back. An empty dump is refused — including a backup taken while pg_dump failed, which can be a valid archive of nothing. The new public schema goes to the database owner, not a role named after the database.

Since v5.9.0, a dump that is in an app's home or in the panel's storage is opened by the owner of that tree — the app user, or www-data for a dump uploaded through the panel — not by root: there the file is whatever that user made of its name a moment ago. A file of root's is read as before.

Laravel apps store the chosen engine in app metadata; backup, sync, and cipi app reset-db-password follow it. Use cipi app create --engine=pgsql (or the interactive prompt) to provision a Laravel app on PostgreSQL — .env and the connection URL match the engine. Root password reset: cipi reset db-password [--engine=].

cipi db upgrade (v5.2.3+)

Both engines are excluded from unattended-upgrades on purpose, so patch-level upgrades are a command you run:

bash
cipi db upgrade                  # every installed engine
cipi db upgrade mariadb [--yes]
cipi db upgrade pgsql   [--yes]

Expect brief downtime while the service restarts — the prompt says so before it starts. See manual stack upgrades.
