app list / app show / app edit / app delete

Command Description
cipi app list List all apps with domain, PHP version, and status ((suspended) when offline)
cipi app show <app> Full details: domain, PHP, deploy key, workers, webhook, suspend state, and since 5.3.1 the app redirect, path redirects and proxy prefixes. Since 5.4.0: the Node mode, commands and blue/green slots of a Node app, and for a Laravel app whether its Node builds are pinned to a major or follow the server default. For custom apps: type "Custom", docroot; webhook (and deploy key) omitted when SFTP-only without a repository. Since 5.8.0: the app's Environment (production unless created or edited with --env).
cipi app edit <app> --php=8.5 Hot-swap PHP version. Updates FPM pool, Nginx socket, Supervisor, crontab, Deployer config, and .env — zero downtime. Since v5.10.0, on an FPM app with JIT on the setting moves to the new version's pool and the shared JIT buffer file is rewritten for both versions; on an Octane app Cipi warns when the pinned FrankenPHP build carries a different PHP (the CLI, cron and workers move, the web workers stay on the binary's PHP until you pin a matching build)
cipi app edit <app> --branch=develop Change the deploy branch. Since 5.7.2 it also rewrites CIPI_DEPLOY_BRANCH in the app's .env; a deploy.branch in cipi.yml does the same through cipi yml apply (5.8.0+)
cipi app edit <app> --env=staging Change the app's environment label (since v5.8.0; same rules as cipi app create --env). Rewrites APP_ENV (Laravel) and CIPI_ENV in the app's .env, and from then on the app reads cipi-staging.yml before cipi.yml — see per-environment cipi.yml. Composable with the other app edit flags
cipi app edit <app> --domain=new.example.com Rename the primary domain (since v4.6.2). Validates format and uniqueness, moves the old primary to aliases, regenerates the Nginx vhost, updates APP_URL, refreshes Git webhooks when auto-configured, and re-issues Let's Encrypt when a certificate already existed
cipi app edit <app> --repository=<SSH-URL> Attach or change the Git repository (e.g. enable deploy on a custom SFTP-only app created without --repository). Composable with --branch, --php, and --domain
cipi app edit <app> --node-build='npm ci && npm run build' Run a Node build after Composer vendors on every deploy (since v5.0). Deployer executes .deployer/node-build.sh (fail-closed; command is validated). Clear with --no-node-build
cipi app edit <app> --node-version=24|default Pin one Laravel app's Node builds to its own major, whatever the server default is (since v5.4.0). node-build.sh exports that major's PATH, and cipi app run and deploy.post use it too. --node-version=default follows the server again. On a Node app it changes the runtime; there --build=, --start=, --output=, --health-path= and --node= are accepted as well
cipi app edit <app> --predeploy-snapshot Enable a database dump before every deploy (since v5.0). Same behaviour as passing --snapshot on each cipi deploy. See Pre-deploy DB snapshots
cipi app convert <app> --to=octane|fpm Convert between PHP-FPM and Laravel Octane (since v5.0). See Laravel Octane. Since v5.10.0 it turns JIT off and pins or unpins FrankenPHP
cipi app jit <app> [status|on|off] [--mode=tracing|function] [--buffer=128M] Show or set PHP JIT for one app (since v5.10.0), FPM or Octane. Checked with the app's own PHP before it is applied and rolled back if the reload fails. REST: GET|PUT /api/apps/{name}/jit (API 1.40.0+). See app jit
cipi frankenphp status|upgrade|use|fetch|import|adopt|remove|prune Manage the FrankenPHP builds Octane apps are pinned to (since v5.10.0): several PHP versions side by side, one pin per app, upgrades on the same PHP minor with a health check and rollback. REST: GET /api/frankenphp, POST /api/frankenphp/upgrade. See FrankenPHP builds
cipi app env <app> [--show|--get|--set|--unset] Open the app's .env in nano, or manage keys non-interactively since v5.0.3 (--show/--get/--set/--unset, optional --json). Exits with error for custom apps (no .env).
cipi app run <app> <cmd> [args…] Whitelisted non-interactive command as the app user (since v5.0.3). See app run
cipi app deploy-config <app> Structured Deployer recipe options (since v5.0.3). See deploy-config
cipi app webhook recreate <app> [--rotate-secret] Recreate the GitHub/GitLab deploy webhook; optional secret rotation updates CIPI_WEBHOOK_TOKEN (since v5.0.6). REST: POST /api/apps/{name}/webhook/recreate (API 1.15.0+). Since 5.0.6, app edit --repository= only recreates webhook/deploy key when the repository URL actually changes.
cipi app fix-permissions [app] Reapply the permission layout Cipi created the home with (since v5.2.1). One named app, or every app. See app fix-permissions
cipi app reset-password <app> Regenerate the app's Linux user SSH password. The new password is displayed on screen — save it immediately
cipi app reset-db-password <app> Regenerate the app's database password (MariaDB or PostgreSQL per app engine) and automatically update DB_PASSWORD in the app's .env. Exits with error for custom apps (no database).
cipi app delete <app> Permanently remove the app, user, database (if Laravel), Nginx vhost, FPM pool, and Supervisor workers. For custom apps, skips database drop (none was created). Since v5.2.2, also revokes the app's Meilisearch key and drops its indexes — see cipi search. Since v5.6.4, also removes its cipi.yml auto-apply sudoers rule (/etc/sudoers.d/cipi-<app>-yml). Since v5.10.0, also removes the app's FrankenPHP pin and its Octane ini directory, and rewrites the shared JIT buffer file without it (builds no other app uses are left for cipi frankenphp prune). Asks for confirmation.
cipi app delete <app> --force Same as delete but skips the confirmation prompt — for scripts, the panel API, and cipi-cli

cipi use — a default app

Available since v5.7.2. cipi use <app> names the app the per-app commands act on when none is given: cipi deploy, cipi app logs|env|artisan|edit, cipi yml plan|apply, cipi worker list, cipi ssl install, cipi www …, cipi alias …, cipi health … and the others run against it and print → <app> (default app — cipi use) on stderr. The default is saved on the server (/var/lib/cipi/default-app); CIPI_APP=<app> does the same for one shell and wins over the file.

bash
cipi use shop                 # the default for the commands that need an app
cipi deploy                   # → shop (default app — cipi use)
cipi app logs --type=php
cipi yml plan
cipi use                      # show it
cipi use --clear              # remove it

It fills in a missing app only where one is a required argument, so nothing that works changes meaning: a command for which a missing app means every app (cipi git refresh|check, cipi scan) keeps it, and cipi app delete|reset-password|reset-db-password|convert|clone and cipi db … still want the name. The panel API never gets a default. Tab-completion and cipi help use know the command.

cipi app clone

Since v5.0, clone an existing Laravel app into a new staging (or review) app with its own domain. Sets cloned_from in apps.json; does not copy webhook or git IDs. If the source has Reverb, the clone gets its own port, credentials and public host (since v5.1.2) — it no longer inherits the production socket. See cipi app reverb. Since v5.2.2, a cloned Scout app gets its own Meilisearch key and SCOUT_PREFIX; the source's MEILISEARCH_* keys are excluded from the copied .env, because a clone that inherited them would reindex into production. See cipi search. Since v5.10.0, an Octane clone is pinned to the same FrankenPHP build as its source when that build is a trusted one (fetched or imported; a build adopted from the source's own release is trusted only for the source, so the clone keeps the newest build it got at create). JIT is not copied: turn it on for the clone with cipi app jit if you want it there too.

bash
cipi app clone myapp --domain=staging.myapp.com
cipi app clone myapp --domain=staging.myapp.com --name=myapp-stg --branch=develop --with-db
cipi app clone myapp --domain=staging.myapp.com --branch=develop --env=staging   # 5.8.0+: the clone reads cipi-staging.yml
cipi app clone myapp --domain=staging.myapp.com --no-db
--domainRequired. Primary domain for the new app.
--nameOptional Linux username for the clone.
--branchDeploy branch for the clone (defaults to the source app's branch).
--envEnvironment label for the clone (since v5.8.0; defaults to the source app's). --env=staging writes APP_ENV=staging / CIPI_ENV=staging into the clone's .env and makes it read cipi-staging.yml before cipi.yml, so one repository can carry both files — see staging and production from one repository.
--with-dbCreate a fresh database for the clone.
--no-dbSkip database provisioning for the clone.

cipi app fix-permissions

The panel already had cipi api fix-permissions and cipi gui fix-permissions; apps did not. A blunt chown -R app:app /home/<app> is wrong: nginx writes vhost logs as www-data into logs/ (2775 setgid), the home must stay 750 so www-data (in the app group) can read the docroot, .ssh must be 700 or OpenSSH StrictModes refuses the deploy key, and shared/.env is 640. This command reapplies that layout — ownership of the tree except logs/, then the log/ACL helper, storage dirs 775, Composer auth.json 640, cipi-databases.env 600. One named app, or every app.

bash
cipi app fix-permissions myapp
cipi app fix-permissions          # every app on this server

cipi deploy already runs the log-ACL helper before Deployer. fix-permissions is the full home, on demand, after someone unpacked a zip as root or chmod'd .ssh to 775. Available since v5.2.1. No migration: cipi self-update copies the libs and refreshes shell completion. The panel sudoers file lists the new command, and since API 1.31 the panel calls it (POST /api/apps/{name}/fix-permissions, and a button in the GUI); existing servers pick that line up the next time sudoers is rewritten (the CLI runs as root and does not need it).
