Nginx, MariaDB, PostgreSQL and Valkey are deliberately kept off unattended-upgrades, which would restart them whenever it runs. PHP has cipi php upgrade (daily at 03:30 since v5.6.3). For the rest there are the commands below (since v5.2.3) — patch-level only, asking first — and, since v5.9.0, cipi autoupdate, which runs the same code every night without asking.

cipi autoupdate — nightly patches (v5.9.0+)

Until 5.9.0 these components waited for someone to run an upgrade command, and nothing said there was one to run; Composer and the Node.js runtimes were never updated at all once installed. They are now patched every night at 04:20:

bash
cipi autoupdate                    # what is on, how the last run went
cipi autoupdate off mariadb        # patch this one by hand
cipi autoupdate off frankenphp     # Octane apps' FrankenPHP builds (v5.10.0+)
cipi autoupdate on                 # everything back on
cipi autoupdate run [name]         # now (what the nightly job runs)
  • Components: nginx, mariadb, pgsql, valkey, node (the runtimes under /opt/cipi/node and the system package), composer and, since v5.10.0, frankenphp — the build of each Octane app, moved to the newest one on the app's own PHP minor and FrankenPHP major, Octane restarted and checked, the previous build back if it does not answer; a release on another PHP minor is announced once, never applied. On unless switched off — on servers that update to 5.9.0 or 5.10.0 too.
  • Patch releases only: apt --only-upgrade of what is already installed, Cipi's configuration files kept, nginx -t before the reload. A Node runtime is checked against its published SHA-256, and an SSR app is restarted (blue/green) only when its runtime changed. Composer is rolled back if the new version does not start.
  • One after the other, the databases last. A database patch restarts the database: it happens at 04:20 on the night the patch arrives, and it is left for the next night while a dump or a deploy is running. Switch a component off if you want to choose the moment.
  • Each upgrade is logged and notified like the manual one (nginx_upgrade, mariadb_upgrade, pgsql_upgrade, valkey_upgrade, node_upgrade, composer_upgrade, frankenphp_upgrade); a failed run is a cron_fail notification and an item in cipi pending. Log: /var/log/cipi/autoupdate.log.

cipi pending — what is waiting for you (v5.9.0+)

A server can be fully up to date and still run last month's kernel, because nothing restarts it. cipi pending collects what an update cannot do by itself:

bash
cipi pending            # the list, with what to run for each item
cipi pending --json
  • a reboot installed updates need — Ubuntu's own flag, and the newest kernel in /boot against the one that is running;
  • PHP below its security release, or a branch that is end of life; Composer and Node.js below theirs;
  • since v5.9.1: nginx below its security release (1.31.9), on the Ubuntu archive's build instead of nginx.org mainline, or upgraded on disk with the old binary still running (nginx security); a PHP that is a release candidate, and the extensions a new PHP branch is still waiting for;
  • a newer package of a component whose automatic update is off, or whose last run failed;
  • PHP extensions installed with PECL (or built by hand). Cipi installs extensions from apt only and cipi php upgrade patches those; a .so no package owns is updated by nothing, and PECL itself is deprecated by the PHP project in favour of PIE;
  • apps with Horizon installed, the queues on Redis and no worker (a deploy from the command line turns Horizon on; one from a Git push cannot);
  • apps that still share one Valkey; Ubuntu's security updates switched off; a Cipi logrotate rule that logrotate refuses.

Checked every morning at 07:30 and mailed when the list changes — then again after a week, for as long as something is on it, never every day (trigger pending_report). cipi status shows the same list when there is one.

cipi reboot (v5.9.0+)

bash
cipi reboot                        # is one required, since when, which kernel
cipi reboot now [--yes]            # restart in one minute
cipi reboot auto on --at=04:45     # at night, only on the nights one is required
cipi reboot auto off

Automatic reboot is off unless you turn it on. When on, the nightly job does nothing on the nights no reboot is required; otherwise it sends a notification (trigger reboot), warns two minutes ahead and restarts — and waits for the next night while a package installation, a database dump, a deploy or another cipi command is running.

By hand

bash
# nginx — apt --only-upgrade of installed nginx*, nginx -t, then reload
cipi nginx upgrade [--yes]
cipi nginx security        # v5.9.1+ patch level, running binary, where HTTP/2 is on

# databases — one engine, or every installed engine when omitted
cipi db upgrade [mariadb|pgsql] [--yes]

# the generic entry, and the home for Valkey
cipi service upgrade [nginx|mariadb|postgresql|valkey] [--yes]

# no name: list installed versions against the current apt candidate
cipi service upgrade
Command What it does
cipi nginx upgrade [--yes] apt --only-upgrade of the installed nginx* packages from the nginx.org mainline repo Cipi already configured, then nginx -t and a reload. /etc/nginx/nginx.conf is kept (--force-confold) — this is not the HTTP/2-bomb rewrite. Since v5.9.1: nginx is restarted instead of reloaded when the old binary is still running after the upgrade, and a server on the Ubuntu archive's nginx is moved to nginx.org mainline.
cipi db upgrade [engine] [--yes] The same for MariaDB / PostgreSQL. Without an engine argument it upgrades every installed engine. The prompt says plainly that there will be brief downtime.
cipi service upgrade [name] [--yes] The generic entry point, and the only way to upgrade Valkey. With no name it lists installed versions against the current apt candidate. all is refused — that is exactly what the blacklist exists to prevent — and php is pointed at cipi php upgrade.

How it stays scoped

All three share lib/stack-upgrade.sh, which pins the package patterns (^nginx(-|$), ^mariadb-, ^postgresql, ^valkey) so a loose match cannot drag PHP in. It re-asserts the nginx.org and MariaDB.org repositories if they were wiped, and holds /run/cipi-stack-upgrade.lock so two upgrades cannot overlap.

On success, and when SMTP is configured, you get a mail: nginx_upgrade, mariadb_upgrade, pgsql_upgrade or valkey_upgrade (disable any of them with cipi notifications disable <trigger>).

These commands are not on a cron and not on the panel. setup.sh and cipi self-update do not run them, and /etc/sudoers.d/cipi-api does not grant them — the same rule as cipi package install. Upgrading a database engine is an operator decision, taken while you are watching.
