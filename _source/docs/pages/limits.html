cipi app limits

Since v5.0, set per-app resource limits with hard caps enforced by Cipi.

bash
cipi app limits myapp --fpm-max-children=20 --memory-limit=256M
cipi app limits myapp --octane-workers=4 --worker-procs=3
cipi app limits myapp --disk=10     # soft disk limit in GB (v5.5.0+) — alerts, blocks nothing
cipi app limits myapp --disk=none   # back to no limit (the default)
cipi app limits myapp   # show current limits
--fpm-max-childrenPHP-FPM pm.max_children for FPM apps.
--memory-limitPHP memory_limit.
--octane-workersOctane worker count for FrankenPHP apps. Since v5.10.0, rewriting the Octane Supervisor program also applies its new environment: the app's own ini directory on PHP_INI_SCAN_DIR (where JIT lives) and /home/<app>/current first on PATH, so Octane finds the pinned binary.
--worker-procsSupervisor queue worker process count.
--diskSoft disk limit in GB for files and database together (e.g. 10, 2.5), or none. Since v5.5.0.

Soft disk limit (v5.5.0+)

No app has a disk limit unless one is set: the default is unlimited, on new and existing servers alike. --disk sets one for the app's files and database together — the TOTAL column of cipi disk — and the command reports what the app uses now, warning if it is already over.

  • It is soft. Nothing is blocked when the limit is passed and the app keeps working. The limit is a threshold for the app_disk monitor check: a warning at 90% of the limit, a critical alert once over it, a recovery when it is back under, with the usual reminder every 4 hours in between (trigger monitor_app_disk).
  • Setting only --disk does not rebuild the FPM pool or restart workers.
  • cipi disk shows the limit next to the app (10 GB (64%), and over once passed).
  • The limit is stored next to the app as disk_limit_gb, not inside limits: that object is what cipi.yml reconciles, and an app's repository must not be able to raise the space its server grants it. cipi sync carries it with the app.
  • Since API 1.32 the same reading and the same write are GET|PUT /api/apps/{name}/limits (disk_limit_gb; abilities apps-view / apps-edit; null removes it). The PHP SDK calls limits(). The control panel shows the limit on Server → Disk (panel 3.1 / API 1.33) and sets it on the host. cipi-cli reads usage with disk and leaves the limit to this command.

app suspend / app unsuspend

Available since v4.5.8. Take an app offline without deleting it — useful for billing holds, maintenance windows, or staging sites you want fully dark. Suspending swaps the Nginx vhost for a static HTTP 503 page served from /var/www/cipi-suspended/.

bash
cipi app suspend myapp      # take offline (503 page)
cipi app unsuspend myapp    # restore normal vhost
Command Description
cipi app suspend <app> Sets suspended: true in apps.json, rebuilds the vhost to return 503 for all requests. Idempotent if already suspended.
cipi app unsuspend <app> Clears the flag, restores the normal Laravel/custom vhost, and reapplies SSL blocks. Idempotent if already online.

Behaviour

  • HTTPS included — certbot clones the suspension vhost into the :443 block, so HTTPS also shows the offline page
  • Let's Encrypt still works — the /.well-known/acme-challenge/ path stays public so certificates can be issued or renewed while suspended
  • Survives vhost regeneration — alias changes, PHP edits, and SSL installs respect the suspended flag
  • Visible in listings — cipi app list marks suspended apps; cipi domains appends ⏸ suspended on each row
Suspend vs basic auth: cipi basicauth shows a login prompt but still runs your app. app suspend stops PHP entirely and serves a static offline page — visitors never reach Laravel. Use suspend for “site closed”; basic auth for “invite-only preview”.

Also available via the REST API (POST /api/apps/{name}/suspend), cipi-cli (apps suspend), and the WHMCS module (Suspend / Unsuspend buttons). Requires token ability apps-suspend for API access.
