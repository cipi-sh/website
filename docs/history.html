History

From shell scripts in 2019 to Cipi 5.

AboutEdit on GitHub

Cipi was created by Andrea Pollastri, a software developer since 2005 specialising in Laravel, system administration, and cybersecurity — with experience at companies like Docebo and Musement. He built Cipi out of a practical need: a fast, scriptable way to provision and deploy Laravel applications on his own VPS, without handing control to a SaaS panel. What started as a private tool became an open-source project that grew to over 1,000 GitHub stars and hundreds of active deployments worldwide. Here is a brief account of how it evolved across six years and five major versions.

v0.1 June 2019

The idea#

A collection of shell scripts to automate the tedious parts of setting up a Laravel server on a fresh Ubuntu VPS — Nginx, PHP, MariaDB, Supervisor. No web UI, no package. Just bash.

v1.x June 2019

First release — Laravel panel#

The shell scripts were wrapped in a Laravel web application acting as a server control panel. Users could create apps, manage deployments, and configure Nginx through a browser UI hosted on the same server. The project was published on GitHub and quickly attracted interest from the Laravel community.

v2.x May 2020

Feature growth#

A year of rapid iteration added SMTP configuration, local database backups, PHP-FPM permission fixes, server service management, and root password reset. The v2 series reached 2.4.9 across dozens of patch releases, establishing Cipi as a stable option for small-team Laravel hosting.

v3.0 March 2021

The big leap — API, PHP 8, real-time UI#

Built on Laravel 8, v3 introduced a fully documented REST API (Swagger / OA), PHP 8 support, real-time CPU/RAM charts, a Cronjob editor, Supervisor management, a GitHub repository manager, Node 15, Composer 2, and JWT authentication. Cipi could now manage the same server it ran on. The project reached 1k GitHub stars.

v3.1 December 2021

The last web UI — and a question#

PHP 8.1 became the default version. Node was upgraded to v16, Certbot was refreshed, and domain alias handling was fixed. The v3.1.x series was the most polished release of the web-UI era and many teams kept it running in production for years.

It was also the version that prompted a harder question: was a browser-based control panel still the right interface? Modern development workflows had moved toward SSH, CI/CD pipelines, GitOps, and — increasingly — AI agents that could orchestrate infrastructure through shell commands. A web UI required authentication, a running Laravel process, and a database just to issue a deploy. A CLI needed none of that. The answer shaped everything that came next.

v4.x March 2026

The rewrite — CLI-first, Laravel-exclusive#

After years of maintaining a full Laravel web application as the control plane, v4 made the boldest decision yet: drop the web UI entirely. Cipi became a pure CLI tool operated over SSH. The scope also narrowed from generic PHP to Laravel exclusively, allowing every part of the stack to be optimised for one framework. MySQL was replaced by MariaDB 11.4, git pull was replaced by Deployer zero-downtime releases, shared deploy keys became per-app ed25519 keys, and S3 automated backups and native webhook support for GitHub and GitLab were added from day one. v4 also introduced a complete REST API for programmatic management of hosts and applications, native integration with GitHub and GitLab git providers, a groundbreaking dual MCP server architecture — one per-app and one global — enabling full AI-driven infrastructure management directly from any MCP-compatible IDE or AI agent, encrypted server sync for migrating apps between VPS instances, and a built-in database anonymizer for GDPR-safe data exports.

The full v4 changelog is available on GitHub Releases. Releases 4.5.10–4.5.12 fixed setup on Ubuntu 26.04 (nginx sites-available layout, MariaDB.org and PHP APT probing with packages.sury.org when Launchpad has no suite). 4.5.9 added app suspend / unsuspend (takes an app offline behind a generic HTTP 503 maintenance page without deleting it), wired into the REST API, MCP server, and WHMCS module. v4.5.6–4.5.7 replaced Redis with Valkey, the BSD-licensed open-source fork, with an automatic, self-healing Redis → Valkey migration on self-update. v4.5.5 added the global cipi domains map (every domain and alias across all apps in one table) and an ll shell alias for app users. v4.5.4 bundled Deployer 8, so new PHP installs are restricted to 8.3, 8.4 and 8.5 (with a deploy-time guard for apps still pinned to older versions). Recent point releases also added HTTP basic auth for apps (cipi basicauth enable/disable/status, 4.5.2) and hardened the panel API against the self-update permission reset that caused intermittent HTTP 500s (4.5.3).
v4.7 July 2026

The GUI returns — this time, optional#

Dropping the web UI in v4 was the right call: it made Cipi lean, scriptable, and AI-native. But the question from the v3.1 era never fully closed — some teams and agencies genuinely wanted a browser dashboard, for themselves and for their clients. v4.7 answered it without walking back a single principle: an optional web control panel, installed with one command (cipi gui <domain>) and removed just as easily. It is a separate Laravel 12 package (cipi/gui) that talks to your servers over the same REST API — a thin visual layer, not a new control plane. Install it if you want it; skip it and Cipi is exactly the pure CLI it was in v4. The default install still ships no web surface at all. See the Control Panel docs.

v4.8 August 2026

Multi-engine databases & www redirects#

v4.8 keeps MariaDB as the native default while adding optional PostgreSQL as a first-class engine — install with cipi db install pgsql, pick per app with --engine=pgsql, and manage both through the same cipi db surface. Canonical www ↔ apex redirects land as cipi www, and cipi ssl force restores HTTP→HTTPS redirects without re-issuing certificates. Alias changes no longer drop HTTPS. The panel API (1.12 and web GUI mirror these capabilities (engine on apps/databases, www endpoints, ssl/force). See cipi db, cipi www, and cipi ssl.

v5.0 August 2026

Laravel Octane, Horizon, Reverb & production ops#

v5 makes Cipi the deepest Laravel hosting CLI yet. Optional Laravel Octane (FrankenPHP) runs alongside classic PHP-FPM apps on the same server — create with cipi app create --octane, convert any existing Laravel app with cipi app convert --to=octane|fpm, and let Nginx proxy_pass to a Supervisor-managed Octane process while static assets stay on disk. The panel API (1.14) and web GUI expose Octane create plus non-interactive .env / auth.json / Artisan / app-run / deploy-config (Cipi 5.0.3+). First-class Laravel Horizon (cipi worker horizon, Laravel Reverb cipi app reverb, scheduler CLI, Node builds on deploy, app cloning for staging, pre-deploy DB snapshots, per-app resource limits, Cloudflare DNS-01 / wildcard SSL, and HTTP healthchecks round out the release. See Laravel Octane, app run, workers / Horizon, and SSL DNS-01.

v5.1 September 2026

Backup profiles, cipi.yml, php.ini and honest deploys#

v5.1 is the ops release. Backups become profiles — what, how often, where, how long — so a 30-minute database copy on disk sits next to an encrypted nightly full copy on S3, and tenant databases created at runtime are discovered from the engine. An app can carry a cipi.yml in its repository (aliases, PHP, extra databases, workers, healthcheck, backups) and opt in with cipi yml auto on. cipi ini edits php.ini for both FPM and CLI. Deploys finally report failure by email and by exit code, timestamp their logs, verify the live release, and can roll it back. Nginx claims unmatched HTTPS hosts. Wildcard aliases work. See backup profiles, cipi.yml, cipi ini, and post-deploy healthchecks.

In 5.1: 5.1.3 — a hotfix for cipi ini list: the table header printed, then the command died on the first setting. No migration: the next cipi self-update copies the new lib/ini.sh. Previous: 5.1.2 — WebSockets, done properly. Reverb now generates credentials, derives ws:// vs wss:// from the certificate, raises connection limits, and proxies only /app/{key} and /apps/{id}/… instead of swallowing every URL beginning with /app. workers.reverb lands in cipi.yml, clones get their own Reverb, and cipi app reverb disable restores the previous broadcast driver. Migration 5.1.2 rewrites greedy vhosts (backed up to /var/lib/cipi/vhost-backup-5.1.2) and fills missing .env keys without overwriting. 5.1.1 was a hotfix over 5.1.0: migration 5.1.1 rebuilds the FPM pools an unterminated heredoc could leave empty and regenerates the vhosts that drifted from apps.json, and wildcard domains (*.example.com) now work end to end — primary domain, webhook URLs and DNS-01 SSL. 5.1.0 brought backup profiles, client-side encryption, cipi backup verify, cipi.yml (generate / plan / apply / auto), cipi ini for FPM and CLI, post-deploy healthchecks with optional auto-rollback, cipi nginx default-server, wildcard aliases, and the reliability fixes that make deploy-failure emails, Horizon enable, custom-app backups and multi-tenant dumps actually work. Migration 5.1.0 converts the old nightly job, backfills CLI php.ini, rewrites FPM pools and claims :443 when nothing else does. Panel API 1.20 and the web GUI remain the 5.0.x surfaces. Full changelog: CHANGELOG.md.
v5.2 September 2026

CrowdSec, nightly integrity, Meilisearch, six Git forges, and a shell that completes itself#

v5.2 is the security release, and it is deliberately opt-in: neither setup.sh nor cipi self-update installs any of it. cipi crowdsec enable brings up the engine and a registered firewall bouncer — decisions without a bouncer ban nothing — reads the logs every vhost actually writes, allowlists your SSH session along with GitHub's webhook CIDRs and Let's Encrypt, and starts a break-glass TLS listener so an automatic ban cannot lock you out of your own server. cipi scan checks nightly that a release still matches the sha256 manifest written at its deploy, then runs one ClamAV pass over the upload directories only. There is no WAF. And tab-completion for bash and zsh is now installed for you. Since 5.2.2, the same opt-in rule covers cipi search — Meilisearch as a native binary for Laravel Scout — and cipi package, an allowlisted apt for the host binaries a project sometimes needs. Since 5.2.3, cipi git auto-configures four more forges — Cursor Origin, AWS CodeCommit, Bitbucket Cloud and Azure DevOps — deploy.post lets a repository declare its own post-deploy steps from an allowlist, and manual stack upgrades give nginx, MariaDB, PostgreSQL and Valkey the operator-triggered equivalent of cipi php upgrade. See cipi crowdsec, cipi scan, cipi search, cipi package, and cipi completion.

In 5.2: 5.2.3 — Git beyond GitHub and GitLab: cipi git now detects Cursor Origin, AWS CodeCommit, Bitbucket Cloud and Azure DevOps from the clone URL, registers the deploy key, and creates the webhook where the forge has one (Bitbucket repo:push with an HMAC secret; Azure a git.push service hook sending X-Gitlab-Token). Origin and CodeCommit get the key only — neither has a per-repo HTTP webhook. cipi.yml gains deploy.post: allowlisted post-deploy steps (artisan, npm, composer, a php/node script — no shell) that run without needing yml auto. cipi nginx upgrade, cipi db upgrade and cipi service upgrade apply patch-level updates to the four packages deliberately kept off unattended-upgrades — manual, never on a cron, and all is refused. Security fix: a custom app's committed cipi.yml was downloadable at https://<domain>/cipi.yml; every app vhost now denies /cipi.yml and /cipi.yaml at any path, applied on update without regenerating the vhost. Previous: 5.2.2 — two more opt-in additions, neither installed by setup.sh or cipi self-update. cipi search is Meilisearch as a native binary for Laravel Scout: listen on 127.0.0.1, mint a key scoped to <app>-*, write SCOUT_PREFIX yourself so two apps cannot share an index. cipi app delete revokes the key; cipi app clone mints a new one instead of inheriting production's. cipi package is an allowlisted apt for host binaries a Laravel project may need — image optimisers, ffmpeg, the ImageMagick CLI, pdftotext — and the allowlist is the feature. Chromium is refused on purpose (it would pull snapd). Previous: 5.2.1 — cipi git refresh [app] and cipi app fix-permissions [app]. Previous: 5.2.0 — opt-in CrowdSec (engine and a registered firewall bouncer) and a nightly integrity check. Panel API 1.20 and the web GUI are unchanged. Full changelog: CHANGELOG.md.
v5.3 September 2026

Cloudflare Zero Trust, a server monitor, and alerts where you actually look#

v5.3 keeps the opt-in contract of 5.2. cipi zt enable installs cloudflared, creates a locally-managed tunnel and teaches Nginx, fail2ban and CrowdSec Cloudflare's edge ranges — without closing a single port. Every step after that is explicit: route an app through the tunnel, put Cloudflare Access in front of staging or the GUI, carry SSH over the tunnel, and only then cipi zt lock http (80/443 closed, or Cloudflare-only) and cipi zt lock ssh, which refuses unless the tunnel already carries SSH. Public sites stay public. cipi monitor is the other half: cipi health watches app URLs, the monitor watches the server — disk, certificate expiry, services, queue workers, 5xx spikes, read-only filesystems and load — every five minutes, alerting on state changes rather than on every run. And every notification Cipi sends can now reach Slack, Discord, Telegram, ntfy or a custom webhook as well as email. See cipi zt, cipi monitor, and notification channels. 5.3.1 adds audit evidence with cipi compliance, plus redirects and proxy prefixes that survive every vhost rebuild.

In 5.3: 5.3.1 — cipi compliance collects evidence for ISO/IEC 27001:2022 and SOC 2 audits: 17 read-only controls (SSH, firewall, patching, TLS, accounts, API tokens, GUI 2FA, secrets, deploys, backups, logging, monitoring and more), and cipi compliance report writes a root-only bundle with report.md, report.json, the raw evidence and SHA256SUMS, archived with a printed SHA-256. No token hashes, password hashes, 2FA secrets or backup credentials are ever exported, and the report states Cipi's own gaps — the vault is AES-256-CBC without a MAC — before an auditor asks. cipi redirect moves a whole app in one hop or redirects single paths and prefixes; cipi proxy hands a prefix to another upstream with WebSocket, forwarded headers and an optional unbuffered mode. Both live in apps.json, survive vhost regeneration, are validated against nginx injection and loops, and roll back if nginx -t fails. CLI only; no migration. Previous: 5.3.0 — Cloudflare Zero Trust (cipi zt), off until you ask: setup.sh and cipi self-update never install cloudflared. The API token lives root-only in /etc/cipi/zt.token and is not the certbot DNS-01 file. lock http refuses while any app still renews Let's Encrypt over HTTP-01; lock ssh refuses unless cloudflared is active with SSH ingress, and cipi zt ssh unlock is the way back. The optional cipi zt origin-cert installs a 15-year Cloudflare Origin CA certificate. cipi monitor runs seven checks from /etc/cron.d/cipi-monitor, each toggleable and each with its own monitor_* trigger, recovery included. cipi notifications channel add fans every trigger out to chat, best-effort with a 5-second timeout. Fixed: jq's // true read an explicit false as true — a muted trigger kept sending email, cipi smtp configure --tls=off was ignored, and health: {enabled: false} in cipi.yml did nothing. Migration 5.3.0 installs the monitor cron and default configs, adds zt status and monitor list to the panel API sudoers, and configures no channel. Panel API 1.20 and the web GUI are unchanged. Full changelog: CHANGELOG.md.
v5.4 September 2026

Node apps, a deploy ledger nobody can argue with, and a cipi.yml that covers the whole app#

v5.4 stops treating JavaScript frontends as second-class. cipi app create --node=spa|static|ssr builds a Vite SPA, a pre-rendered site or a Next.js, Nuxt, SvelteKit, Astro or Remix server on every deploy, with the same releases, rollback, webhook and SSL as a Laravel app — SSR apps switch blue/green only after the new release answers its health path. cipi node installs checksum-verified official Node builds and can make one the server-wide Node for Laravel asset builds, which is how servers leave end-of-life Node 20 for 22. Every deploy, however it was started — CLI, panel, webhook, dep over SSH or an MCP client inside the app — now lands in a root-only, hash-chained ledger that records what root verified apart from what the app claimed. And cipi.yml gains the www redirect, basic auth, redirects, proxies, Meilisearch, recipe options, limits, forced HTTPS, required .env names, crons and a Node app's build. See Node apps, cipi node, the deploy audit ledger, and the new cipi.yml keys.

In 5.4: 5.4.1 — opens redirects, proxies and Node app management to the panel: www-data may now run cipi redirect, cipi proxy add|remove|list and cipi node list|status|restart, each as an exact command line. Node runtime management, cipi search install|upgrade|key-rotate, cipi package install|remove and every zt change deliberately stay CLI-root. Panel API 1.31.0 covers Cipi 5.1.1 → 5.4.0 in one release — redirects, proxies, Node apps and runtimes, the deploy audit, Meilisearch, read-only packages / monitor / Zero Trust, fix-permissions and wildcard domains, 68 MCP tools — and the web GUI puts all of it in the browser. Previous: 5.4.0 — Node apps with blue/green SSR and a webhook receiver that needs no cipi/agent; cipi node; the deploy audit ledger in /var/log/cipi/deploys.jsonl, mirrored to syslog, read by cipi deploy --audit and cipi compliance deploys; twelve new cipi.yml keys. Fixed: old backups were never deleted — archives from before 5.1 and from removed profiles are now pruned, and S3 retention errors alert instead of failing silently; cipi api update no longer announces an update every night. Migration 5.4.0 adds the audit hooks without touching the rest of deploy.php and moves servers still on Node 20 to 22. Full changelog: CHANGELOG.md.
v5.5 October 2026

Who is filling the disk, who may log in, and logs that finally expire#

v5.5 answers the questions an operator asks at 2am. cipi disk prints every filesystem and then every app, largest first — files, database, total and share of the disk — and cipi disk db lists every MariaDB, PostgreSQL, Valkey and Meilisearch database in MB, including the ones no app owns. An app can get a soft disk limit that alerts at 90% and when passed, through the monitor and every chat channel, without ever blocking a write. cipi ssh apps disable keeps app users out of SSH and SFTP from other machines while deploys over ssh localhost keep working, and cipi firewall attempts sets how many failed SSH logins it takes for fail2ban to ban an address, in a drop-in no update resets. Wildcard certificates can now come from several Cloudflare accounts on one server, each renewing with its own token. And Laravel logs finally follow the 12-month retention: one laravel.log, rotated once, compressed and expired. See cipi disk, soft disk limits, cipi ssh apps, cipi firewall attempts, and Cloudflare accounts for DNS-01.

Latest: 5.10.0 — FrankenPHP builds pinned per Octane app: every deploy links the build Cipi pinned instead of letting Octane download the latest one, so an app changes PHP only when you say so; apps on PHP 8.5 and 8.6 run side by side, and nightly patches stay on each app's PHP minor. cipi app jit turns PHP's JIT on for one app, checked before and rolled back if the app does not come up. cipi notification sends every alert through SMTP, Resend, Amazon SES, Slack, Discord, Mattermost, Google Chat, Telegram, ntfy, Pushover or a signed webhook. Fixed on fresh servers: Deployer 8 pinned (deployer.org served Deployer 6, and every deploy failed) and the panel vhost on nginx.org packages. Panel API 1.40.0.
5.9.1 — a security release for nginx 1.31.9 (18 November 2026, ten CVEs) and for the PHP security release of 19 November 2026 (8.2.36, 8.3.37, 8.4.28, 8.5.13: the update installs them and reports anything older as vulnerable), and PHP 8.6, released the same day. Every server is brought to nginx 1.31.9 or newer from nginx.org mainline: CVE-2026-118899 (an endless loop while reading a request body over TLS 1.3) needs nothing but an HTTPS vhost, and CVE-2026-125283 (try_files under an alias) is what the panel API vhost had for /api-docs — the alias is gone. CVE-2026-123007 and CVE-2026-123633 are in the HTTP/2 code: Cipi 4 and 5 never turn HTTP/2 on, so they apply only where someone did by hand. Servers installed with 4.6.5–5.9.0 ran the Ubuntu archive's nginx, which nothing patched; migration 5.9.1 moves them to nginx.org mainline (simulated first, nginx.conf adapted in place with a backup). After an nginx upgrade Cipi restarts nginx when the old binary is still the one running; cipi nginx security shows patch level, running binary and where HTTP/2 is on, and cipi pending lists the same. PHP 8.6: cipi php install 8.6, --php=8.6, php: "8.6" in cipi.yml — a new server is installed with 8.6 (8.5 for as long as the repository has no complete release of it — on the day of the release 8.6.0 was there without its redis, memcached and imagick packages), a server already installed keeps its PHP and gets 8.6 only when you install it. A branch that is new in the repository installs without the extensions that are not packaged yet (redis, memcached, imagick), which the nightly cipi php upgrade adds when they are; a release candidate is reported as prerelease. Panel API cipi/api 1.39.2 and cipi/agent 2.1.1 accept 8.6.
5.9.0 — a security release, and what people asked for. Two reported holes closed: app users are out of the www-data group (any app could reach any other app's PHP-FPM socket), and cipi-app-notify and parse_args no longer evaluate an argument as arithmetic. Root no longer writes, reads or chowns by path inside an app's home or the panel's tree — it asks the owner — and the logs nginx, supervisor and cipi deploy write moved to /var/log/cipi-apps/<app>; logrotate rotates an app's own logs as the app user. One Valkey per app (cipi valkey isolate). cipi autoupdate patches nginx, MariaDB, PostgreSQL, Valkey, Node.js and Composer every night; cipi pending says when a reboot, a patch or a PECL extension is waiting; cipi reboot auto on is opt-in. The server's SSH keys log in as any app user. cipi api token create --full-access (cipi/api 1.39.0). A failed deploy releases its lock; cipi auth create opens the editor. Then the requests: cipi deploy --history and --last read the rotated deploy logs (webhook deploys keep their duration); a deploy turns Horizon on when it is installed, on Redis, with no worker; cipi db create --app= links a database to an app; the installer asks for the Git token; and the panel (4.2.0) gets a backup matrix, Node runtimes, dump upload and the last deploy of every app.
5.8.5 — cipi api ip-whitelist add|remove|set|allow-all replace the list by an atomic rename next to /etc/cipi/api-ip-whitelist (a temp under a tmpfs or private /tmp made mv remove the live file and copy) and, on a read-only /etc/cipi, say whether the kernel remounted the root or a sandboxed systemd unit started cipi — instead of the mv: inter-device move failed … Read-only file system the panel's IP tab showed; vault_write renames in place too; the public-IP hint runs only at a terminal. Panel cipi/gui 4.1.1: every button that calls the server shows a spinner while it waits, and a time zone per account. 5.8.4 — cipi deploy <app> --status [--json] says whether a deploy is running right now, whoever started it (Git push, CLI, panel, rollback), with phase, trigger and elapsed time; the panel (4.1.0) shows it live with its log; a failed post-deploy healthcheck says where the check comes from and how to turn it off; cipi yml example ships health: commented out.
5.8.3 — the panel API shows a job's result and output only to a token holding the ability the job was created under (cipi/api 1.36.1; before, any token could read any job by id, passwords included), and keeps the jobs that hold a password for a day. 5.8.2 — the installer accepts several SSH keys, shows what it will set up before the first package, prints the credentials in one layout and waits until you confirm they are saved, then offers the panel API and the GUI as two questions. cipi api <domain> and cipi gui <domain> check the DNS first, install and issue the certificate themselves (a token offered by cipi api). cipi credentials prints the summary again and cipi credentials export writes a CSV for any password manager. cipi gui sso brings single sign-on over OpenID Connect to the panel (cipi/gui 4.0.2). Also fixed: the GUI that never updated (composer reinstall) and a cipi yml plan that never reached "in sync".
5.8.1 — cipi deploy exited 1 after a successful deploy. Since 5.2.3 the success branch ended on [[ $post_rc -ne 0 ]] && return, false — status 1 — whenever the post-deploy steps passed or none were declared, and under set -e that 1 became the exit code of a command that had just printed ✓ Deploy completed. The release was live each time, but cipi/api marks a job by the exit code, so every deploy started from the GUI, the API, cipi-cli or an MCP tool showed as Failed with the success line quoted as the error. Webhook deploys were not affected. The branch now returns the post-deploy status itself, and cipi deploy prints the steps as they run and ends with ✓ Post-deploy: <summary> — before, those lines reached the notification mail only. No migration. Ecosystem: GUI 4.0.1 tells a deploy that published and then failed from a failed one (a warning with the post-deploy error or the exit code, and what to check) and names this bug for servers before 5.8.1.
5.8.0 — environments: cipi app create --env, per-environment cipi.yml, deploy.branch. Every app carries an environment label — cipi app create --env=staging (default production; lowercase letters, digits, -, _, max 32), cipi app edit --env, cipi app clone --env (default: the source's), shown by cipi app show — written to the app's .env as APP_ENV (Laravel) and CIPI_ENV (Laravel and Node), next to CIPI_DEPLOY_BRANCH. An app with environment <label> reads cipi-<label>.yml before cipi.yml, in every place it already looked, so one repository serves a staging app (cipi-staging.yml) and a production app (cipi.yml or cipi-production.yml); the file is chosen by the server, an invalid cipi-<label>.yml has no fallback, and cipi yml auto status, plan --json and auto --json report the env and the file. New deploy.branch in cipi.yml sets the deploy branch exactly like cipi app edit --branch (apps.json, deploy.php, CIPI_DEPLOY_BRANCH), from the next deploy — develop in cipi-staging.yml, main in cipi.yml; cipi yml generate emits it and names the file to commit. Nginx denies /cipi-<anything>.yml|yaml as well. Ecosystem: panel API 1.36.0 (MCP server 1.6.0) accepts and returns env; cipi-cli 1.9.0 (app create|edit --env, app show); PHP SDK 1.4.0 (Apps::create(['env' => …])); GUI 4.0.0 (Environment field on the app forms, the env on the cipi.yml tab); cipi/agent 2.1.0 (env in cipi:status, app_info, deploy_status, the webhook answer and the health report; reads cipi-<env>.yml first; validator knows deploy.branch); Cipi Studio 2.4.17 (env badge, env field on new/edit app, a starter named cipi-<env>.yml). Migration 5.8.0 adds CIPI_ENV=production to existing apps that lack it and updates the vhosts.
5.7.1 — security release for the PHP advisory of 2026-10-23 (CVE-2026-115560, no fixed release yet; mitigation session.upload_progress.enabled=0). FPM pools have carried it since 5.6.3; now Octane apps get it too: FrankenPHP loads /etc/php/cipi-octane.d/99-cipi-hardening.ini (upload progress and, on 8.5, fatal error backtraces off) through PHP_INI_SCAN_DIR in the Octane Supervisor program. Migration 5.7.1 rewrites the Octane programs and restarts them.
5.7.0 — cipi api move <domain> and cipi gui move <domain> move the panel API or the GUI to another domain: same app, tokens, admins and history; the vhost, api.json and APP_URL are rewritten, the old certificate is deleted and a new one issued. cipi api remove removes everything cipi api <domain> set up, leaving apps and the GUI alone. A panel's domain is its own: the API and the GUI refuse a domain or alias that belongs to an app or to the other panel, and app create, edit, aliases, clone, sync import and cipi.yml refuse the panel domains. cipi gui ssl exits 1 when certbot fails, and cipi gui remove keeps a certificate an app still uses. No migration.
5.6.4 — cipi yml auto <app> on applies cipi.yml on Git-webhook deploys too (the wrapper could not read /etc/sudoers.d and skipped the step); cipi yml plan --json and cipi yml auto status --json; cipi.yml from the panel API 1.35. Migration 5.6.4 installs the fixed deploy wrapper and rewrites the sudoers rules.
5.6.3 — security release for the PHP advisory of 2026-10-21 (CVE-2026-109618, CVE-2026-109619: unauthenticated RCE in PHP-FPM, FrankenPHP and every web SAPI; fixed in 8.5.12, 8.4.27, 8.3.36, 8.2.35). cipi php upgrade runs every night instead of every Sunday, reports each version as patched, VULNERABLE, distro or END OF LIFE, checks the PHP inside each Octane app's FrankenPHP binary, and exits 1 while a version is vulnerable; cipi php list --json adds patch, security and security_floor. Every FPM pool Cipi writes sets php_admin_flag[session.upload_progress.enabled] = off and, on PHP 8.5, php_admin_flag[fatal_error_backtraces] = off. PHP packages now come from packages.sury.org first (it had the fixed 24.04 builds while the ondrej PPA was still building them), then the PPA, then Ubuntu main. Migration 5.6.3 rewrites the pools, moves the cron to daily, moves existing servers from the PPA to sury.org, runs cipi php upgrade and restarts PHP-FPM.
5.6.2 — cipi db restore on PostgreSQL keeps the database intact when the restore fails: wipe and import run in one transaction, COMMIT only after the whole dump is read, empty archives refused, the new schema goes to the database owner. No migration.
5.6.1 — deploy.post artisan steps run: they all failed with /usr/bin/phpX.Yartisan: No such file or directory. A failed step reports its real exit code, and post_on_failure: abort fails the deploy. No migration.
5.6.0 — cipi app create opens with menus (app type, PHP-FPM or Octane, MariaDB or PostgreSQL; cipi db create asks the engine the same way) and asks for the asset build; the deploy key is tested against the repository on create, on app edit --repository|--branch and with cipi git check, with an offer to save or replace the forge token; named S3 destinations (cipi backup destination add) let one profile ship to several buckets. Fixed: a failed PostgreSQL restore was reported as done, a cipi.yml cron with a newline passed validation, lists lost their columns with long names. No migration.
5.5.2 — cipi disk is available to the panel API. Migration 5.5.2 regenerates /etc/sudoers.d/cipi-api so www-data may run cipi disk and cipi disk *. Panel API 1.33.0 then serves GET /api/disk and GET /api/disk/dbs (ability disk-view, MCP DiskUsage and DiskDatabases, 73 tools). cipi-cli disk (1.6.0) and the control panel Server → Disk tab (3.1) read them. API 1.32.0 already covered the soft disk limit (GET|PUT /api/apps/{name}/limits), Cloudflare DNS-01 accounts (/api/ssl/dns) and app type. Nothing cipi disk prints changes. The same release aligns cipi.yml with the server: deploy.node_build is the Laravel asset build before the release goes live, deploy.predeploy_snapshot is the pre-deploy snapshot (snapshot is still accepted), cipi yml generate --save writes /home/<app>/cipi.yml, backup profiles the file drops leave the schedule, and the deploy-success mail quotes the auto-apply result.
5.5.1 — wildcard certificates finally install: Cipi writes the HTTPS vhost itself and certbot only issues and renews (its nginx installer could not be driven non-interactively for a *. name), every tenant is redirected to HTTPS, Origin CA works on any app, a DNS-01 certificate is reissued over DNS-01, renewals reload nginx and no longer force HTTP-01, cipi ssl status shows per app the names its certificate does not cover, and cipi app list no longer shows PHP-FPM apps as Octane — guide: Wildcard domains & SSL.
In 5.5: 5.5.0 — cipi disk [--json] and cipi disk db; cipi app limits <app> --disk=<GB>|none with the new app_disk monitor check (trigger monitor_app_disk), stored as disk_limit_gb outside the limits that cipi.yml reconciles, so a repository cannot raise its own quota; cipi firewall attempts (1–100, default 3) in /etc/fail2ban/jail.d/cipi-attempts.local, checked with fail2ban-client -t and rolled back if refused; cipi ssh apps via the cipi-nossh group and one sshd -t-validated Match block; named Cloudflare accounts (cipi ssl dns set --name=, ssl install --account=, ssl dns list|remove). Fixed: Laravel logs were rotated twice and never expired — apps now use LOG_CHANNEL=single; tab-completion now works after sudo cipi without bash-completion, in sudo -s/su/tmux shells, and with app names for the cipi user; the installer names a container instead of reporting a wrong Ubuntu version. Migration 5.5.0 switches Laravel apps to single, folds dated logs into laravel.log, and gracefully restarts running workers, Horizon, Octane and Reverb and reloads PHP-FPM where the .env changed. cipi ssh apps and cipi firewall attempts stay on the host CLI. Disk usage reached the panel API in 1.33.0 (Cipi 5.5.2) and the soft limit in 1.32.0. Full changelog: CHANGELOG.md.
