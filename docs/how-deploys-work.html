How deploys work

Push to deploy with the agent, or deploy from your pipeline: how each works and which to pick.

Deploy

A Cipi deploy always runs on your server, as the app's own Linux user. The server pulls the code from Git, builds a new release next to the live one and switches to it in one step. Nothing is uploaded from your laptop or your CI, and no build artifacts travel over the network.

What changes from one setup to another is only who says "deploy now". There are two main ways to say it, plus a few manual ones:

Push to deploy (agent mode)Pipeline mode
In one sentenceEvery push to the deploy branch goes live by itselfYour CI decides when to deploy, usually after the tests pass
Who starts the deployYour Git provider, through a signed webhookA job in GitHub Actions, GitLab CI, Jenkins, AWS CodeDeploy…
What your app needsThe cipi/agent package (Laravel), or nothing for Node appsNothing
What CI needsNothingAn SSH key, or an API token with only deploy-manage
Tests before going liveNo: the push deploys anywayYes: the deploy job runs only if tests pass
Setup timeAbout 2 minutes10 to 30 minutes, once
ReadAuto-deploy on pushCI/CD pipelines, Jenkins, AWS CodeDeploy

Both modes end in the same place: the same pipeline, the same lock, the same audit ledger and the same notifications. You can switch from one to the other at any time without touching the server.

What every deploy does#

Step 1 of 6Trigger

Something asks for a deploy: a git push through the webhook, a CI job, cipi deploy on the server, the web panel, the REST API or an AI assistant through MCP. From here on, all of them take exactly the same path.

Step 2 of 6Lock

Cipi takes the app's deploy lock. If another deploy is already running, a push waits in the queue and deploys right after it, while a deploy asked by hand stops at once with a clear message: two deploys never write the same release.

Step 3 of 6Build release

A new folder under releases/ gets the code of the deploy branch, its Composer packages and, if you set a build command, its front-end assets. The live site is not touched yet: if anything fails here, nothing is published and the previous release keeps serving.

Step 4 of 6Migrate

Migrations run against the live database. If you turned on pre-deploy snapshots, Cipi takes one just before, as a restore point.

Step 5 of 6Swap

The current link moves to the new release in a single operation. Visitors go from the old code to the new one without a single failed request.

Step 6 of 6Verify

Workers and Horizon restart on the new code, the health check calls your app (if you set one) and the notification goes out. With automatic rollback on, an unhealthy release is replaced by the previous one within seconds.

Cipi always deploys the latest commit of the app's branch at the moment the release is built. A pipeline doesn't send a specific commit: it tells the server to pull the branch. Keep one deploy per branch at a time in your CI (every recipe in these docs shows how), so the commit your tests checked is the one that goes live.

Push to deploy: the agent mode#

The simplest setup, and the right one for most apps. You push, the app is live about a minute later.

Step 1 of 4git push

You push to the app's branch (main by default). Pushes to other branches are answered and ignored.

Step 2 of 4Webhook

GitHub, GitLab, Bitbucket, Gitea, Forgejo or Azure DevOps call https://your-app/cipi/webhook. The request is signed with a secret only your server and the provider know.

Step 3 of 4Agent checks it

In a Laravel app, the cipi/agent package checks the signature and the branch, writes a small trigger file and answers 200 immediately. It never runs the deploy inside a web request.

Step 4 of 4Server deploys

A cron job on the server finds the trigger and starts the normal deploy as the app user.

Why it is built this way:

  • No server access for anyone. The provider talks to your app over HTTPS, like any visitor. No SSH key leaves the server and no extra port opens.
  • Instant answer, safe deploy. The webhook returns in milliseconds, so providers never time out, and the deploy runs with the same rights as cipi deploy.
  • Set up for you. With a provider token saved (cipi git github-token …), Cipi creates the webhook and the secret when you create the app. See Git providers.

Node apps don't need the agent: Cipi installs a built-in receiver for them. Full details: Auto-deploy on push.

Pipeline mode#

Your CI runs the tests first and asks for a deploy only if they pass. The server still does the deploy itself: the pipeline only gives the order, in one of three ways.

Way to callHowGives CIBest for
SSHssh cipi@server "sudo cipi deploy shop"An SSH key that can run any cipi command as rootSimple setups, one server
API (cipi-cli or curl)cipi-cli deploy shopA token limited to deploy-manage: deploy, rollback, unlock, statusLeast privilege, no SSH, many servers
Agent webhookcurl -X POST https://shop.example.com/cipi/webhook -H "Authorization: Bearer …"The app's webhook secret: it can only queue a deployTools that can only send an HTTP request

The API and SSH wait for the deploy and return its result, so the pipeline turns red when the deploy fails. The webhook only queues the deploy and answers at once.

Recipes for every popular CI are in CI/CD pipelines: GitHub Actions, GitLab CI/CD, Bitbucket Pipelines, Azure Pipelines, Gitea and Forgejo Actions, CircleCI and Laravel Envoy. Jenkins and AWS CodeDeploy have their own pages.

One trigger per app. If the webhook and a pipeline both react to the same push, you get two deploys of it — or a red pipeline, when it asks while the webhook's deploy is running. When you move an app to pipeline mode, turn its webhook off in the Git provider (GitHub: Settings → Webhooks, untick Active).

ProblemCauseFix

Questions#

QuestionAnswer
Does CI upload my code to the server?No. The server always pulls from Git with its own read-only deploy key. CI only says when.
Can I deploy a specific commit or tag?Cipi deploys the tip of the app's branch. To ship a tag, point a release branch at it and deploy that branch.
What if two deploys start at once?The lock lets one run. A push that arrives meanwhile is queued and deploys after it; a deploy asked by hand stops with a message. cipi deploy shop --status shows what is running.
Does a failed deploy block the next push?No. The failed commit is paused so a retry doesn't build it again, but any new commit deploys.
Can I see who deployed?cipi deploy shop --audit lists every deploy with its origin (webhook, CLI, panel, API), the operator and the IP. See Deploy audit.
How do I go back?cipi deploy shop --rollback switches to the previous release in a second. Migrations are not undone.
Do I need the agent for pipeline mode?No. The agent is needed only for push to deploy in Laravel apps (and for its health, MCP and anonymizer endpoints).
