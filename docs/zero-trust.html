Cloudflare Zero Trust

Sites through a Cloudflare Tunnel, Access in front of what is private, and no inbound port left open.

Security

Put your server behind Cloudflare: visitors reach apps through a Cloudflare Tunnel (with CDN and WAF), staging sites, admin paths, the panel, the API, databases and SSH sit behind Cloudflare Access, and finally the origin closes its ports — all of them, if you like. Every step that could lock you out is a separate, explicit command. Off until you enable it.

Cloudflare publishes the sites to visitors. For the way in for you — SSH, the panel, the API on a private address — see Tailscale & NetBird: a mesh network sits beside the tunnel, and the two know each other's locks.

Step 1 of 5Token

Create a Cloudflare API token with Tunnel, Access and DNS permissions and save it with sudo cipi zt token set.

Step 2 of 5Enable

sudo cipi zt enable creates the tunnel and makes apps see visitors' real IPs. Ports stay open for now, so nothing can break yet.

Step 3 of 5Route

Route each hostname through the tunnel, add Access where you want a login wall — a whole site, some paths, some people — and SSH through Access.

Step 4 of 5Test

From your laptop, check every site and SSH through the tunnel. Don't skip this.

Step 5 of 5Lock

sudo cipi zt lock closes 80, 443 and 22 to the internet, or sudo cipi zt lockdown does all of it at once. Only the tunnel reaches the server now.

bash
sudo cipi zt token set --token=CF_API_TOKEN --account=ACCOUNT_ID
sudo cipi zt enable
sudo cipi zt hostname add myapp                  # public, through CDN/WAF
sudo cipi zt access enable staging               # login required (Cloudflare Access)
sudo cipi zt access enable myapp --path=/admin,/horizon --allow=@example.com
sudo cipi zt access enable --gui
sudo cipi zt ssh enable --hostname=ssh.example.com
sudo cipi zt lock http --yes                     # 80/443 closed or Cloudflare-only
sudo cipi zt lock ssh --yes                      # port 22 closed
sudo cipi zt lockdown                            # everything on the tunnel, no inbound port
sudo cipi zt status                              # --json for the whole picture
sudo cipi zt token show                          # is a token saved? (never the secret)
sudo cipi zt refresh                             # fetch Cloudflare's IP ranges again (done every night too)

Token permissions: Account · Cloudflare Tunnel: Edit, Account · Access: Apps and Policies: Edit, Zone · DNS: Edit (plus Zone · SSL and Certificates for Origin CA). For what you use: Account · Access: Service Tokens: Edit (service tokens), Account · Access: SSH Auditing: Edit (SSH certificates), Zone · Cache Purge: Purge (purges). A token without these keeps working; a command that needs more names the permission it misses. The token is stored root-only, separate from the DNS token used for certificates and from the Cloudflare token of the web panel's connector.

Access on some paths, for some people#

access enable alone asks anyone who signs in with your identity provider. Two options narrow it:

bash
sudo cipi zt access enable shop --path=/admin,/horizon,/pulse  # only these paths; the rest stays public
sudo cipi zt access enable shop --allow=me@example.com,@example.com # these emails and domains only
sudo cipi zt access enable --api --allow=none                  # service tokens only, no people
sudo cipi zt access enable shop --path=                        # back to the whole site
sudo cipi zt access enable shop --allow=all                    # back to anyone who signs in

--path= puts Filament, Horizon, Pulse or Telescope behind single sign-on and leaves the site public. Running access enable again updates the same Access application and keeps what you didn't pass. The /cipi/webhook Bypass is created only when Access covers that path. --gui and --api take the same options.

Service tokens#

Machines can't sign in with a browser. A service token is a pair of headers Access lets through:

bash
sudo cipi zt service-token create github-actions --for=shop  # or --for=gui, --for=api
sudo cipi zt service-token create panel --for=api --duration=8760h --json
sudo cipi zt service-token list
sudo cipi zt service-token revoke github-actions

Cipi creates the token and a Service Auth policy on the target's Access application, and prints CF-Access-Client-Id and CF-Access-Client-Secret once. Re-creating a target's Access application keeps its tokens' policies.

bash
curl -H "CF-Access-Client-Id: 3f2a….access" -H "CF-Access-Client-Secret: …" https://shop.example.com/health

For a server whose API is behind Access (sudo cipi zt access enable --api --allow=none), the web panel sends the token with every call: Connections → the server → Behind Cloudflare Access, with the id and the secret. The secret is stored encrypted, never shown again, and kept when the field is left empty.

Databases and Valkey from your laptop#

bash
sudo cipi zt tcp add mysql --hostname=db.example.com --allow=me@example.com
sudo cipi zt tcp add valkey --hostname=cache.example.com
sudo cipi zt tcp list
sudo cipi zt tcp remove db.example.com

mysql, mariadb, pgsql, redis, valkey or a port number: a hostname that reaches 127.0.0.1:<port> on the server, always behind Access — nothing is published if Access can't be created. The port stays closed. On your laptop:

bash
cloudflared access tcp --hostname db.example.com --url 127.0.0.1:13306

then TablePlus, DBeaver or mysql -h 127.0.0.1 -P 13306 on that address, with the database's own user and password.

SSH with short-lived certificates#

Instead of keys to hand out and take back, Cloudflare signs a certificate at every sign-in:

bash
sudo cipi zt ssh cert enable --principals=andrea,mario     # for the cipi user
sudo cipi zt ssh cert enable --user=deploy --principals=ci
sudo cipi zt ssh cert status
sudo cipi zt ssh cert disable

sshd trusts the CA of the SSH Access application (TrustedUserCAKeys) and accepts, for each Unix user, the principals listed for it (AuthorizedPrincipalsFile): the part of the email before the @ — andrea for andrea@example.com. sshd -t checks the drop-in before the reload; keys in authorized_keys keep working. sudo cipi zt ssh enable takes --allow= too. On your laptop, once:

bash
cloudflared access ssh-config --hostname ssh.example.com --short-lived-cert >> ~/.ssh/config
ssh cipi@ssh.example.com          # the browser asks you to sign in, no key needed

No inbound port: lockdown#

bash
sudo cipi zt lockdown       # asks first; --yes to skip, --force to accept an HTTP-01 renewal failing

Every app, the panel and the API go on the tunnel, then 80/443 close and, when SSH runs through the tunnel, port 22: the shape of a server behind NAT with no port forwarding. It stops at the first step that fails, and it still refuses to close port 80 while a certificate renews over HTTP-01 (see certificates). At the end it prints the inbound ports still open — none, if SSH was on the tunnel.

Previews of a branch#

bash
sudo cipi zt preview create shop --branch=feature/login     # behind Access
sudo cipi zt preview create shop --branch=feature/login --public --hostname=login.example.com
sudo cipi zt preview list
sudo cipi deploy shopfeaturelogin                           # update it
sudo cipi zt preview remove shopfeaturelogin

An app of its own — the same repository and PHP, its own database and .env, environment preview — on feature-login-shop.example.com, one level below the zone so Cloudflare's Universal certificate covers it, through the tunnel, behind Access (anyone who signs in, or the people of --allow=) unless --public, and deployed once (--no-deploy to skip). remove deletes the app, its database and its hostname. See also preview environments.

The same tunnel on more servers#

bash
sudo cipi zt replica export             # on the server with the tunnel: prints a bundle
sudo cipi zt replica join cipi-zt1:…    # on another server with the same apps
sudo cipi zt replica list               # connectors, and which one is this server
sudo cipi zt replica leave              # stop the connector here; tunnel, DNS and Access stay

The bundle holds the tunnel's credentials and routes: treat it as a password. Cloudflare then sends requests to either server. To move a server without touching DNS (the records point at the tunnel): join the new one, check it, replica leave on the old one. sudo cipi zt disable refuses on a replica, or while other servers run the tunnel (--delete-tunnel deletes it for everyone).

Cloudflare's cache#

bash
sudo cipi zt purge shop                # the app's hostnames
sudo cipi zt purge shop --everything   # the whole zone
sudo cipi zt purge shop --on-deploy=on  # after every successful deploy

Purge by hostname works on every Cloudflare plan. With --on-deploy=on, sudo cipi deploy and the webhook alike purge after a successful deploy, and the deploy notification says how it went.

The tunnel in the monitor#

With Zero Trust on, the monitor runs a tunnel check every 5 minutes: critical when cloudflared stops or Cloudflare sees the tunnel down or inactive, a warning when it is degraded (fewer connections: a network problem, or a replica down). Trigger monitor_tunnel, urgent, with recovery and reminders like every check. With 80/443 closed it is the one outage a server can still report: notifications go out, not through the tunnel. Outbound port 7844 (TCP and UDP) must stay open.

In the web panel#

The server's Zero Trust tab shows what sudo cipi zt status --json knows: the tunnel as Cloudflare sees it and every connector — which one is this server, the others its replicas — what is closed, each hostname with its domains, Access paths and people, service tokens, previews and the purge setting, the panel and the API, TCP services, SSH and its certificates, and what is not on the tunnel yet. Cloudflare's card is read-only: every change to the tunnel stays on sudo cipi zt. The API gives the same as details on GET /api/zt.

Under it, the Mesh network card is where a Tailscale or NetBird network is joined, locked and left from the browser.

The zones and DNS records of your Cloudflare accounts are in the panel's Cloudflare connector, with a token saved in the panel.

Certificates#

lock http refuses while an app still renews over HTTP (Let's Encrypt can't reach a closed origin). Move apps first to sudo cipi ssl install <app> --dns=cloudflare, or use a 15-year Cloudflare Origin CA certificate:

bash
sudo cipi zt origin-cert myapp

Apps on the tunnel skip Cipi's HTTP→HTTPS redirect automatically (the tunnel talks HTTP to the origin and Cloudflare handles HTTPS). sudo cipi zt disable reopens 22/80/443 and removes everything Cipi created in your Cloudflare account; Let's Encrypt certificates are left alone.
