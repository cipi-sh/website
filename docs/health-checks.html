Health checks

HTTP checks per app, including after every deploy.

Backups & monitoring

Two different questions, two checks: is the site up? and did the release I just shipped break it? Combined with automatic rollback, a bad deploy can undo itself within seconds.

Health checks
$ sudo cipi health set shop
$ sudo cipi health check shop
CheckRunsAlerts
Periodic probeEvery 5 minutesAfter 3 consecutive failures (health_fail)
Post-deploy checkRight after every release, CLI and webhook alikeImmediately (deploy_health_fail)
bash
sudo cipi health set myapp --url=https://myapp.com/up --expect=200
sudo cipi health check myapp
sudo cipi health list [--json]
sudo cipi health unset myapp

Laravel 11+ serves /up when health: '/up' is set in bootstrap/app.php. The URL must belong to the app's own domains.

After every deploy#

Step 1 of 5Release live

The deploy swapped current to the new release: it's serving traffic now.

Step 2 of 5Grace period

Cipi waits a moment (3 seconds, 8 for Octane, configurable with --grace) so caches and workers can warm up.

Step 3 of 5Probe up to 5×

It calls your health URL up to five times, so one slow first request doesn't count as a failure.

Step 4 of 5Verdict

The result goes into the deploy notification. A success message is only sent after a healthy verdict.

Step 5 of 5Optional rollback

With --rollback-on-unhealthy (or rollback_on_unhealthy: true in cipi.yml), an unhealthy release is replaced by the previous one within seconds.

bash
sudo cipi health set myapp --grace=15       # longer warm-up (max 120 s)
sudo cipi health set myapp --no-postdeploy  # keep the 5-minute probe only
sudo cipi health postdeploy myapp           # run the verification now

The success notification is sent after the verdict, so it never announces a release that returns errors. A failed verdict tells you where the check is configured and how to change it.

Automatic rollback#

bash
sudo cipi health set myapp --rollback-on-unhealthy  # always, for this app
sudo cipi deploy myapp --rollback-on-unhealthy  # this deploy only
Outcome reportedMeaning
RecoveredThe previous release answers healthy again
Rolled back, still unhealthyThe cause probably isn't the code (database, external service)
Rollback failedThe bad release is still live: act now
Nothing to roll back toFirst release

Off by default on purpose: migrations are not undone. Enable it for apps whose migrations are backwards-compatible, or pair it with pre-deploy snapshots.

Also in cipi.yml (health:), the REST API and the panel. To watch the server rather than the app, see Server monitor.

Uptime history#

The URL is also probed every minute by the metrics collector, which keeps the status and response time: uptime over 24 hours, 7 and 30 days, minutes down, incidents and uptime per day.

bash
sudo cipi metrics uptime myapp --range=30d

The alerts above don't change: the history only records. sudo cipi metrics probe off stops the per-minute probe.
