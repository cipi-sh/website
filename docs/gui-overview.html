Panel overview

What the panel does, with a tour of every screen.

Web panelEdit on GitHub

The optional web control panel#

Cipi is, and always will be, CLI-first. Everything a server needs — apps, databases, SSL, deploys, backups, firewall — is a single cipi command away over SSH. But from v4.7.0 Cipi also ships an optional web control panel: a self-hosted Laravel dashboard that manages one or more Cipi servers from the browser, over the same REST API the CLI client and WHMCS module use.

A working replica of the panel with demo data. The real screenshots follow below.

100% optional. The panel is a separate package you install only if you want it. Skip it and Cipi runs exactly as before — a lean CLI with no daemon, no web surface, and nothing extra listening. Install it and your team or clients get a friendly UI without giving up the terminal. Your server, your choice.

The panel is a thin visual layer on top of the API — it does not replace the CLI or add a proprietary control plane. Anything you do in the browser, you can still do from the terminal, and vice versa. A single panel can drive many servers, so it doubles as a lightweight multi-server cockpit.

What you can do from the panel#

  • Manage apps — create, edit, deploy, suspend/unsuspend, fix permissions and delete Laravel, Node (SPA / static / SSR) and custom apps; manage aliases, WWW/apex redirects, SSL (install + force HTTPS), and HTTP basic auth. Wildcard primary domains (*.example.com) are accepted. The create and edit forms have an Environment field (production, staging, … — panel 4.0, API 1.36 / Cipi 5.8.0+), the same label as cipi app create --env, and the app page shows it.
  • Create Node apps with a framework preset (Next.js, Nuxt, SvelteKit, Astro, Remix, Vite), Node major, build/start commands, output directory and health path; edit them later, restart SSR apps blue/green, and pin a Laravel app's asset build to its own Node major (API 1.31+ / Cipi 5.4.1+). See Node apps.
  • Routing — whole-app redirects (set, enable, disable, unset), path redirects and prefix reverse proxies, with the same validation as cipi redirect and cipi proxy (API 1.31+ / Cipi 5.4.1+).
  • Deploy — deploy, rollback and unlock; structured deploy.php options; and the app's deploy audit ledger — who or what deployed each release, from where (API 1.31+ / Cipi 5.4.0+). Since panel 4.1.0 (API 1.37.0 / Cipi 5.8.4+) a deploy in progress — started by a Git push, the command line, the panel or a rollback — is shown on the app page while it runs, with its trigger, branch, elapsed time and the live tail of the deploy log, listed first in the audit, and announced when it ends; every audit row opens its own deploy log.
  • cipi.yml — the app's tab shows the file of the live release, whether it is valid, what applying would change and what blocks it; apply it as a job, and turn auto-apply after every deploy on or off, with a confirmation that says who can then change the server (API 1.35+ / Cipi 5.6.4+). With panel 4.0 (API 1.36 / Cipi 5.8.0+) the tab also names the app's environment and the file in use — cipi-staging.yml for a staging app, cipi.yml otherwise. See cipi.yml and staging and production from one repository.
  • Search — Meilisearch status and per-app enable/disable for Laravel Scout (API 1.31+ / Cipi 5.2.2+).
  • Create Laravel apps with optional Laravel Octane (FrankenPHP) (API 1.13+ / Cipi 5.0+); list and detail views show FPM vs Octane.
  • Edit app .env, manage Composer auth.json, run Artisan, and execute whitelisted App commands (cipi app run) — requires API 1.14+ / Cipi 5.0.3+ (terminal output supports Markdown copy).
  • Pick a database engine at app create (mariadb or pgsql) and manage multi-engine databases — list, create, back up, restore, regenerate passwords (API 1.12+ / Cipi 4.8+). Deleting a database stays on the host CLI since API 1.19.
  • Browse application and server logs with type filter, pagination, and auto-refresh.
  • Watch async jobs in an interactive overlay (spinner + terminal output while polling GET /api/jobs/{id}).
  • A time zone per account (panel 4.1.1, Settings → Profile, UTC until chosen, with a Use my browser's shortcut): the deploy in progress, the deploy audit and the dashboard clock all follow it, and say which zone they are in. Every button that calls the server shows a spinner while it waits.
  • Live dashboard — CPU, memory, disk, services, and app count via GET /api/status.
  • Server cockpit (API 1.15+ / Cipi 5.0.6+) — install PHP versions, manage SSH keys, services, SMTP notifications, HTTP healthchecks, and panel API IP whitelist from the browser. The versions offered are the ones the server lists: PHP 8.6 appears on a server with Cipi 5.9.1 and API 1.39.2, with no panel update. Legacy versions a server still has (7.4–8.2) are listed with a legacy badge; an app that runs on one keeps it in its configuration form, and no other app is offered it. Since API 1.31 the same page shows Node runtimes, Meilisearch, the optional host packages catalog, the system monitor and Cloudflare Zero Trust status — read-only by design: installing software, changing monitor thresholds and every zt change stay with the operator on the CLI. Since API 1.33 (panel 3.1, Cipi 5.5.2+) the same page has a Disk tab: who is filling the disk, the figures of cipi disk and cipi disk db.
  • Register multiple servers under one login. In the default fleet view (panel 4.0) Apps and Databases list every server in one place, with a server column and filter, and the sidebar has one entry per server; admins can switch the panel back to one server at a time, picked from the header. App links carry the server so they can be bookmarked and shared.
  • Roles (panel 4.0): admins see and do everything; users get what an admin grants — View or Manage on whole servers, and View, Deploy, Edit, Environment, Logs, Commands or Delete on single apps. People are invited with a copyable link that carries the role and the grants; nothing is emailed.
  • Deploy in progress (panel 4.1.0, API 1.37.0, Cipi 5.8.4+): the app page polls cipi deploy <app> --status and shows a deploy it did not start — a Git push through the webhook, the command line, another panel, a rollback — as a banner with the trigger, the branch, the phase (Deployer building the release, then post-deploy steps, cipi.yml and healthcheck), a ticking elapsed time and the live log tail; Deploy and Roll back are held while it runs; when it ends a toast gives the result and the page, the audit and the logs reload. A push waiting for the per-minute cron shows as queued, a run that died shows as interrupted with the Unlock action. Each audit row has a Log button that opens that deploy's own slice of the deploy log, post-deploy verdict included. The app header links to the app's server, and the healthcheck card says the check also runs after every deploy. On an older server the panel simply shows none of this.
  • Deploy times (panel 4.0, Cipi 5.6+): the deploy audit shows how long each deploy took and the Deploy card the last and average time, read from the deploy log's end banners. Dialogs with a form keep what was typed, and IPs copy on click.
  • One-time credentials (SSH and database passwords, deploy key, webhook URL and token) are listed with copy buttons when a job returns them, instead of being buried in CLI output.
  • Single sign-on (panel 4.0.2, Cipi 5.8.2): sign in through Microsoft Entra ID, Google Workspace, Okta or any OpenID Connect provider, configured from the server with cipi gui sso; accounts matched by email, optional auto-created accounts per domain, an SSO-only mode with the break-glass on the CLI.
  • Repository check and build at creation (panel 3.2, API 1.34, Cipi 5.6.0+): creating a Laravel app takes an optional build command (npm ci && npm run build) that runs on every deploy before the release goes live, and the job overlay says whether the deploy key can read the repository — after a create, or an edit that changed the repository or branch. When it cannot, it shows git's error and the command to run on the server, with a copy button: the API cannot save Git tokens, so that step stays on SSH.
  • A deploy that published and then failed (panel 4.0.1) is told apart from a failed deploy: when the job output says the release went live (Successfully deployed!) and the command still exited non-zero, the overlay shows a warning with the post-deploy error or the exit code and what to check — the release is live, nothing was rolled back — instead of "The job failed" with the Git-key hints. Cipi before 5.8.1 exited 1 after every successful deploy started through the API, which is why every panel deploy looked failed; the overlay names it, and cipi self-update on the server clears it.
  • The last deploy in the app list (panel 4.2.0, API 1.39.0 / Cipi 5.9.0+) — when each app was last deployed and how it went (OK, failed, a rollback), with release, duration and who started it in the tooltip. It is asked after the list is on the page, of every server at once. The database column counts the databases linked to the app.
  • Deploy durations that stay (same versions). The Deploy tab took them from deploy.log, which the server rotates every night: a deploy kept its time until the first rotation, and one started by a Git push — looked at the day after — never showed any. They come from the server's deploy history now, rotated logs included.
  • Backups — Server → Backups (panel 4.2.0, API 1.39.0 / Cipi 5.9.0+): a matrix of every app and every database against the backup profiles. A column per profile says what it takes, how often, where it sends it, how long it keeps it and how its last run went (OK, failed, overdue, running); a mark says which apps and databases it covers, and a row no enabled profile covers is flagged. Create, edit, pause, run now (on the server, in the background), verify and delete profiles; test the destinations; list the stored runs. Buckets are added on the server (cipi backup destination add): their secret key does not go through the panel. Since panel 4.2.1 the tab never guesses: Backups are not configured is shown only when the server answers so — with the host that answered and the file it looked for (/etc/cipi/backup.json) — and a status that could not be read is shown as an error, with what the server answered and Try again. To read on the server exactly what the panel reads: sudo -u www-data sudo -n /usr/local/bin/cipi backup status --json.
  • Node runtimes — Server → Node (panel 4.2.0, API 1.39.0 / Cipi 5.9.0+): install a major, upgrade to the latest patch (the SSR apps move to the new binary blue/green, without downtime), choose the server default, remove one nothing uses.
  • Databases that belong to apps, and dumps from your computer (panel 4.2.0, API 1.39.0 / Cipi 5.9.0+). The Databases page shows the app of each database and links or unlinks one from its row; Create database takes an app. Restore accepts a .sql or .sql.gz from your computer as well as a file on the server: the browser cuts it into chunks and the panel hands each one on — it keeps nothing, so a dump of any size passes through request limits that were never meant for it — up to the size the server allows (2 GB by default), with a progress bar and a Stop.
  • Saved commands (panel 4.2.0) — the one-click commands above the Artisan and Commands inputs are a list the panel's admins edit from the tab: add the ones the team runs, remove the ones it never does — the defaults included — or go back to the defaults. One list for every app and everyone.
  • A confirmation dialog of the panel's own (panel 4.2.0) in place of the browser's: the question, what it will do, the action's own word on the button — red, and not focused, when it destroys something.
  • Pages before answers (panel 4.2.0) — Server and the log viewer are shown at once and load their data after, like Dashboard, Apps and Databases; what a page still needs first is asked in one round instead of one request after the other. Nothing a server says is cached between requests: a panel that shows a worker or a backup that is no longer there is worse than one that takes a moment.
  • What a user may do is asked at every request (panel 4.2.0, a security fix): the abilities on an app, the app, the server and the job a page works on can no longer be changed from the browser — a user with View on one app could act on another app of the same server. Update the panel: cipi gui update.
  • Light and dark themes, a phone layout, and per-section fallbacks: a server whose API is older or whose token is narrower still works for everything it supports.

Panel 3.0 (October 2026) redesigned every page around the same design system as this site. Panel 3.1 adds Server → Disk; 4.0 roles with invite links, the fleet view, deploy times, the Environment field and the environment on the cipi.yml tab; 4.1.0 a deploy in progress — whoever started it — on the app page with its live log, a log per audit row, a link to the app's server; 4.1.1 every button that calls the server ignores further clicks and shows a spinner until the answer arrives, and a time zone per account (UTC until chosen) that every time in the panel follows (API 1.37.0 / Cipi 5.8.4); 4.0.2 single sign-on over OpenID Connect, a header and lists that follow every change without a reload, and jobs run in the background that still report back; 4.2.0 backups as a matrix, Node runtimes, the last deploy of every app, dump upload, databases linked to apps, saved commands, the panel's own confirmation dialog, and a security fix; 4.2.1 a Backups tab that says "not configured" only when the server does, the server's own reason under every "Not available on this server", the API version each server runs next to its Cipi version (API 1.39.1), and "Cipi" instead of the host app's name in the browser tab. See the screenshot tour and the changelog.

Screenshot tour#

Every image below is a real screenshot of the panel, taken against its demo environment — a stand-in for the panel API with three fictional servers that ships with the package (./dev/demo.sh; --reset picks up the API 1.33 disk fixtures). Domains and IPs are documentation ranges.

Apps#

Laravel (PHP-FPM or Octane), Node (SPA, static, SSR) and custom PHP apps of every connected server in one list — a server column and filter, type filters, search and a deploy button on every row. The Dashboard and Server pages open the list narrowed to one server; a user sees only the apps granted to them.

Creating an app starts with its type. Node framework presets (Next.js, Nuxt, SvelteKit, Astro, Remix, Vite) fill the mode and show the same defaults cipi app create --node uses.

App detail#

A header with status, type, runtime and quick actions, then one tab per area. Tabs are part of the URL, so ?tab=deploy can be bookmarked.

Jobs#

Deploys, SSL, app and database operations run as async jobs on the server. The overlay polls GET /api/jobs/{id}, shows the elapsed time and colour-codes the CLI output; closing it leaves the job running.

Team and roles#

Admins see and do everything. A user gets what an admin grants — View or Manage on whole servers, and View, Deploy, Edit, Environment, Logs, Commands or Delete on single apps — and is invited with a copyable link that carries that access. Nothing is emailed; a link works once and expires after seven days.
