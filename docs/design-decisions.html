Design decisions

Why no Docker, why MariaDB, PostgreSQL, Valkey, Laravel — and why not local.

About

Why not local?#

Cipi is a production server provisioner: it turns a fresh Ubuntu VPS into an internet-facing host. It doesn't run on a laptop, in local Docker, or behind a home NAT, by design.

A Cipi server needsBecause
A public IPv4 address, no NATDomains must resolve to it and Git providers must reach its webhooks
Full virtualization or bare metal (KVM, VMware, Hyper-V, Xen HVM)Shared-kernel containers (OpenVZ, LXC) can't run the services and firewall Cipi manages; the installer detects them and stops
Ports 22, 80 and 443 reachableSSH, Let's Encrypt validation and HTTPS

Don't install Cipi inside Docker Desktop, OrbStack, Colima, WSL or a local VM expecting a working stack: certificates won't issue, domains won't resolve and webhooks can't arrive. A small VPS is enough for staging.

Every production provisioner has the same constraint. What Cipi doesn't ask for is the difference: no agent phoning home, no external control plane, no cloud account.

Locally, use Laravel Herd, Sail or php artisan serve, then push to a Cipi server for staging and production.

Why no Docker?#

Cipi installs Nginx, PHP-FPM, MariaDB or PostgreSQL, Valkey and Supervisor as native Ubuntu packages, managed by systemd, and seals apps off from each other with Linux users. There are no containers, no images and no Docker daemon on a Cipi server. That's deliberate: for one server running Laravel and PHP apps, Docker adds a layer that has to be secured, patched and debugged, without giving anything the OS doesn't already provide.

With DockerOn a Cipi server
Ease of useA second system to learn on top of Linux: images, Compose files, networks, volumes, registries. Every task goes through Docker firstOne command per task (cipi app create, cipi deploy, cipi ssl install). Underneath, a plain Ubuntu server: nothing to translate
An extra layerDocker sits between you and every component: to change a php.ini or an Nginx rule you edit an image or a mount, then recreateThe component is the one on the host: /etc/nginx, /etc/php, managed by Cipi and visible to you
SSH and SFTPSSH lands on the host, not in the app: then docker exec into a container that usually has no SSH, no editor and no SFTPssh myapp@server drops you into the app as its own user, with artisan, composer, logs and SFTP for your IDE
Remote databasesThe database lives on a container network. To reach it from TablePlus or DBeaver you publish its port (bypassing the firewall, see below) or chain an SSH tunnel into the container networkNative MariaDB or PostgreSQL on localhost: connect over SSH with the mariadb+ssh:// URL shown at creation. No database port is ever exposed
Ports and firewallPublished ports (-p 3306:3306) are opened by Docker's own iptables rules, ahead of UFW: a firewall that says "deny" doesn't apply to themOne firewall. UFW, Fail2ban, CrowdSec and cipi zt lock see and govern every port
Security patchesA CVE in PHP or OpenSSL means rebuilding every image that contains it and redeploying every app. Images pinned months ago keep old librariesPHP patched every night at 03:30 from packages.sury.org, Nginx from nginx.org, the rest by unattended-upgrades. One update fixes every app
Privilegesdockerd runs as root, and anyone in the docker group is root in practiceNo daemon with root access to manage. Apps run as their own unprivileged users
IsolationContainers share the host kernel; a misconfigured mount or a privileged container breaks the boundaryPer-app Linux user (home 750), PHP-FPM pool with open_basedir, database user and Valkey instance
Restarts and reloadsA config change usually means recreating the container. Restarting or upgrading dockerd stops every container, unless live-restore is configuredsystemctl reload: Nginx and PHP-FPM pick up changes without dropping connections. Nightly patching restarts only the affected PHP-FPM service
WorkersRestart policies only know "the process exited"Supervisor restarts workers, Horizon, Reverb and Octane individually, with logs per program
Native componentsBridge networks, NAT, docker-proxy and an overlay filesystem between the request and PHPUnix sockets between Nginx, PHP-FPM, the database and Valkey. Nothing in between
ResourcesThe daemon plus a runtime and a copy of the userland per container; heavy on a 1–2 GB VPSOne shared runtime. Cipi sizes MariaDB's buffer pool from the server's RAM
DataDatabases on volumes; one docker compose down -v deletes themData in the standard directories, backed up by cipi backup, encrypted and verified
DeploysBuild an image, push it to a registry, pull it, swap containers behind a proxygit push: Deployer builds a release and swaps a symlink atomically, with one-command rollback
Debuggingdocker exec into a minimal image, with logs per containersystemctl, journalctl, /var/log, strace: the tools and tutorials every sysadmin already knows

The firewall point is the one that bites. Docker writes its own iptables rules for published ports, and they're evaluated before UFW. A database container published on 3306 is reachable from the internet even with ufw deny 3306. Docker's own documentation calls Docker and UFW incompatible. On a Cipi server, what the firewall says is what's open.

What you don't lose. The things people use Docker for on a server are already there: per-app isolation, one version of PHP per app (8.3 to 8.6 side by side), a database per app, reproducible settings in cipi.yml committed to the repository, and zero-downtime deploys with rollback.

When Docker is the better fit. Many stacks on one host (Go, Python, Rails next to PHP), images built once in CI and shipped unchanged, or a team that already thinks in containers. Then a Docker PaaS such as Coolify or Dokku suits you better: see the comparison. Locally, Docker is great: Sail or init on your laptop, Cipi on the server. Cipi itself doesn't install inside a container: the installer detects Docker, LXC, OpenVZ or WSL and stops.

Why MariaDB by default?#

MariaDB (port 3306) is the default because it fits most Laravel apps with zero friction. PostgreSQL is one command away and can run next to it.

ReasonDetail
Drop-in for Laravelmysql driver, same DB_* keys, same migrations; works with TablePlus, DBeaver, Sequel Ace
Built for web concurrencyStrong optimizer and a native thread pool in the community edition, good with PHP-FPM connection churn
Tuned to your VPSCipi sizes innodb_buffer_pool_size from RAM (256 MB on 1 GB hosts up to 4 GB on 16 GB+)
Simple licensingGPL community server, no enterprise feature gates, no Oracle dual-licensing to navigate
Native packagingInstalled from MariaDB.org or Ubuntu; Cipi adds users, backups and vault credentials on top

Why PostgreSQL as an option?#

bash
cipi db install pgsql                       # port 5432, side by side with MariaDB
cipi app create shop --engine=pgsql

Choose PostgreSQL per app when the product needs more than tables:

NeedPostgreSQL gives you
Rich dataJSONB, arrays, ranges, UUID, full-text search, CHECK and exclusion constraints
IndexingB-tree, GIN, GiST, BRIN, partial and expression indexes
Extensionspgcrypto, pg_trgm, PostGIS, pgvector for embeddings and RAG
ConcurrencyMVCC: readers don't block writers; long reports and busy writes coexist
PortabilityThe standard of managed databases, BI tools and data pipelines

The same cipi db workflow covers both engines: create, list, backup, restore, password rotation.

Why Valkey?#

ReasonDetail
Drop-inSame protocol on 6379, same phpredis, same REDIS_* keys; Laravel doesn't notice
Truly open sourceBSD-licensed, stewarded by the Linux Foundation after Redis moved to source-available licences
Native on Ubuntuvalkey-server from the Universe repository, no third-party PPAs
Automatic migrationServers moved from Redis to Valkey on cipi self-update, same password and data

Why Laravel first?#

Knowing the framework lets Cipi automate what generic panels leave to you: the release layout, .env handling, queue workers, the scheduler, Horizon, Reverb, Octane, health routes. Every assumption maps to a known structure, so there's no guesswork. Anything that isn't Laravel still runs as a custom app (WordPress, Symfony, static sites) or a Node app.

Laravel bringsCipi turns it into
Queues and HorizonSupervisor workers, cipi worker horizon enable
ReverbSupervisor process, Nginx /app proxy, REVERB_* keys: cipi app reverb enable
OctaneFrankenPHP apps side by side with FPM: cipi app create --octane
SchedulerOne cron per app, nothing to configure
ScoutMeilisearch on the server: cipi search
Secure defaults and a long support cycleApps you can leave in production for years

Taylor Otwell's mantra is "we must ship". Cipi exists for the same reason: to remove the server work between a developer and a live application.

Why "ci-pi"?#

Cipi is the Italian reading of the letters C and P: Control Panel. A nod to the project's Italian roots, and to what it does under the hood: manage Nginx, PHP-FPM, databases, Supervisor, certificates and the firewall for you.

The mascot is a penguin, a reference to Tux, the Linux mascot drawn by Larry Ewing in 1996. Same species, different attitude: minimal, hand-sketched, happier in the terminal than in the spotlight.
