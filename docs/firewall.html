Firewall & bans

UFW rules, blocked addresses and Fail2ban bans, from the CLI or the panel.

Security

UFW allows only SSH, HTTP and HTTPS; everything else is closed. Fail2ban bans addresses that keep failing SSH logins, longer each time. The web panel shows all of it, CrowdSec included, and changes what is safe to change from a browser.

Firewall
$ cipi firewall status
$ cipi firewall allow 3306 --from=10.0.0.5
$ cipi firewall block 198.51.100.0/24
$ cipi firewall deny 22

Ports#

bash
cipi firewall status [--json]                    # UFW, fail2ban and CrowdSec at a glance
cipi firewall list [--json]
cipi firewall allow 3306 --from=10.0.0.5         # one address
cipi firewall allow 3306 --from=10.0.0.0/24      # a private subnet
cipi firewall allow 8000:8100 --proto=udp        # a range, UDP
cipi firewall remove 3306 --from=10.0.0.5        # drop what allow made
cipi firewall deny 8080                          # ahead of every allow
cipi firewall attempts [5|default]               # failed logins before a ban
ProtectionDefault
Open ports22, 80, 443
Failed SSH logins before a ban3 (counted over 1 hour)
Ban24 hours, doubling on each repeat, up to 7 days
Repeat offenders (recidive)3 bans in 24 h → 7 days

The threshold is written to a drop-in that updates never reset, validated with fail2ban-client -t before reload (a rejected value changes nothing). Need a database port? Open it to specific addresses only, or better, connect over SSH with the mariadb+ssh:// URL.

To close a port you opened, remove it: the rule goes and the port is closed again by the default policy. deny is for refusing what an allow would let in (a port to one address, say). It goes ahead of every allow (ufw prepend): UFW stops at the first rule that matches, so a deny placed after an allow of the same port would change nothing.

Zero Trust closes what UFW keeps open: behind Cloudflare, cipi zt can close 80/443 to everyone but Cloudflare and close 22 entirely; on a Tailscale or NetBird network, cipi zt tailscale|netbird lock leaves 22 and 80/443 open on the mesh only.

Blocked addresses#

bash
cipi firewall block 198.51.100.23        # every port refused to it
cipi firewall block 198.51.100.0/24      # a range
cipi firewall unblock 198.51.100.23

A block refuses every port to an address or a range, ahead of every allow, until you unblock it: a scanner, an abuser, a range that keeps knocking. Unlike a ban it never expires. Ranges wider than /8 (IPv4) or /16 (IPv6) are refused.

What stays open#

The firewall commands refuse what would cut the server off:

RefusedWhy
deny of the SSH port, 80 or 443 to everyone; remove of the rule that opens themThey are how the server is reached. The SSH ports are read from sshd -T, so a custom port counts. One address can still be denied with --from=
block of a range that takes in the address of your SSH sessionYou would cut yourself off. The same holds for deny --from= on the SSH port
allow to everyone of what a Zero Trust lock keeps closedcipi zt lock http keeps 80/443 to Cloudflare, cipi zt lock ssh keeps SSH closed, and a mesh network's lock keeps a port to the mesh: the message names who holds it and which command reopens it. cipi firewall status says it too

--force gets past these at the server's shell, when you know why. From the panel it is ignored, whatever the panel sends.

Every change is written to cipi.log, and says when the rule was already there, when it did not exist, or when UFW is inactive.

Bans#

bash
cipi ban list                   # banned IPs, by jail (Fail2ban and CrowdSec)
cipi ban unban 203.0.113.42     # from every jail at once
cipi ban unban 203.0.113.0/24   # a CrowdSec range decision

The address is matched whole (unban 1.2.3.4 never lifts a ban on 11.2.3.45), and ban unban takes nothing but an address or a CIDR. Locked out a colleague or a CI runner by mistake? Unban from another session, the provider's console or the panel. For CI, use a dedicated key (key logins don't fail).

From the panel#

The server page of the web panel has a Firewall tab (over the API):

SectionWhat it shows and does
At a glanceUFW and its default policy, the ports always kept open, fail2ban and its threshold, CrowdSec, how many addresses are banned; the Zero Trust locks, when there are — who holds each (Cloudflare, the Tailscale or NetBird network), with a link to the Zero Trust tab for the ones reopened there
RulesUFW's rules in its order (port or range, protocol, action, source, IPv4/IPv6), Kept open on SSH, 80 and 443, the Cipi feature that owns a rule (Zero Trust, Metrics, CrowdSec rescue); Remove on what may be removed; Open a port or a range, TCP or UDP, to everyone or to one address or range
Blocked addressesBlocks: Block, Unblock
Banned nowFail2ban's jails and CrowdSec's decisions in one list, an address once; Unban lifts every ban on it
SSH login attemptsThe threshold, back to the default, and a warning when fail2ban still runs an older value or isn't running
CrowdSecEnable (a job of a few minutes; what would stop it is said before trying), bouncer and rescue listener, the addresses it never bans, disable
Cloudflare real IPThe visitor's address behind Cloudflare: on, the ranges fetched again, off — what Fail2ban and CrowdSec ban depends on it

Reading needs a level on the server, changing needs Manage. The panel takes only what the page lists, and the server refuses what keeps it reachable whatever is sent: the Firewall tab can't close SSH, 80 or 443, undo a Zero Trust lock or block the panel's own address. Closing those three ports to the world is Zero Trust's job: the mesh network's locks have their own buttons in the Zero Trust tab, with their own guards. It doesn't deny ports either (it opens ports and blocks addresses), and the CrowdSec rescue stays at the server.

The server's API token needs firewall-view and firewall-manage (a --full-access token has them). On an older server the tab says what to update: cipi self-update, then cipi api update.

Questions#

QuestionAnswer
I locked myself out.Use the provider's web console to log in, then cipi ban unban <your IP> (or Unban in the panel, from another network). Key logins never count as failures, only passwords.
Should I open the database port?Avoid it. Connect over SSH (TablePlus, DBeaver support it). If you must, allow one address with --from.
How do I close a port I opened?cipi firewall remove <port> with the same --from and --proto you opened it with, or Remove in the panel.
Deny, block or ban?deny refuses a port; block refuses every port to an address until you unblock it; a ban is Fail2ban's or CrowdSec's, and expires.
Does the provider's firewall conflict?No. Keep 22, 80 and 443 open in both.
