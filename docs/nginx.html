Nginx

The default server and editing an app's Nginx config.

Domains & SSLEdit on GitHub

cipi nginx default-server#

Available since v5.1.0. Claims whichever of :80 / :443 has no default server and closes unmatched requests with an empty reply (444).

bash
cipi nginx default-server status
cipi nginx default-server on
cipi nginx default-server off

Cipi always had a default server on :80, but never on :443. An HTTPS request carrying an unknown Host therefore fell through to whichever vhost Nginx had loaded first — for a wildcard multi-tenant app, straight into a tenant resolver that cannot parse it.

It is enabled on fresh installs, and migration 5.1.0 claims it on existing servers where nothing else already does. If another vhost legitimately owns the default server, the command says so and changes nothing.

cipi nginx upgrade (v5.2.3+)#

Nginx is on the unattended-upgrades blacklist, so patches are applied when you ask for them: cipi nginx upgrade [--yes] runs apt --only-upgrade over the installed nginx* packages, keeps your nginx.conf, checks the config with nginx -t and reloads. Since v5.9.0 the nightly cipi autoupdate runs the same code. Details in manual stack upgrades.

cipi nginx security and nginx 1.31.9 (v5.9.1+)#

nginx 1.31.9 (18 November 2026) is a security release with ten CVEs. Cipi 5.9.1 brings every server to it; cipi self-update is all it takes. What applies to a Cipi server:

  • CVE-2026-118899 — an endless loop while reading a request body over TLS 1.3: one request keeps a worker at 100% CPU. Any HTTPS vhost, so every server.
  • CVE-2026-125283 — a buffer overflow with try_files under an alias. The panel API vhost had exactly that for /api-docs; 5.9.1 serves it without the alias, which did nothing, and the migration removes the line from an installed vhost.
  • CVE-2026-123007 and CVE-2026-123633 — memory corruption in the HTTP/2 code. Cipi 4 and 5 write listen 443 ssl;, never http2 on;, and nginx has HTTP/2 off by default since 1.25.1, so a server as Cipi sets it up cannot be reached by either. They apply where HTTP/2 was turned on by hand, on a vhost written by Cipi 3, or by an older version of the preview environments workflow on this site, which added listen 443 ssl http2;.
  • The other six are in parts Cipi does not use: the resolver, HTTP/3, mail, stream and the PROXY protocol v2.
bash
cipi nginx security        # patch level, the binary that is running, where HTTP/2 is on

It prints the installed version against the oldest one that carries every fix Cipi knows about (1.31.9), whether the nginx that answers requests is the one on disk, and every configuration file that turns HTTP/2 on. It only reports; cipi pending carries the first two as items (below 1.31.9, the archive's build, an old binary still running).

Which nginx a server runs. Since 4.5.9 Cipi runs nginx from nginx.org's mainline repository. Between 4.6.5 and 5.9.0 (10 June – 19 November 2026) the installer did not: a server installed in that period runs the Ubuntu archive's nginx (1.24.0 on 24.04), without max_headers, and — nginx being on the unattended-upgrades blacklist — got security updates from nobody. dpkg-query -W nginx tells: a version like 1.24.0-2ubuntu7.x is the archive's, 1.31.9-1~noble is nginx.org's. Migration 5.9.1 moves such a server to nginx.org mainline:

  • one apt transaction — nginx.org's nginx in, libnginx-mod-http-headers-more-filter out — simulated first: if apt cannot do all of it, nothing is removed and nginx stays as it is, with a warning;
  • refused before anything is touched when the installed nginx already fails nginx -t, or when a file other than nginx.conf uses a headers-more directive (more_set_headers and the like), which nginx.org's build does not have. The warning names the files; remove the directives and run cipi nginx upgrade;
  • nginx.conf is adapted in place and keeps the rest of what is in it: the modules-enabled include and more_clear_headers go, max_headers 1000; comes in. The previous file stays next to it as nginx.conf.cipi-<timestamp>.bak. Only if nginx refuses the adapted file is it replaced by Cipi's own.

cipi nginx upgrade and the nightly run do the same on such a server, asking first when run by hand.

The binary that answers is the one just installed. The nginx.org package asks the running master to start the new binary, and exits 0 when that fails; when it works, old workers stay for as long as one of their connections is open — hours, with a WebSocket. After an upgrade Cipi waits a few seconds and looks at every nginx process: if one still runs the replaced binary, nginx is restarted instead of reloaded (connections drop for well under a second).

After cipi self-update to 5.9.1, run cipi nginx security once. The move from the Ubuntu archive's packages to nginx.org's was tested against simulated package managers, not on every combination of a real server: if the migration printed a warning, this command says what is left to do.

Edit Nginx config#

To customise the Nginx vhost for an app, edit the site config directly. After changes, test and reload Nginx.

bash
sudo nano /etc/nginx/sites-available/<app>
sudo nginx -t && sudo systemctl reload nginx
