Backups to S3 & SFTP

Scheduled database and storage backups to any S3-compatible bucket or SFTP server, such as a Hetzner Storage Box.

Backups & monitoring

Backups that run on their own, go where you want, are encrypted before they leave the server, and tell you when they stop. Built on profiles: each one answers what, how often, where and how long.

Backups to S3
$ sudo cipi backup configure
$ sudo cipi backup profile add nightly --scope=all --cron='0 2 * * *' --keep-days=14 --dest=s3
$ sudo cipi backup run --profile=nightly
Step 1 of 6Profile runs

Each backup profile has its own schedule (--every=30m, --cron='0 2 * * *'…). When it's due, the run starts on its own.

Step 2 of 6Dump + archive

Each database is dumped and each app's files are archived separately, so you can restore one app without touching the others.

Step 3 of 6Integrity check

Every archive is opened and checked before upload. A broken archive is reported, not shipped as if it were fine.

Step 4 of 6Encrypt

With --encrypt, archives are encrypted with AES-256 on the server before leaving it. The bucket only ever sees encrypted files. Keep the key from sudo cipi backup key show.

Step 5 of 6Upload

The archive goes to each destination of the profile: the server's disk, an S3 bucket, an SFTP server (a VPS, a Hetzner Storage Box), or several of them.

Step 6 of 6Prune & watch

Old runs beyond --keep/--keep-days are deleted. If a profile stops producing backups, you get a staleness alert.

1. Set up: on the server first#

Backups start on the server: sudo cipi backup configure sets up the local folder and a nightly profile, default, that takes every app and every database and keeps them there. At a terminal it then offers to send them elsewhere too — an S3 bucket and/or an SFTP server, as many as you want — and sends the nightly profile there as well:

bash
sudo cipi backup configure
  Local backup directory [/var/backups/cipi]:
  Temp directory [/var/tmp]:
✓ Backups set up on this server: /var/backups/cipi

  A copy only on this server is lost with the server.
  Send the backups somewhere else too?
    1) none       No — only on this server, for now (default)
    2) s3         An S3 bucket — AWS, Hetzner, Cloudflare R2, DigitalOcean, Backblaze, Scaleway, MinIO…
    3) sftp       An SFTP server — a VPS with a backup user, a Hetzner Storage Box, a NAS

Without a terminal (a script, the panel) it asks nothing: the server is set up with the defaults, and destinations are added next. --local-dir= and --tmpdir= move the local folder and the folder archives are built in, at the server's shell only. Running it again changes the folders and nothing else.

2. Destinations: S3 buckets and SFTP servers, on a par#

local (this server) is always there. S3 buckets and SFTP servers are destinations on a par: each has a name — s3, offsite, sftp, box… — its own credentials, and the same commands. A profile sends its runs to any of them; --use sends profiles there as the destination is added.

bash
sudo cipi backup destination add s3 --bucket=acme-backups --key=AKIA… --secret-stdin \
    --endpoint=https://fsn1.your-objectstorage.com --region=fsn1 --use=default < secret.txt
sudo cipi backup destination add sftp --type=sftp --host=… --user=… --port=23 --use=default  # an SFTP server — below
sudo cipi backup destination list               # every destination, and the profiles that use it
sudo cipi backup destination show s3            # its settings — never a secret
sudo cipi backup destination edit s3 --region=nbg1  # only what is given changes
sudo cipi backup destination test [s3]          # reach each one with its own credentials
sudo cipi backup destination remove s3          # no profile may use it; the archives stay there
sudo cipi backup status [--json]                # destinations, profiles, last run, overdue, uncovered
ProviderEndpointRegion
AWS S3leave emptythe bucket's (eu-central-1…)
Hetzner Object Storagehttps://<location>.your-objectstorage.comfsn1, nbg1, hel1
Cloudflare R2https://<account-id>.r2.cloudflarestorage.comauto
DigitalOcean Spaceshttps://<region>.digitaloceanspaces.comthe Space's (fra1…)
Backblaze B2https://s3.<region>.backblazeb2.comeu-central-003…
Scalewayhttps://s3.<region>.scw.cloudfr-par, nl-ams, pl-waw
MinIO, Wasabi, othershttps://your-hostas the service says

The secret key. At a terminal it is asked, not shown as you type. --secret-stdin reads it from the first line of standard input, so it is not in ps, the shell's history or a log; --secret= still works at the server's shell. A key or a secret is printable characters with no space and no quote. Give Cipi a key limited to its bucket. Every bucket is reached with its keys before it is saved — a wrong key changes nothing.

A server set up when sudo cipi backup configure asked for a bucket ("the default bucket") carries on unchanged: that bucket is the destination s3, edited, tested and removed like any other. configure --bucket= --key= --secret-stdin … still works and does the same as destination add|edit s3.

Notified. Every change of where archives go — the setup, a destination added, changed or removed, the encryption key rotated — sends the backup_config notification (Security), with who did it: the owner of the server hears of it, also when it comes from the panel.

SFTP: a VPS, a Storage Box, a NAS#

A server reached over SSH is a destination like a bucket: a cheap VPS with a user for backups, a Hetzner Storage Box, a NAS at the office. Only SFTP is asked of it — no shell, no software of Cipi's.

bash
sudo cipi backup destination add box --type=sftp --host=u123456.your-storagebox.de \
    --user=u123456 --port=23 --path=cipi --use=default
ssh-copy-id -p 23 -s -i /etc/cipi/backup-keys/box.pub u123456@u123456.your-storagebox.de   # a Storage Box: its password, once
sudo cipi backup destination test box
The keyCipi makes an SSH key (ed25519) for each SFTP destination, kept on the server in /etc/cipi/backup-keys, readable by root only. It signs in with it, never with a password: no password of the remote is stored, anywhere
The remote accepts itA server of yours: append the public key to ~<user>/.ssh/authorized_keys there. A Storage Box: ssh-copy-id -p 23 -s … as above, which asks the box's password once. sudo cipi backup destination key box prints it again (--raw for the key alone)
The host keyLearned at the first connection and checked at every other one (/etc/cipi/backup-keys/known_hosts): a server that changes key afterwards is refused, not trusted
--pathThe folder for the backups, created if missing — relative to the user's login folder, or absolute with a leading /. Empty: the login folder
--port22 by default; 23 for a Storage Box
--testOn add and edit: write a small file there and remove it, as destination test does
--new-keyOn edit: a new key; install its public half on the remote again
Removesudo cipi backup destination remove box deletes its key here; the archives stay on the remote, and the public key in its authorized_keys until you take it out

Everything else is the same as for a bucket — they are on a par: retention prunes the old runs there, backup list, fetch and verify read them back, the archives are encrypted first with --encrypt. Several servers can share a Storage Box: each one writes under cipi/<profile>/ of its own --path, so give each its own folder (--path=cipi/web1).

On a Hetzner Storage Box, turn on SSH support in its settings (port 23), and give each server a sub-account of its own with its own folder: a compromised server then reaches only its own backups. On a VPS of yours, a user that can only use SFTP in its folder (ForceCommand internal-sftp with ChrootDirectory) does the same.

How to choose, and a step-by-step for a Storage Box: Backups to a Hetzner Storage Box over SFTP.

3. Profiles#

bash
# every 30 minutes: databases only, on the server, last 48 runs
sudo cipi backup profile add hourly-db --scope=db --databases='shop,tenant_*' \
    --exclude-tables='*.jobs,*.telescope_*' --every=30m --keep=48 --dest=local
# every night: files + databases, encrypted, a bucket and an SFTP server, 14 days
sudo cipi backup profile add nightly --scope=all --cron='0 2 * * *' --keep-days=14 \
    --dest=local,s3,box --encrypt
FlagMeaning
--scope=all|files|dbWhat to take
--apps, --databases, --exclude-databasesGlob patterns; tenant databases created at runtime are found too
--exclude-tablesSkip noisy tables (*.jobs, *.telescope_*)
--exclude-pathsLeave folders or files out of the app archives (storage/app/uploads, *.mp4) — below
--every=30m|6h|1d or --cron='…'Schedule
--dest=local,<name>,…Where to send it: this server and destinations by name
--keep=N, --keep-days=N, --keep-weeks=NRetention
--encryptAES-256 before upload
bash
sudo cipi backup profile list | show nightly | edit nightly --keep-days=30
sudo cipi backup profile disable hourly-db | enable hourly-db
sudo cipi backup profile remove hourly-db [--purge]  # --purge also deletes its runs

Apps can declare their own profiles in cipi.yml (named <app> or <app>-*); server-wide profiles stay yours.

Leave big folders out#

A terabyte of uploads is better kept with rsync (or on object storage) than archived every night. A profile can leave paths out of the app archives:

bash
sudo cipi backup profile edit nightly --exclude-paths='storage/app/uploads,*.mp4'
sudo cipi backup run --profile=nightly --dry-run  # what each app leaves out
sudo cipi backup profile edit nightly --exclude-paths=  # everything again
RuleDetail
Relative to the appstorage/app/uploads leaves out shared/storage/app/uploads; wp-content/uploads a custom app's htdocs/wp-content/uploads
Patternstar wildcards, which also match across /: *.mp4 is every video, storage/app/*/cache any such folder
Some apps only<apps>:<pattern>, with an app name or a glob: shop:…, api-*:…
RefusedAbsolute paths (they would match nothing) and the whole app (*, shared, htdocs)
RecordedEach archive's meta.json lists excluded_paths, so a restore knows what comes back from elsewhere

Also as exclude_paths in a profile of cipi.yml, in the web panel and over the API. Which folders to leave out, cipi.yml examples for Laravel and WordPress, and how to keep excluded folders safe: Exclude files and folders from backups.

4. Encryption#

The bucket provider never sees readable data. The manifest stays readable so runs can be listed.

bash
sudo cipi backup key show  # store it off-server, now (logged and notified)
sudo cipi backup key rotate  # new key for future runs; the old one is kept next to it

Without the key, an encrypted backup cannot be restored by anyone. Runs taken before a rotation still need the old key.

5. Run, verify, restore#

bash
sudo cipi backup run [--profile=nightly] [--dry-run] [--detach]
sudo cipi backup list [--profile=nightly]
sudo cipi backup verify [--deep]          # does the newest run open?
sudo cipi backup prune [--profile=nightly] [--dry-run]  # apply the retention now
sudo cipi backup fetch nightly 2026-11-02_020000 --dest=/root/restore
sudo cipi db restore myapp /root/restore/databases/mariadb/myapp.sql.gz
tar -xzf /root/restore/apps/myapp/files.tar.gz -C /tmp/restore-files
Honesty checkEffect
Archive integrity tested before uploadA dump cut short by a full disk never replaces a good backup
Staleness watchdog (hourly)backup_stale when a profile hasn't succeeded in twice its interval
Empty fetch / nothing to verifyReported as an error, never as success
Prune errorsLogged and alerted, never swallowed

From the panel#

Everything above but downloading a run is in the web panel, on a server's Backups tab, and over the API, the PHP SDK and cipi-cli:

Set upA server without backups offers Set up backups: the local folder and the nightly profile, on the server. While backups are only there, the tab says so
S3 buckets and SFTP serversAdd an S3 bucket — a provider fills in the endpoint and the region — and Add an SFTP server — a Storage Box preset; the key shown with how to install it. Each asks which profiles to send there too (the ones that keep their runs on the server only are ticked). Test, Edit (an empty key or secret keeps the one the server has), Remove, the same for both
Encryption keyShow the key (asked first; logged and notified on the server), Rotate
RetentionPreview the retention, Apply the retention
Profiles and runsThe matrix of what each profile takes; create, edit, pause, run, verify

A secret key never rides a command line. The panel sends it to the API once; the API writes it to the CLI's standard input (--secret-stdin) in a synchronous call — never in a job, never stored, never answered back — and the form clears it. From the panel the CLI refuses --secret=, and refuses to move the local or temp folder (root creates the local one and makes it 0700: a path from the panel could be any directory). sudo cipi backup fetch is not in the panel's sudoers: a run is downloaded and decrypted at the server's shell.

A token with backups-manage can point backups at a bucket or a server of its choosing, and read the encryption key. Give it to whom you would give the backups; every such change is notified (backup_config).

Layout#

<destination>/cipi/<profile>/<YYYY-MM-DD_HHMMSS>/
├── manifest.json
├── apps/myapp/files.tar.gz        # + meta.json (excluded_paths, if any)
└── databases/mariadb/myapp.sql.gz

Files and databases are stored separately, so a database restores without unpacking an app. Staging uses /var/tmp (disk), not a small RAM-backed /tmp. Meilisearch indexes are not backed up: scout:import rebuilds them from the database.

Common problems#

ProblemFix
destination test failsWrong endpoint, region or key permissions on the bucket
SFTP: Permission denied (publickey)The remote doesn't accept the key yet: sudo cipi backup destination key <name> and add it there
SFTP: Host key verification failedThe remote's host key changed since the first connection. If you know why (a reinstalled server), remove its line from /etc/cipi/backup-keys/known_hosts
Profile overduesudo cipi backup status names it; check disk space and the run log
Can't open an encrypted archiveYou need the backup key from sudo cipi backup key show (store it off-server)
Archives too big, runs too slowLeave large uploads or media out with --exclude-paths and sync them with rsync

Questions#

QuestionAnswer
Where should backups go?Off-site: another provider or region — an S3-compatible bucket, or an SFTP server such as a Storage Box. Your own: Johnny.
Can the panel add a destination?An SFTP one, yes — the Backups tab makes the key and shows the public half to install. An S3 bucket is added here, on the server: it takes a secret key, which doesn't go through the panel.
How often?Databases every 30–60 minutes for busy apps, everything nightly. Backup guide.
Have I tested a restore?Do it now with sudo cipi backup fetch into a scratch folder: a backup you haven't restored is a hope.
