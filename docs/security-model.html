Security model

What Cipi isolates, hardens and encrypts — and why.

Security

Security on Cipi is the default, not an add-on: apps are isolated from each other, the server is hardened at install, secrets are encrypted, and every privileged action leaves a trace. This page is the map; each layer links to its details.

  • NetworkUFW 22/80/443, Fail2ban, CrowdSec, Zero Trust (Cloudflare Tunnel, Tailscale, NetBird)
  • Accesskey-only admin, no root login, alerts
  • Isolationuser, PHP pool, database, Valkey per app
  • SecretsAES-256 Vault, encrypted backups & sync
  • Patchingnightly PHP & stack patches, CVE reports
  • Auditdeploy ledger, event log, compliance

Layers#

LayerWhat Cipi doesDetails
NetworkUFW allows only 22, 80, 443; the panel can open ports and block addresses, never close those three. Fail2ban bans after 3 attempts, doubling up to 7 days; repeat offenders get a 7-day block. Unknown hostnames get an empty replyFirewall & bans, Nginx
SSHRoot login off; the cipi admin user is key-only; app users have their own password logins, which you can switch offSSH keys
PrivilegeApp users can't su; their sudo is a short list of helpers that take their own app's name and nothing else — restarting its workers, recording its deploys, its post-deploy health check, emptying its page cache. The web user's sudo is limited to an explicit list of cipi sub-commands; the API checks every command against a whitelist. Abilities that reach as far as SSH — ssh-manage, zt-manage, sync-manage — are given one by one; backups-manage can point backups at a bucket or a server and read their encryption key, and every such change is notified (backup_config)Panel architecture, API tokens
App isolationOne Linux user per app (home 750), its own PHP-FPM pool, open_basedir to its home, its own database user and Valkey instanceHow Cipi works
GitA separate read-only deploy key per app; signed webhooks; deploys run as the app userGit, Auto-deploy
SecretsConfigs, tokens and passwords encrypted at rest (AES-256); backups and sync archives encrypted before they leave. A secret the panel sends — an S3 key, a mesh key — reaches the server's CLI on its standard input, never a command line or a job, and is kept by neither panel nor APIVault, Backups
PatchingUbuntu security updates daily; PHP nightly with a patch-level report; Nginx, databases, Valkey, Node and FrankenPHP nightly, one at a timeStack upgrades, PHP
Updates of CipiNightly from GitHub, backed up first. Optionally: a delay before a new release is installed — and, once they are available, only releases signed by a key the server already trusts (signed releases are not available at the moment) — so a taken-over account can't reach every server overnightSafer self-updates
HardeningPHP pools lock down settings used by recent CVEs; Nginx never enables HTTP/2; TLS 1.2/1.3 with modern ciphersPHP, Nginx
DetectionAlerts on SSH logins, sudo/su, key changes; nightly malware scan; 5xx and service monitorNotifications, Malware scan
AuditHash-chained deploy ledger, one-year event log, ISO 27001 / SOC 2 evidence reportDeploy audit, Compliance
PrivacyNo telemetry; logs with IP addresses kept 90 daysLog retention

No web surface by default#

A fresh Cipi server has no admin panel: management happens over SSH. The web panel is opt-in, runs as an isolated app on its own domain with two-factor login (an admin can require it for every account), and talks to servers only through the API's whitelisted commands.

What isolation protects#

If one app is compromised (a vulnerable plugin, a leaked .env), the attacker gets that app's user:

They can'tBecause
Read other apps' filesHomes are 750, open_basedir confines PHP
Read other apps' dataEach database and Valkey instance has its own credentials
Become root or cipisu is restricted to the sudo group; an app user's sudo is a few helpers bound to its own app (workers, deploy audit, health check, cipi-cache-clear), each checking what it is given
Read Cipi's secretsEncrypted, readable by root only
Change the web serverVhosts and pools are root-owned
Reuse the deploy key elsewhereOne key per repository, read-only

Reboots after kernel updates are never automatic unless you enable cipi reboot auto; cipi pending tells you when one is due.
