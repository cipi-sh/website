Deploy & roll back

cipi deploy, releases, rollback, status and logs.

DeployEdit on GitHub

Cipi uses Deployer for all deployments. Every deploy is atomic: a new release directory is prepared fully before the current symlink is swapped, so traffic is never interrupted.

Deploy, list releases, roll back
$ cipi deploy shop
$ cipi deploy shop --releases
$ cipi deploy shop --rollback
Since v4.5.4 Cipi bundles Deployer 8, which requires PHP ≥ 8.3. cipi deploy and cipi deploy --rollback abort with a clear upgrade message before invoking Deployer when an app is still pinned to an older PHP version — switch it with cipi app edit <app> --php=8.3 (or higher) first.

Deployer version (v5.10.0+)#

Up to 5.9.x the installer downloaded https://deployer.org/deployer.phar, which now serves Deployer 6.8.0: no deploy:publish, so every deploy of a fresh server stopped at Task `deploy:publish` not found (#519). Since v5.10.0 Deployer comes from its GitHub release, pinned to 8.0.5, checked against the SHA-256 GitHub publishes for deployer.phar and asked its version before it is installed; setup.sh stops when it cannot install it, and cipi deploy refuses Deployer 6 with what to run. Migration 5.10.0 moves a server on Deployer 6 or 7 to 8.0.5 — keeping 7, and naming the apps, where an app still runs PHP below 8.3.

bash
dep --version                                                    # Deployer 8.0.5
# by hand, as root (what setup.sh and the migration run)
source /opt/cipi/lib/deployer-install.sh && cipi_deployer_install

Deploy pipeline#

Deployer and Composer run with the app's configured PHP version (e.g. /usr/bin/php8.5), not the system default. This applies to cipi deploy, cipi deploy --rollback, crontab deploy triggers, cipi sync import deploys, and the deploy / composer aliases in the app user's .bashrc.

  1. Stop queue workers (cipi worker stop)
  2. Clone repo into releases/N/
  3. Run composer install --no-dev (with app's PHP)
  4. Link shared/.env and shared/storage/
  5. Run artisan migrate --force
  6. Run artisan optimize
  7. Run artisan storage:link
  8. Swap current symlink atomically
  9. Restart queue workers
  10. Prune old releases (keep last 5)
bash
cipi deploy myapp              # deploy latest commit
cipi deploy myapp --rollback   # instant rollback to previous release
cipi deploy myapp --releases   # list releases with date, how long the deploy took (v5.7.2+), commit and subject
cipi deploy myapp --history    # v5.9.0+ past deploys and rollbacks: result, release, duration, who started it [--limit=30] [--json]
cipi deploy --last             # v5.9.0+ the last deploy of every app [--json]
cipi deploy myapp --log        # timestamped deploy log (v5.1.0+)
cipi deploy myapp --log=200    # last 200 lines of it
cipi deploy myapp --status     # v5.8.4+ is a deploy running right now, whoever started it? [--json] [--tail=N]
cipi deploy myapp --audit      # v5.4.0+ who and what deployed each release [--days=90] [--json]
cipi deploy myapp --key        # show the SSH deploy key
cipi deploy myapp --webhook    # show webhook URL and token
cipi deploy myapp --unlock     # remove a stuck deploy lock (a failed deploy releases its own since v5.9.0)
cipi deploy myapp --snapshot   # v5.0+ opt-in DB dump before deploy
cipi deploy myapp --snapshot-required  # fail if snapshot cannot be taken
cipi deploy myapp --rollback-on-unhealthy  # v5.1.0+ undo a release that fails its healthcheck
cipi deploy myapp --trust-host=git.mycompany.com       # trust a custom Git server fingerprint
cipi deploy myapp --trust-host=git.mycompany.com:2222  # trust on non-standard port (also writes ~/.ssh/config)

Knowing whether a deploy worked (v5.1.0+)#

Up to 5.0.x a failing deploy could pass in silence: the failure branch, its warnings, the rollback hint and the deploy_fail email were unreachable code, because a non-zero exit from Deployer killed the cipi process on the spot. Since v5.1.0:

  • Both paths email on success and on failure — the CLI and the automatic Git webhook alike. Subjects are visibly different (Cipi deploy succeeded: myapp release 55 … / Cipi deploy FAILED: myapp …), and the body names the branch, the release number, the commit hash and subject, its author and date, the duration, the previous release, the deploy log path and the post-deploy healthcheck verdict.
  • cipi deploy exits non-zero when the deploy failed, so CI and webhooks can see it. The same applies to cipi deploy --rollback.
  • The success email is sent after post-deploy verification, so it can never announce a successful deploy while the site is returning 500.

Reading the deploy log#

/home/<app>/logs/deploy.log used to be raw Deployer output appended forever, which made a deploy that failed overnight unreadable afterwards. Since v5.1.0 every line is timestamped and each run is bracketed by a banner naming the trigger (CLI or webhook), the branch, the release and the duration.

bash
cipi deploy myapp --log=100   # same as tailing /home/myapp/logs/deploy.log
cipi deploy myapp --releases  # release number, date, TOOK (5.7.2+), commit, subject

Release directories stay numeric — rollback depends on that ordering — so --releases adds the human detail on top rather than renaming anything.

Since v5.0, opt-in pre-deploy DB snapshots are available via --snapshot / --snapshot-required or a permanent app setting — see Pre-deploy DB snapshots. Octane apps use the laravel-octane.php Deployer template (reload/restart Octane on deploy); enable Node builds with cipi app edit <app> --node-build='…'.

Since v5.9.0 a deploy that fails releases its own lock: the next one starts without --unlock (the Laravel recipes end with after('deploy:failed', 'deploy:unlock'), and the update adds the line to the deploy.php of existing apps). A lock is still left behind when a deploy is interrupted — the process killed, the server restarted: use cipi deploy myapp --unlock to remove it before re-deploying. Not sure whether it is interrupted or still working? cipi deploy myapp --status (v5.8.4+) tells the two apart.

Is a deploy running? (v5.8.4+)#

A deploy started by a Git push has nobody watching it. cipi deploy <app> --status answers from what both deploy paths already write — the start and end banners of /home/<app>/logs/deploy.log — and from the processes still alive, so it covers cipi deploy, the panel, the webhook, cipi/agent and rollbacks alike. It is read-only and safe to poll; the panel does, to show a deploy it did not start.

bash
cipi deploy myapp --status
cipi deploy myapp --status --json --tail=20   # for scripts and the panel API, with the last 20 log lines
State Meaning
running A start banner with no end yet and a process still on it. phase is deploy while Deployer builds the release, post-deploy while the post-deploy steps, cipi.yml and the healthcheck run after it. current names the trigger (cli, panel, webhook, mcp, rollback), the branch, the previous release, the start time and the seconds elapsed.
queued The webhook has received a push and the per-minute cron has not started the deploy yet.
interrupted A start banner with no end and nothing alive any more — a reboot, a kill. The lock it left behind is what --unlock removes.
idle Nothing running. last says how the previous run ended: result, kind (deploy or rollback), release, duration, exit code, trigger.

Past deploys, and how long each took (v5.9.0+)#

Both deploy paths end a run with a banner in the deploy log — result, release, duration, exit code. The log is rotated every night, so the banner of yesterday's deploy is no longer in deploy.log but in deploy.log.1, and after that in a .gz. Anything that read the current file alone — the panel did — showed how long a deploy took until the first night and never again: a deploy you start is watched while it runs, one a Git push starts is looked at the day after. --history reads the rotated files too.

bash
cipi deploy myapp --history              # newest first: finished, result, release, took, trigger, branch
cipi deploy myapp --history --limit=100 --json
cipi deploy --last                       # every app: when it was last deployed and how it went
cipi deploy --last --json                # what the app list of the panel shows
  • A run is a deploy or a rollback, ok or failed, with its release, its duration in seconds, its exit code, what started it (cli, panel, webhook, mcp, rollback), the branch and the release it replaced. Times are ISO 8601 with the server's offset. The keys are those of last in --status --json.
  • Files are read newest first and only as far back as it takes; a run that starts before a rotation and ends after it keeps its start.
  • cipi deploy myapp --releases finds the duration of a release in the rotated logs as well.
  • Scripts that cannot be sure of the Cipi version put the flag first: cipi deploy --history myapp. A Cipi older than 5.9.0 takes the flag for an app name and answers not found; cipi deploy myapp --history on it would start a deploy. The panel API uses the first form.
