Install the panel

Requirements, install, SSL, domain changes and two-factor login.

Web panelEdit on GitHub

Requirements#

The panel talks to your servers exclusively through the Cipi REST API. Before installing it, make sure each server you want to manage has the API enabled with a token that covers the full ability set.

Install the panel
$ cipi api api.example.com
$ cipi gui panel.example.com
Each managed server needs cipi api installed and a Bearer token with all abilities. See the API setup guide to generate one; since Cipi 5.9.0, cipi api token create --name=gui --full-access creates a token that has every ability, including the ones later releases add.
  • A running Cipi server (Ubuntu 24.04 / 26.04) to host the panel — this can be one of the servers you manage or a small dedicated box.
  • A domain or subdomain of its own, pointed at that server with a DNS A (and AAAA) record, e.g. panel.example.com. The panel is a separate Laravel application with its own Nginx vhost and certificate. It cannot share a hostname with an app, or with the API, which needs its own too, e.g. api.example.com (see a domain of its own). Since Cipi 5.7.0, Cipi refuses a domain that is already taken.
  • cipi api enabled on every server you want to control, each with a full-ability token (include www-manage, status-view, and for app tooling apps-env, apps-auth, apps-artisan, apps-run, apps-deploy-config). For Node apps, redirects and proxies, managed servers need API 1.31+ and Cipi 5.4.1+ (the 5.4.1 migration opens those commands to the panel sudoers); the deploy audit needs Cipi 5.4.0+. Server → Disk needs API 1.33+, the disk-view ability and Cipi 5.5.2+ (migration 5.5.2). The app's cipi.yml tab needs API 1.35+, the yml-view / yml-manage abilities and Cipi 5.6.4+; the Environment field and the environment shown on the cipi.yml tab need panel 4.0, API 1.36+ and Cipi 5.8.0+. For server cockpit (PHP, SSH, services, SMTP, health, IP whitelist), managed servers need API 1.15+ and Cipi 5.0.6+. For .env / auth.json / Artisan / App commands, managed servers need API 1.14+ and Cipi 5.0.3+. For Octane create and FPM/Octane indicators, API 1.13+ and Cipi 5.0+. For multi-engine MariaDB/PostgreSQL and www redirects, API 1.12+ and Cipi 4.8+.

A token covering everything the panel uses (API 1.35):

bash
cipi api token create --name=gui --abilities=apps-view,apps-create,apps-edit,apps-delete,apps-suspend,apps-basicauth,apps-env,apps-auth,apps-artisan,apps-run,apps-deploy-config,aliases-view,aliases-create,aliases-delete,www-manage,redirects-view,redirects-manage,proxies-view,proxies-manage,node-view,node-manage,search-view,search-manage,deploy-manage,ssl-manage,dbs-view,dbs-create,dbs-manage,php-view,php-manage,ssh-view,ssh-manage,services-view,services-manage,smtp-view,smtp-manage,health-view,health-manage,packages-view,monitor-view,zt-view,disk-view,yml-view,yml-manage,ip-whitelist-view,ip-whitelist-manage,status-view

PHP, the FPM pool, the Nginx vhost and the scheduler are all provisioned for you by the installer — you do not set up a Laravel environment by hand.

Installation — cipi gui <domain>#

One command provisions the whole panel on a Cipi server: a dedicated PHP-FPM pool, an Nginx vhost for your domain, and a scheduler cron job. The Laravel app is bundled at /opt/cipi/gui, the same model used by the cipi-api package. Since Cipi 5.8.2 the command checks the DNS first — the domain must already point at the server, or it stops with the record to create (--skip-dns-check behind a NAT or proxy it cannot see through) — and ends with the Let's Encrypt certificate (--no-ssl to skip it).

bash
cipi gui panel.example.com

The installer prompts interactively for the first administrator account — an email and a password. The password must satisfy the panel's policy:

  • Minimum 12 characters.
  • At least one uppercase, one lowercase, one digit, and one special character.
  • No more than 4 identical consecutive characters.

Configuration is written to /etc/cipi/gui.json. Once the command finishes, open your domain in a browser and log in with the admin account you just created.

The domain you pass is the panel's alone. If you have an app on example.com on the same server, the panel goes on a subdomain such as panel.example.com, not on example.com or one of the app's aliases. Cipi refuses those, and refuses the API's domain. Picked the wrong one? cipi gui move changes it.

cipi gui <domain> issues the certificate itself (Cipi 5.8.2+). Before that, or after --no-ssl, the panel is served over plain HTTP until you run cipi gui ssl.

SSL — cipi gui ssl#

Issue (or re-issue) a free Let's Encrypt certificate for the panel's domain and switch it to HTTPS. cipi gui <domain> does this itself since Cipi 5.8.2; the command stays for a certificate skipped with --no-ssl or one that failed. It checks first that the domain points at the server (--skip-dns-check to go ahead anyway). The panel is HTTPS-aware and sets the correct forwarded headers behind the Cipi Nginx vhost.

bash
cipi gui ssl

The certificate renews automatically through the same ACME renewal that Cipi uses for app domains. Since 5.7.0 a failed certbot run is reported as a failure (exit 1). Before, the command could print “SSL installed” anyway.

Changing domain — cipi gui move#

Moves the panel to a new domain or subdomain. Admin accounts, 2FA enrolments and saved server connections stay; admins sign in again, since their sessions belong to the old domain.

bash
cipi gui move panel.newdomain.com            # move and issue the new certificate
cipi gui move panel.newdomain.com --no-ssl   # move now, certificate later (cipi gui ssl)
  1. Point the new domain at the server first (DNS A/AAAA record).
  2. The Nginx vhost is rewritten for the new domain. If nginx -t rejects it, the old vhost goes back and nothing else changes.
  3. /etc/cipi/gui.json and APP_URL are updated.
  4. SSL: the old domain's certificate is deleted, so nothing keeps renewing it, and one is issued for the new domain. If that fails, the panel is already on the new domain over HTTP: fix DNS or port 80 and run cipi gui ssl.

The managed servers need no change: the panel calls their API URLs, and their IP whitelists are by IP, not by domain. To move a managed server's API instead, run cipi api move on that server and update its URL under Connections.

Cloudflare Zero Trust: a panel routed through the tunnel is tied to its hostname (DNS record, tunnel route, Access app). Run cipi zt hostname remove --gui before the move, then cipi zt hostname add --gui and cipi zt access enable --gui after it. cipi gui move refuses to run until the hostname is off the tunnel.

Two-factor authentication (TOTP)#

The panel uses classic session login and supports optional TOTP two-factor authentication. Each administrator can enrol an authenticator app (Google Authenticator, 1Password, Aegis, …) from their profile. 2FA is opt-in per user, not forced. With single sign-on the identity provider is the authority for MFA: the TOTP step is skipped after an SSO sign-in and kept for password sign-ins.

If an administrator loses access to their second factor, an operator with shell access can clear it from the server with cipi gui reset-user, which rewrites the account and removes the 2FA enrolment.
