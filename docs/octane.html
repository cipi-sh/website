Laravel Octane

Run apps on FrankenPHP, convert existing apps and pin builds.

AppsEdit on GitHub

Since v5.0, Laravel apps can serve HTTP via Laravel Octane with the FrankenPHP server instead of a per-app PHP-FPM pool. Octane and classic FPM apps run side by side on the same Cipi server.

What Cipi configures#

  • Allocates a localhost port in 8100–8999 and stores octane / octane_port in apps.json
  • Nginx vhost uses proxy_pass to Octane and serves static files from current/public — no per-app FPM pool
  • Supervisor program ${app}-octane alongside queue workers
  • Deployer template laravel-octane.php links the app's pinned FrankenPHP build into each release and restarts / reloads Octane on deploy (v5.10.0+, see below)
  • .env: OCTANE_SERVER=frankenphp, OCTANE_HTTPS=true

App requirements#

Your Laravel repository must include laravel/octane and run php artisan octane:install --server=frankenphp. Octane starts after the first successful deploy.

Since v5.10.0 octane:install is still needed for the worker file and the .gitignore entries, but the frankenphp binary itself no longer comes from the repository or from Octane's own download: right after Composer vendors, the deploy links the app's pinned build into the release. If laravel/octane requires a newer FrankenPHP than the pin, the deploy stops before the release goes live and tells you to run cipi frankenphp upgrade <app>.

bash
# create an Octane app
cipi app create --user=myapp --domain=myapp.com \
    --repository=git@github.com:you/myapp.git --octane

# convert an existing FPM app → Octane (or the reverse)
cipi app convert myapp --to=octane
cipi app convert myapp --to=fpm

# tune Octane workers (also see app limits)
cipi app limits myapp --octane-workers=4

cipi app convert --to=octane|fpm rewrites the pool / vhost / Supervisor / Deployer template / .env, and re-applies SSL when a certificate is already present. Since v5.10.0 convert also turns the app's JIT off (the setting lives in a different place for FPM and Octane, so it is not carried over: run cipi app jit again after converting) and pins the app to a FrankenPHP build when it becomes Octane, or drops the pin when it goes back to FPM.

FrankenPHP builds, pinned per app (v5.10.0+)#

An Octane app answers on the PHP built into its FrankenPHP binary, which apt never patches. Up to 5.9.x that binary was nobody's: Laravel Octane downloads the latest FrankenPHP release into the project whenever it finds none there, octane:install puts frankenphp in .gitignore, and every release starts from a fresh checkout — so each deploy fetched whatever GitHub had that minute, a new PHP minor included.

Since v5.10.0 the binary is Cipi's. Builds live in /opt/cipi-frankenphp/builds/ (root's, read-only to the apps), each with the FrankenPHP and PHP versions inside it; one is pinned per app, and every deploy links it into the new release before it goes live. Octane downloads nothing, and the PHP an app answers on changes only when you say so.

bash
cipi frankenphp                       # each app's build, the PHP inside, patched or not
cipi frankenphp upgrade myapp         # newest build on myapp's PHP minor
cipi frankenphp upgrade --all
cipi frankenphp use myapp <build>     # pin a given build
cipi frankenphp import ./frankenphp   # a build made elsewhere — another PHP minor
cipi frankenphp adopt myapp           # pin the binary Octane downloaded
cipi frankenphp remove <build>        # or: prune
  • Upgrades stay on the app's PHP minor and FrankenPHP major. Octane restarts, has to answer on its port, and the previous build comes back when it does not. A release on another PHP minor (or a new FrankenPHP major) is announced once, never applied: move the app with cipi app edit myapp --php=8.6, then cipi frankenphp upgrade myapp.
  • Several PHP minors side by side. An app on 8.5 and one on 8.6 run different builds on the same server. GitHub publishes static binaries for one PHP minor at a time; to keep an app on an older one with its patches, build FrankenPHP on it with the static builder and cipi frankenphp import it.
  • Nightly patches: cipi autoupdate has a frankenphp component, with the same rules (cipi autoupdate off frankenphp to choose the moment).
  • A deploy whose laravel/octane asks for a newer FrankenPHP than the pinned build stops before the migrations, with the live release untouched — instead of letting Octane replace the binary when it starts.
  • A binary that came out of an app's own release (adopt) is that app's only: it is never offered to another app.
  • cipi php upgrade and cipi pending report the PHP inside each build; a restart pending (Octane still on the previous binary) is listed too.
Migration 5.10.0 pins, for each Octane app, the binary in its live release — the one it runs now: same bytes, nothing restarts, no app changes PHP. It adds the cipi:frankenphp task to each Octane app's deploy.php in place.
Octane tip: keep long-running queue work on cipi worker or Horizon — Octane handles HTTP only. Pair with Reverb for WebSockets.
