Valkey

Cache, sessions and queues on Valkey, shared or one instance per app.

Server & runtimeEdit on GitHub

Valkey is the in-memory data store that Cipi installs as part of the default stack. Since v4.5.6 Cipi provisions Valkey instead of redis-server. It excels at caching, session storage, message queues, real-time broadcasting, and rate limiting.

One instance per app (v5.9.0+)#

Until 5.9.0 the server had one Valkey and one password, and every app got it in its .env: any app could read and write the cache, the sessions and the queued jobs of every other app, and one FLUSHDB emptied them all. An app now has an instance of its own — cipi-valkey@<app>.service, running as the app's user, listening on 127.0.0.1 on a port of its own (from 6400), with its own password (REDIS_HOST, REDIS_PORT, REDIS_PASSWORD in the app's .env), its configuration in /etc/cipi-valkey/<app>.conf and its data in /var/lib/cipi-valkey/<app>. An idle instance costs about 10 MB of RAM.

bash
cipi valkey list [--json]         # which app uses which instance
cipi valkey isolate shop          # its own instance: keys copied, .env switched, workers restarted
cipi valkey isolate --all         # every app still on the shared one
cipi valkey share shop            # back to the shared instance
cipi valkey restart shop
cipi valkey flush-shared          # once nobody uses it: empty it and change its password
  • New Laravel apps get their instance from cipi app create (--valkey=shared keeps the old behaviour for one app). It is removed with the app.
  • Apps that exist are not touched until you run isolate. The app goes into maintenance mode, its workers stop, its keys are copied with their expiry — by the key prefix the application itself reports — the .env is switched, the config cache rebuilt, workers (queue, Horizon, Octane, Reverb) restarted, maintenance mode off: seconds. A copy that is refused leaves the app exactly where it was.
  • An app whose prefix cannot be read (no release deployed yet, an empty prefix) is not moved unless you pass --no-copy: it then starts empty, without maintenance mode. An app whose .env points Redis at another host, or through REDIS_URL, is left alone.
  • --maxmemory=256mb and --policy=allkeys-lru set a ceiling for the instance; without them it behaves like the shared one.
  • cipi app clone gives the clone its own instance and no longer copies the source's REDIS_*; cipi sync keeps this server's Valkey settings for an app that exists and gives an imported one an instance here.
  • cipi pending lists the apps still on the shared instance; a Valkey package upgrade restarts every instance.

Why Valkey instead of Redis#

Valkey is the truly open-source, BSD-licensed fork of Redis, stewarded by the Linux Foundation. It was created in 2024 after Redis Inc. relicensed Redis away from the permissive BSD license to the source-available SSPL / RSALv2 — a change that no longer met the open-source definition. Backed by AWS, Google Cloud, Oracle, and a large community, Valkey continues the same battle-tested codebase under a license that stays free forever. That makes it a perfect fit for Cipi's MIT, no-vendor-lock-in philosophy, and it ships natively in Ubuntu 24.04's Universe repository (packages valkey-server + valkey-tools) — no third-party PPA to trust.

Just as importantly, Valkey is a drop-in replacement: it speaks the exact same RESP protocol on the same port (127.0.0.1:6379), honours the same requirepass / bind directives, and reads the same RDB/AOF data format. Your apps need zero changes — the phpredis extension and your existing REDIS_* .env values keep working exactly as before.

How Cipi implements it#

  • Install — setup.sh installs and configures Valkey (/etc/valkey/valkey.conf, service valkey-server), bound to localhost only and protected with a password.
  • Service management — cipi service … manages valkey-server (the names redis-server, redis, and valkey are still accepted as aliases). It is added to the unattended-upgrades blacklist, so Cipi manages it instead of an automatic upgrade.
  • Credentials — stored under valkey_user / valkey_password in /etc/cipi/server.json (the legacy redis_* keys are still read as a fallback). Host: 127.0.0.1, Port: 6379.
  • Password reset — cipi reset valkey-password regenerates the password and restarts the service (cipi reset redis-password stays as an alias).

Migrating from Redis (4.5.6 / 4.5.7)#

Existing servers are switched to Valkey automatically on cipi self-update — no app .env editing required. The migration reuses the current Redis password (recovered from server.json or /etc/redis/redis.conf), forces an RDB SAVE and snapshots dump.rdb/AOF, purges redis-server, installs valkey-server + valkey-tools on the same port with the same requirepass / bind, restores the dataset, and rewrites server.json (redis_* → valkey_*) and the unattended-upgrades blacklist — so cache, sessions, and queued jobs survive the switch.

v4.5.7 corrects the package name to valkey-server (the Ubuntu 24.04 daemon package; 4.5.6 initially used valkey) and makes the migration fully self-contained and safe. It auto-enables the universe APT component when the package isn't found, runs a post-start health check (PING → PONG with the password), and rolls back to redis-server — restoring both the saved password and the dataset — if Valkey can't be installed or doesn't come up healthy. The dataset snapshot is kept until the switch is verified, then cleaned up. The migration is idempotent: servers already on Valkey skip it.

Laravel integration#

New apps use the database driver for cache, sessions and queues: Valkey is one instance with one password for every app of the server, and whoever has the password can read — and flush — every app's keys. The database driver keeps each app inside its own database and user. Switch an app to Valkey when you want it (faster cache and queues, Horizon, Reverb scaling) and trust every app on the server with that.

The password is in the installation summary; cipi reset valkey-password sets a new one and prints it (every app that uses Valkey then needs it). Add these variables with cipi app env myapp. The names stay REDIS_* — that is what phpredis and Laravel's redis driver expect, and Valkey answers on the very same socket:

env
REDIS_HOST=127.0.0.1
REDIS_PASSWORD=the-valkey-password
REDIS_PORT=6379
REDIS_PREFIX=myapp_   # one per app, so keys never collide

Then set the drivers for each use case:

  • Cache — CACHE_STORE=redis
  • Session — SESSION_DRIVER=redis
  • Queue — QUEUE_CONNECTION=redis (then cipi worker restart myapp)
  • Broadcasting — BROADCAST_CONNECTION=redis

The phpredis extension is installed with every PHP version Cipi installs; predis/predis works too, as a pure-PHP fallback. Both talk to Valkey transparently.
