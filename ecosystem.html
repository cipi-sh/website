Ecosystem · 9 pieces, 1 core

One core. Every way in.

Cipi starts as one command on a server. Around it grows a set of open-source pieces: settings in Git, an agent inside your app, MCP for your AI assistant, a REST API, a web panel, a CLI for your laptop, a PHP SDK and a WHMCS module. Use one, or all of them. They all end in the same place.

01

The core

Runs on every server. Free, MIT, no account, nothing phoning home.

Cipi core

cipi
Required

The server, in one command.

A CLI that installs a hardened Nginx, PHP, MariaDB or PostgreSQL, Valkey and Supervisor stack on Ubuntu, then creates and runs isolated apps on it. Everything else in the ecosystem ends here.

  • Every app sealed off: its own Linux user, PHP pool, database, vhost and deploy key
  • Zero-downtime releases, one-command rollback, health-checked auto-rollback
  • Let's Encrypt over HTTP or Cloudflare DNS, wildcards included
  • Encrypted backups to S3, sudo cipi sync between servers, monitor and alerts
  • UFW, Fail2ban, CrowdSec, Cloudflare Zero Trust, nightly PHP patches
wget -O - https://cipi.sh/setup.sh | bash
How it works →Quickstart →cipi-sh/cipi

cipi.yml

sudo cipi yml
Built in

Server settings, in your repository.

One file next to your code describes how the server runs the app. Change it in a pull request: Cipi shows the plan and applies it, all or nothing.

  • PHP version and ini, workers, Horizon, Reverb, scheduler
  • Domains, redirects, proxies, extra databases, crons, backups
  • plan before apply, or auto-apply on every deploy
  • Refuses anything outside the app's own namespace
sudo cipi yml plan shop

Inside your app

Optional packages that connect a Laravel app to its server and to your AI assistant.

Cipi Agent

cipi/agent
Laravel 12, 13

The app, connected to its server.

A Laravel package that gives your app what the server can't see from outside: signed push-to-deploy, a health endpoint, an MCP server and a GDPR-safe anonymizer.

  • Push-to-deploy from GitHub, GitLab, Bitbucket, Gitea, Azure DevOps
  • /cipi/health: database, cache, queue, storage, live release
  • cipi.yml validation in CI and in your editor
  • Anonymized database dumps for developers, staging and AI
composer require cipi/agent

MCP servers

/cipi/mcp + /mcp
Optional

AI on your real apps, with guardrails.

Two self-hosted MCP servers: one inside each app, one per server. Claude, Cursor or VS Code read real logs and schema, run safe commands and deploy.

  • App MCP: health, logs, schema, capped queries, Artisan, deploy
  • Server MCP: create apps, SSL, databases, backups
  • SQL and Artisan guards, read-only mode, secrets redacted
  • Every deploy recorded with who asked
php artisan cipi:mcp
MCP for AI →Docs →cipi-sh/agent
03

The automation layer

One API per server. Everything below talks to it, and it talks only to the core.

REST API

cipi/api
Optional

Every server, scriptable.

One command adds a REST API and an MCP endpoint to a server, on its own subdomain. The panel, cipi-cli, the SDK, WHMCS and your CI all speak to it.

  • 100+ endpoints: apps, deploys, domains, SSL, data, cipi.yml
  • Sanctum tokens with 40+ abilities, expiry and an IP allowlist
  • Async jobs you can poll, OpenAPI and Swagger UI at /docs
  • Calls an allowlist of cipi commands: destructive host operations stay on SSH
sudo cipi api api.example.com

Clients

Pick the ones that fit how you work. Skip them all and Cipi stays a lean CLI.

Web panel

cipi/gui
Needs the API

Your whole fleet, in the browser.

A self-hosted Laravel panel for your team, your clients or you on a phone. Many servers under one login, through each server's API.

  • Apps, deploys with live logs, databases, backups, logs and jobs
  • Admins and users, per-server and per-app permissions, invite links
  • TOTP two-factor and OpenID Connect single sign-on
  • Light and dark themes, phone layout
sudo cipi gui panel.example.com
Web panel →Docs →cipi-sh/gui

cipi-cli

cipi-cli
Needs the API

Every server, from your laptop.

A single Go binary that manages your Cipi servers without SSH. One profile per server, so a fleet is one command away.

  • Apps, deploys, cipi.yml, SSL, databases, PHP, services
  • Profiles per server, tokens stored 0600
  • Linux and macOS, amd64 and arm64, SHA-256 checksums
  • Anonymized dumps piped straight into your local database
cipi-cli prod deploy shop
Docs →Download →cipi-sh/cli

PHP SDK

cipi/sdk
Needs the API

Cipi, from your own PHP code.

A typed PHP client for the API. Build your own dashboard, onboarding flow or release tool from Laravel, Symfony or a plain script.

  • Apps, deploys, cipi.yml, domains, databases, backups, server
  • Writes return jobs: $cipi->wait($job) until done
  • Laravel facade and config, auto-discovered on 11, 12 and 13
  • Next to the agent, adds panel_* tools to the app's MCP
composer require cipi/sdk

WHMCS module

cipi-sh/whmcs
Needs the API

Sell Laravel hosting on your servers.

The official provisioning module maps the WHMCS lifecycle to Cipi: orders create isolated apps, suspensions take them offline, terminations remove them.

  • Create, suspend, unsuspend, change package, terminate
  • Laravel or custom apps (WordPress, static, any PHP)
  • Optional Let's Encrypt right after creation
  • Drop-in for WHMCS 8.x, no Composer dependencies
cp -r modules/servers/cipi ~/whmcs/modules/servers/

Questions

Do I need every piece?

No. The core is the only required part, and on its own it's a complete server tool. Add the API when you want a panel, cipi-cli, the SDK or WHMCS; add the agent when you want push-to-deploy, health checks or MCP inside an app.

What does it cost?

Nothing. Every piece is open source under the MIT license and runs on servers you own. There's no account, no subscription and no hosted control plane.

Which pieces need the REST API?

The web panel, cipi-cli, the PHP SDK and the WHMCS module are all clients of the API, so a server needs sudo cipi api <domain> and a token first. The core, cipi.yml and the Cipi Agent work without it.

What's the difference between the agent and the API?

The agent (cipi/agent) lives inside one Laravel app and sees that app: its logs, schema, deploys and health. The API (cipi/api) runs on its own domain and manages the whole server: every app, domains, certificates, databases and backups. See Agent vs API.

Can a client do something the CLI can't?

No. Every client ends in the same cipi commands you'd run over SSH, through an allowlist. Installing software, monitor thresholds and Zero Trust changes stay on the CLI by design.

Does anything send data to Cipi?

No. The core, the API, the panel and both MCP servers run on your machines. Nothing reports home.
